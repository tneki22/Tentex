# Качество кода Tentex

Этот код защищается на курсовой, и качество кода оценивается в баллах отдельно от функционала. Правила ниже — не абстрактный хороший стиль, а прямое следствие критериев оценки. Слои, доменные ошибки и сессии — в `tentex-api`, здесь про ремесло.

## Что именно оценивают

| Критерий | Дословно | Что делать в коде |
| --- | --- | --- |
| Технологичность | «стиль программирования, **степень независимости модулей** и **степень повторного использования кодов**» | Ноль циклов между пакетами, одно правило в одном месте |
| Универсальность | «количество и сложность **дополнительных функций**» | Функционал вознаграждается. Резать дубли и мёртвый код, а не возможности |
| Соответствие ТЗ | «функционал, **временные характеристики**, организация входных и выходных данных» | Долгая операция показывает прогресс, а не выглядит как зависание |

Методичка отдельно требует: «комментарии в формате генераторов документации doxygen, javadoc, rdoc» и «размещение фрагментов исходных текстов в основной части записки не допускается» — то есть листинги уйдут в приложение и должны читаться без автора.

## Докстринги

Обязательны у модуля, класса, публичной функции и у приватной длиннее 20 строк. Python — докстринг, TypeScript — TSDoc. Формат обязателен: документация должна собираться генератором, иначе требование методички не выполнено.

Пиши про **почему** и про инварианты. Пересказ имени функции — мусор:

```python
# плохо
def create_program_node(...):
    """Создаёт узел программы."""

# хорошо
def create_program_node(...):
    """Добавить узел в дерево программы под указанным родителем.

    Дерево ограничено четырьмя уровнями, вставка проверяет отсутствие циклов.
    Изменение идёт через ревизионную блокировку: параллельная правка того же
    проекта получит `stale_program_revision`, а не молча перезапишет чужое.
    """
```

Обработчикам HTTP хватает одной строки: путь и схема документируют сами себя, добавь только нетривиальные коды ошибок.

Замер: `python backend/scripts/check_docstrings.py` (если скрипта ещё нет — считай через `ast`, обязательно на Python 3.13: на 3.9 файлы с `match` молча не парсятся и выпадают из статистики). На 01.09.2026 покрытие было 17,5%.

## Границы размера

| Что | Предел |
| --- | --- |
| Цикломатическая сложность | 12 |
| Вложенность | 3 уровня |
| Вызовов хуков в React-компоненте | 15 |

`match` или `if/elif` больше чем на 5 ветвей, где каждая длиннее трёх строк, — это не функция, а диспетчер. Вынеси ветви, оставь таблицу соответствия.

## Исключения не глотать

```python
# запрещено
except Exception:
    pass          # или молчаливый откат на резервный путь

# правильно
except LayoutParseError as exc:
    logger.warning("Разбор через layout не удался, откат на текстовый слой: %s", exc)
    diagnostics.append("layout_fallback")
```

Три требования: конкретный тип, логирование причины, признак в диагностике при откате. Молча проглоченное исключение — единственный класс ошибок, который невозможно найти по логам, когда что-то не заработает на демонстрации.

## Независимость модулей

Ядро домена зависит от **интерфейса** внешней системы, не от реализации. Если `projects` импортирует `ai.gateway.ModelGateway` напрямую — это нарушение, ставь порт.

Обратных импортов между пакетами нет. Никогда. Проверяется `import-linter`, а не глазами.

Перед тем как что-то удалить — найди обратные ссылки. В этом проекте связи держатся вручную, `relationship()` в модели нет, компилятор про них не знает. Один и тот же смысл может быть вшит в перечисление на бэкенде, тумблер в настройках, пункт меню и вкладку рабочей области одновременно.

## Одно правило — одно место

Перед новой функцией поищи, нет ли её уже. Места, где дубли появляются незаметно:

- проверки инвариантов («узел принадлежит проекту», «проект доступен для записи»)
- обходы дерева программы и поиск узла
- нормализация и сравнение заголовков
- сериализация сущности в ответ API
- границы транзакции
- расчёты, которые есть и на сервере, и на клиенте

Скопировал вместо выноса — через неделю копии разойдутся, и это будет баг, который придётся ловить дважды.

## Значения не в логике

Любой порог, таймаут, лимит — именованная константа с комментарием, откуда взялось число. Зависит от окружения — в конфигурацию.

`timeout=15` прямо в вызове недопустимо: на защите спросят «почему пятнадцать».

## Типы честные

`any`, `as any`, `@ts-ignore` запрещены — сейчас их в проекте ноль, не начинай. В Python `Any` только для действительно разнородных данных и с комментарием, почему.

Типы ответов API не писать руками, генерировать из OpenAPI.

## Термины и язык

Одна сущность — одно имя везде: модель, схема, тип на клиенте, интерфейс, записка. Не «тема» в одном месте и «вопрос» в другом.

Комментарии и докстринги — по-русски, весь проект. Терминологическая путаница на защите читается как непонимание предметной области.

## Мёртвый код

Удаляешь функцию — удаляй целиком: код, стили, типы, маршруты, тесты, записи в реестрах модулей, значения перечислений. Половина удаления хуже, чем ничего: остаётся тумблер, который ничего не включает.

Закомментированный код не коммитить. Демо-данные и сеятели не должны быть включены по умолчанию. Артефакты прогонов — в `.gitignore`.

## Тесты

На защите два вопроса: «как тестировался продукт» и «какие методы оценочного тестирования применяли и почему». Тесты — часть защищаемой работы.

- Проверяй наблюдаемое поведение, не реализацию. Рефакторинг без смены поведения не должен ломать тест
- Обязательные краевые случаи: пустой ввод, отсутствующий файл, дубликаты, повторный запуск (идемпотентность), гонка при одновременном изменении
- Однотипные случаи — `pytest.mark.parametrize`, не десять похожих функций
- Повторяющаяся подготовка — в фикстуры
- Имя теста — предложение с проверяемым правилом
- Удаляя функционал, назови число тестов до и после. Иначе потеря тестов пройдёт незаметно

## Как вводить новую проверку

Не включай строгое правило на код, который ему не соответствует: CI покраснеет, и правило выключат. Действуй храповиком:

1. Правило включается сразу и строго.
2. Все существующие нарушения объявляются известным долгом — `per-file-ignores` в ruff, `ignore_imports` в import-linter, baseline в ESLint.
3. CI зелёный с первого дня.
4. Записи из долгового списка только удаляются. Обратно не добавляются.

Новый код обязан соответствовать сразу, старый чинится постепенно, прогресс виден в диффе.

## Перед «готово»

Прогон проверок — по `verification-before-completion`. Дополнительно к нему:

- [ ] Докстринги у всего публичного, что добавил или тронул
- [ ] Ни одного `except Exception` без логирования
- [ ] Ни одного нового `any`
- [ ] Долговые списки в конфигах не выросли
- [ ] Удаление доведено до конца: ни одного осиротевшего тумблера, пункта меню или значения перечисления
