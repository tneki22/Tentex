## Что реально проверяется на 09.09.2026

Действующий CI находится в `.github/workflows/ci.yml`; предложения §3 не следует принимать за уже установленную конфигурацию.

- Backend: `ruff check` с текущим набором `E, F, I, UP, B, SIM`, затем `pytest`, `alembic upgrade head` на чистой базе и `alembic check`.
- Frontend: `tsc -b` при `strict: true` в `tsconfig.app.json` и `tsconfig.node.json`, затем `vite build`.
- Сейчас **нет** import-linter, ESLint, отчёта или порога coverage и `ruff format --check`. Ruff не проверяет заявленные ниже пределы 60 строк/complexity 12, докстринги и дополнительные семейства правил, пока они не добавлены в конфигурацию.
- Из файлов репозитория нельзя подтвердить защиту ветки `main`; это отдельная настройка GitHub.

§2 — желаемый стандарт ревью и развития кода. §3 и чеклист §4 — **предлагаемые усиления/критерии приёмки**, а не отчёт о действующих gate. Датированные замеры §5 сохранены как историческая база.

## 1. Что именно оценивают в коде

Из документа критериев, раздел «Рабочая версия программного продукта», 11 неделя, 30–50 баллов,
оценивает руководитель. Три пункта, и два из них — про код напрямую:

| Пункт критериев | Дословная формулировка | Что это значит в коде |
|---|---|---|
| Соответствие ТЗ | «выполнение требований к функционалу, временным характеристикам, организации входных и выходных данных, защиты» | Каждая функция из ТЗ работает и её видно в демонстрации. «Временные характеристики» — значит долгие операции не должны выглядеть как зависание |
| **Технологичность** | «проработанность модели, **стиль программирования**, **степень независимости модулей** и **степень повторного использования кодов**» | Ясный код, слои без циклов, одно правило — в одном месте |
| **Универсальность** | «**количество и сложность дополнительных функций**» | Богатый функционал вознаграждается. Резать надо дубли и мёртвый код, а не возможности |

Из методички 2021 года, дополнительно:

- **«Оформить в соответствии с „хорошим стилем“ программирования… рекомендуется использовать
  комментарии в формате генераторов документации doxygen, javadoc, rdoc».** Это прямое требование
  к формату комментариев: докстринги в Python, TSDoc в TypeScript, машиночитаемо.
- **«Размещение фрагментов исходных текстов программы в основной части записки не допускается»** —
  весь код идёт в приложения, поэтому листинги должны читаться без пояснений автора.
- Схемы алгоритмов — по **ГОСТ 19.701-90**. Значит алгоритмы, которые пойдут в записку, должны
  быть выделены в отдельные функции, а не размазаны по обработчику HTTP.
- Для UML явно предписано «руководствоваться стандартом UML».

**Практический вывод.** Три вещи стоят баллов и проверяются глазами: понятность кода при чтении,
отсутствие циклических зависимостей между модулями, отсутствие дублирования. Всё остальное —
следствие.

## 2. Правила

### 2.1. Документируй всё публичное

Правило методички про doxygen/javadoc — не про красоту, а про то, что документацию можно собрать
генератором. Значит формат обязателен.

**Python.** Докстринг у каждого модуля, класса и публичной функции. Одна строка — что делает,
дальше при необходимости — почему именно так.

```python
def link_answers_by_headings(session: Session, project_id: UUID, material_id: UUID) -> AnswersLinkResult:
    """Связать разделы файла ответов с вопросами программы по совпадению заголовков.

    В файле ответов заголовок раздела дословно повторяет формулировку вопроса,
    поэтому связь ставится детерминированно, без обращения к модели.

    Возвращает результат с числом связанных вопросов и списком спорных случаев.
    """
```

**TypeScript.** TSDoc у экспортируемых компонентов, хуков и функций API-слоя.

```ts
/**
 * Показывает разобранную страницу материала.
 * Компонент нейтрален: не знает ни про привязки, ни про проект.
 */
```

Плохой докстринг — пересказ имени функции. `"""Создаёт узел программы."""` у функции
`create_program_node` не добавляет ничего. Пиши либо про «почему», либо про инварианты,
либо не пиши.

Приватные функции (с подчёркиванием) документировать не обязательно, но если функция длиннее
20 строк — обязательно.

### 2.2. Одна функция — одно дело

Желаемые границы, при превышении которых функцию надо разбить (сейчас это ручное ревью; автоматизация предложена в §3.1):

- **60 строк** — верхний предел
- **12** — цикломатическая сложность
- **3 уровня вложенности** — глубже не опускаться
- Если в функции есть `match` или `if/elif` на более чем 5 вариантов, и каждая ветка длиннее
  трёх строк — это не функция, это диспетчер. Вынеси ветки в отдельные функции и оставь
  таблицу соответствия

Для React-компонентов: **больше 15 вызовов хуков в одном компоненте — сигнал разбить.**
Компонент, который держит состояние нескольких экранов, надо делить по экранам.

### 2.3. Ни одного молчаливого исключения

Запрещено:

```python
except Exception:
    pass          # или return None, или fallback без следа
```

Разрешено только так:

```python
except SpecificError as exc:
    logger.warning("Разбор через layout не удался, откат на текстовый слой: %s", exc)
    ...
```

Три требования: перехватывать конкретный тип, а не `Exception`; логировать причину;
если делаешь откат на резервный путь — оставить признак в диагностике, чтобы потом было видно,
что сработал резерв.

Это не педантизм: молча проглоченное исключение — единственная категория ошибок, которую
невозможно найти по логам, когда на защите что-то не заработает.

### 2.4. Зависимости идут в одну сторону

Слои и направление:

```
router/    → только HTTP: разбор запроса, коды ответов
service/   → только правила домена, транзакция начинается здесь
repo/      → только доступ к данным
models/    → схема
ports/     → интерфейсы для внешних систем (модели, распознавание)
```

Правила:

- Обработчик HTTP не содержит SQL и бизнес-правил
- Служба домена не знает про HTTP и не поднимает `HTTPException`
- Ядро домена зависит от **интерфейса** внешней системы, а не от её реализации.
  Если модуль `projects` импортирует `ai.gateway.ModelGateway` напрямую — это нарушение
- Обратных импортов между пакетами нет. Никогда

Это тот самый критерий «степень независимости модулей». Сейчас он проверяется ревью; автоматический import-linter только предложен в §3.2.

### 2.5. Одно правило живёт в одном месте

Перед тем как написать функцию, поискать, нет ли её уже. Типичные места, где дубли появляются
незаметно:

- проверки инвариантов («узел принадлежит проекту», «проект доступен для записи»)
- обходы дерева и поиск узла
- нормализация и сравнение заголовков
- сериализация сущности в ответ API
- получение сессии и границы транзакции

Если одно и то же нужно в двух пакетах — вынести в общий модуль, а не копировать.
Если скопировал — это не «быстрее», это гарантия, что через неделю две копии разойдутся.

Это критерий «степень повторного использования кодов».

### 2.6. Числа и строки не живут в логике

Любой порог, таймаут, лимит или размер — именованная константа наверху модуля с комментарием,
откуда взялось значение. Если значение зависит от окружения — в конфигурацию.

```python
# Строки ближе этого расстояния считаем продолжением абзаца, а не новым.
# Значение подобрано на PDF из методичек: у них межстрочный интервал ~14 пунктов.
WRAP_TOLERANCE_PT = 60
```

`timeout=15` прямо в вызове — нельзя. Это ровно тот вопрос, который задаёт руководитель:
«почему пятнадцать?».

### 2.7. Типы честные

- Python: аннотировать все аргументы и возвраты. `Any` допустим только для действительно
  разнородных данных (снимок JSON), и рядом должен быть комментарий, почему
- TypeScript: `any`, `as any`, `@ts-ignore` запрещены. Если тип не выводится — значит контракт
  неясен, надо исправить контракт, а не заглушить компилятор
- Типы ответов API не писать руками. Генерировать из схемы OpenAPI, которую отдаёт бэкенд

### 2.8. Тесты проверяют поведение

На защите есть два вопроса про тестирование: «как тестировался ваш программный продукт»
и «какие методы оценочного тестирования вы использовали и почему». Значит тесты — часть
защищаемой работы, а не служебный код.

Требования:

- Тест проверяет **наблюдаемое поведение**, а не внутреннюю реализацию. Если рефакторинг
  без смены поведения ломает тест — тест плохой
- Каждый тест: минимум один содержательный `assert` с осмысленным сообщением при падении
- Обязательно покрывать краевые случаи: пустой ввод, отсутствующий файл, дубликаты,
  повторный запуск (идемпотентность), состояние гонки при одновременном изменении
- Повторяющаяся подготовка данных — в фикстуры, а не копипастой в каждый тест
- Однотипные случаи — через `pytest.mark.parametrize`, а не десятью похожими функциями
- Имя теста — предложение, описывающее проверяемое правило:
  `test_повторная_привязка_не_плодит_дубли_и_не_затирает_ручной_ответ`

Держать зелёными постоянно. Красные тесты в репозитории обнуляют смысл всей затеи.

### 2.9. Один термин — одно понятие

Если сущность называется «узел программы» — она называется так везде: в модели, в схеме API,
в типе на фронтенде, в интерфейсе и в записке. Не «тема» в одном месте и «вопрос» в другом.

Отдельно: **язык комментариев один на весь проект.** В Tentex это русский — значит русский
везде, без вкраплений английских докстрингов.

Это важнее, чем кажется: на защите терминологическая путаница читается как непонимание
собственной предметной области.

### 2.10. Не оставлять мёртвого

- Удалённая функция удаляется целиком: код, стили, типы, маршруты, тесты, записи в реестрах
- Закомментированный код не коммитится. Для истории есть git
- Демонстрационные и сеющие данные не должны быть включены по умолчанию в рабочей сборке
- Артефакты (скриншоты, отчёты прогонов, кеши) не коммитятся, им место в `.gitignore`

## 3. Предлагаемое усиление автоматического контроля

Ниже — план, как превратить желаемые правила §2 в автоматические проверки. Эти конфигурации **не активны**, пока соответствующие зависимости, файлы и команды не добавлены в репозиторий и CI.

### 3.1. Предложение: расширить Ruff

Текущий выбор правил — `["E", "F", "I", "UP", "B", "SIM"]`. Добавить то, что закрывает §2:

```toml
[tool.ruff.lint]
select = [
  "E", "F", "I", "UP", "B", "SIM",   # уже есть
  "N",      # именование (§2.9)
  "ANN",    # обязательные аннотации типов (§2.7)
  "D",      # докстринги (§2.1) — требование методички
  "C90",    # цикломатическая сложность (§2.2)
  "PL",     # длина функций, число аргументов и ветвлений (§2.2)
  "BLE",    # запрет except Exception (§2.3)
  "TRY",    # культура исключений (§2.3)
  "ERA",    # закомментированный код (§2.10)
  "T20",    # print вместо логирования
  "ARG",    # неиспользуемые аргументы
  "RUF",    # прочие полезные проверки
]

[tool.ruff.lint.mccabe]
max-complexity = 12

[tool.ruff.lint.pylint]
max-statements = 50
max-args = 6
max-branches = 12

[tool.ruff.lint.pydocstyle]
convention = "pep257"

[tool.ruff.lint.per-file-ignores]
# Тесты: докстринги и аннотации не обязательны, длинные сетапы допустимы
"tests/**" = ["D", "ANN", "PLR2004"]
# Миграции генерируются, их не документируем
"migrations/**" = ["D", "ANN", "ERA"]
```

**Про докстринги важное.** Включение `D` на кодовую базу с текущим покрытием даст сотни
замечаний сразу. Не надо чинить всё за один раз. Порядок:

1. Сначала включить `D` только для доменных служб — там, где логика:
   `per-file-ignores` с `"app/*/router.py" = ["D103"]`, чтобы обработчики HTTP пока не требовали
   докстрингов (у них путь и схема сами документируют)
2. Дописать докстринги в модулях домена
3. Потом снять послабление с роутеров

### 3.2. Предложение: проверять границы модулей через import-linter

Критерий «независимость модулей» можно проверять этим инструментом. Предлагаемый файл `.importlinter`:

```ini
[importlinter]
root_package = app

[importlinter:contract:layers]
name = Слои приложения
type = layers
layers =
    app.main
    routers
    services
    repositories
    models

[importlinter:contract:core-independent]
name = Ядро не зависит от адаптеров
type = forbidden
source_modules =
    app.projects
    app.bindings
forbidden_modules =
    app.ai
    app.ocr
```

После добавления зависимости и согласования контрактов запускать в CI. Только тогда случайное нарушение границы станет gate сборки.

### 3.3. Предложение: добавить frontend-линтер

В `frontend/package.json` есть TypeScript/Vite и генерация типов OpenAPI, но ESLint отсутствует: нет ни зависимости, ни конфига, ни npm-скрипта, ни шага CI. `tsc` работает в строгом режиме и проверяет типы, но не заменяет правила React и стилевые проверки.

Поставить:

```
eslint typescript-eslint eslint-plugin-react-hooks eslint-plugin-react-refresh
```

Минимально обязательные правила:

- `react-hooks/rules-of-hooks` — ошибка
- `react-hooks/exhaustive-deps` — ошибка, не предупреждение. Именно это правило ловит
  устаревшие замыкания в `useEffect`, самый частый источник «данные не обновились»
- `@typescript-eslint/no-explicit-any` — ошибка (§2.7)
- `@typescript-eslint/no-floating-promises` — ошибка. Незамеченный отказ промиса — это
  ошибка, которая не видна в интерфейсе
- `max-lines-per-function` — предупреждение на 150 строк для компонентов

Добавить скрипт `lint` в `frontend/package.json` и завести его в CI.

### 3.4. Предложение: добавить контроль покрытия

Поставить `pytest-cov`, включить в CI отчёт покрытия. На вопрос «как тестировался продукт»
ответ «модульными тестами, покрытие N процентов по строкам, отдельно сквозные сценарии»
сильно лучше, чем «тестировал вручную».

Задать порог, ниже которого сборка падает, и поднимать его постепенно.

### 3.5. Целевой состав CI

Ниже **цель**, не текущий workflow:

```
pytest + покрытие
ruff check
ruff format --check
alembic upgrade head на чистой базе
alembic check
import-linter
tsc -b
eslint
vite build
```

Сейчас из этого списка CI выполняет `pytest` без coverage-gate, `ruff check`, оба Alembic-вызова, `tsc -b` и `vite build`. Формат, import-linter и ESLint не проверяются. Целевая защита `main` — слияние только с зелёной сборкой; её состояние задаётся в GitHub и этим документом не подтверждается.

## 4. Целевой чеклист перед сдачей руководителю

К 11 неделе сдаётся рабочая версия, её оценивают в баллах. Это критерии приёмки: пункты, которых нет в текущем CI, проверяются вручную до внедрения предложений §3.

**Работоспособность**
- [ ] Проект поднимается на чистой машине по инструкции из README без ручных доделок
- [ ] Сценарий демонстрации проходится от начала до конца, ни один шаг не требует объяснений
- [ ] Долгие операции показывают прогресс, а не выглядят как зависание
  («временные характеристики» из критериев)
- [ ] Демонстрация не зависит от интернета и внешних сервисов. Если функция требует внешней
      модели — есть заранее подготовленные данные или запись демонстрации

**Код**
- [ ] Все проверки CI зелёные
- [ ] Докстринги у всех публичных функций домена, документация собирается генератором
- [ ] Ни одной функции длиннее 60 строк
- [ ] Ни одного `except Exception` без логирования
- [ ] `import-linter` не находит циклов
- [ ] Ни одного `any` на фронтенде
- [ ] Мёртвый код, демо-данные и заглушки удалены или явно выключены по умолчанию

**Готовность к вопросам.** Методичка 2021 приводит вопросы защиты дословно. Четыре из девяти —
про код и решения, ответ на них должен быть виден в самом коде:

- «Уточните способ декомпозиции… Почему вы выбрали именно этот способ?» — ответ должен читаться
  по структуре каталогов. Если слои названы и разделены, ответ очевиден
- «Что показывает схема структурная программного обеспечения?» — схема должна соответствовать
  фактическим модулям, а не желаемым
- «Как тестировался ваш программный продукт?» — см. §3.4
- «Какие методы оценочного тестирования вы использовали и почему?» — знать разницу между
  функциональным, модульным, интеграционным и нагрузочным тестированием и уметь сказать,
