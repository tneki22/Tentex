# AGENTS.md

Общие правила работы над Tentex; `CLAUDE.md` импортирует этот файл. Tentex — локальный тренажёр подготовки к экзамену и изучения по программе, один пользователь, офлайн по умолчанию. Внешние модели опциональны.

## Источники истины

Перед правкой прочитай `STATUS.md` и только относящиеся к задаче документы:

| Вопрос | Источник |
| --- | --- |
| Что работает сейчас | `STATUS.md`, затем код и тесты |
| Что делать дальше | Текущий срез `PLAN.md` |
| Желаемое поведение и термины | `REQUIREMENTS.md` |
| Текущий интерфейс | `SCREENS.md` |
| Реализованный контракт подсистемы | Код и нужный документ из `docs/architecture/` (индекс — `README.md`) |
| Учебниковый режим | `TEXTBOOK_MODE.md` |
| Дизайн и обработка файлов | `DESIGN.md`, `LIBRARY_FILE_PROCESSING.md` соответственно |

`BRIEF.md` объясняет смысл продукта, когда он неясен. Датированные срезы и эскизы не заменяют текущее состояние. При расхождении проверь код, потребителей и тесты, затем поправь действующий документ.

## Структура и стек

`backend/` — FastAPI, SQLite; `frontend/` — React, TypeScript, Vite; `data/` — локальные данные вне Git. `frontend/src/app/screens.ts` — реестр экранов, `views.ts` — готовые маршруты. UI строится из токенов, примитивов Radix и доменных виджетов; подробности в `DESIGN.md` и `/ui-kit`. Версии и обоснования технологий — в зависимостях и `REQUIREMENTS.md`, не в этом файле.

## Цикл правки

1. Проверь статус рабочего дерева и чужие изменения. Выбери минимальные достаточные проверки по разделу ниже. В итоге назови выполненные проверки и их результат; объясни существенные ограничения проверки.
2. При изменении приложения перезапусти `docker compose restart web` или `docker compose restart api web`, если менялся бэкенд. В обычном Docker-запуске web отдаёт готовую сборку: после правок фронтенда сначала выполни `docker compose up -d --build web`. Автоперезагрузка доступна через `docker-compose.dev.yml`. Проверь нужный пользовательский сценарий и состояние контейнеров: горячее обновление на `localhost:5173` бывает ненадёжным.
3. Добавь только свои файлы и сделай осмысленный коммит, если задача не запрещает Git.

**Комитить и переносить в main после небольших правок, перезапускать чтобы пользователь увидел правки сразу.** Перед переносом проверь `main` и сохрани чужие незакоммиченные изменения. Для больших задач перенос в `main` выполняй по запросу пользователя. `git push` и PR — только по явному запросу.

Команды запуска: `npm run dev` или `docker compose up`. На фронтенде нет общего `npm test`; два точечных `node:test` запускаются вручную. Для бэкенда доступны `python -m ruff check .` и подсистемные проверки в `backend/scripts/`.

### Как выбирать проверки

Полный набор тестов **не запускай по умолчанию**, в том числе перед каждым коммитом или после мелкой правки. Проверки выбирай по изменённому поведению и его потребителям, а не по факту изменения файла.

- Только документация, инструкции, комментарии без изменения поведения — проверь diff; тесты, сборка и перезапуск контейнеров не нужны.
- Тексты и локальные стили интерфейса — проверь затронутый экран; для чистой правки текста/CSS typecheck, build и тесты не нужны.
- TypeScript/React — `npm run typecheck`; при изменении логики добавь существующий точечный тест или сценарий. `npm run build` нужен при изменении сборки, зависимостей, импортов ресурсов или поведения, зависящего от production-сборки. Lint запускай по изменённым файлам, если инструмент настроен.
- Бэкенд — Ruff по изменённым Python-файлам и тесты затронутого поведения: из `backend/` запускай `python -m pytest tests/<нужный_файл>.py -q` или конкретные тесты через `::test_name` / `-k`. Найди тесты и прямых потребителей изменённого кода; при общем контракте включи тесты затронутых подсистем. Профильный скрипт из `backend/scripts/` запускай, только если он проверяет сценарий, не покрытый выбранными тестами.
- Миграции — дополнительно проверь применение и согласованность схемы на одноразовой БД. Общие фикстуры, инфраструктура тестов, транзакции, очередь или широко используемый контракт требуют более широкого набора затронутых тестов.

Полный `python -m pytest` или весь E2E-набор запускай только по явному запросу пользователя либо при изменении общей инфраструктуры/контракта с влиянием на большую часть приложения, когда точечный набор не даёт достаточной проверки. **До запуска объясни конкретную причину полного прогона.** Сам по себе большой размер задачи не является причиной.

После успешной проверки не повторяй её без новых изменений, связанных падений или новой конкретной причины. При падении сначала повтори упавший тест; расширяй набор по найденной причине. Не запускай несколько одинаковых прогонов одновременно. Не добавляй тесты для мелких обратимых правок текста, стилей или документации.

### Проверка веб-интерфейса

Сначала существующий `npx playwright test <путь>`. Если сценария нет, используй `npx playwright-cli`: DOM-снимок, необходимые действия, короткий итог. Полный CDP нужен только для диагностики console/network. Для визуальной правки при необходимости сделай скриншот через Playwright. Computer Use не применяй.

## Worktree и агенты
Мелкие правки сразу делаются в main, если не мешают другим работам там. При больших задачах:
Один агент — одна задача — один worktree. Новая задача по умолчанию начинается от `main`: `git worktree add .worktrees/<задача> -b codex/<задача> main`. Перед началом проверь `git worktree list` и `git -C <путь> status`. Не переключай чужой worktree, не перезаписывай чужую работу; несколько агентов не правят один worktree. Между ветками переноси только коммиты через merge или cherry-pick, конфликты решай по содержимому. Не удаляй worktree через Проводник, `rm`, `git clean` или `reset --hard`; используй `git worktree remove` после сохранения изменений.

## Как писать

Русские тексты интерфейса, английские идентификаторы. Комментарий объясняет причину или инвариант. Цвета и размеры — через токены `tokens.css`; перед новым компонентом смотри `/ui-kit` и `tentex-ui`. Готовую библиотеку или опубликованный алгоритм предпочитай собственному механизму, если они подходят задаче. Изменения бэкенда сверяй с `tentex-api`, ревью качества — с `tentex-code-quality`, визуальную отделку — с `better-ui`.

## Словарь

Определения — в глоссарии `REQUIREMENTS.md`. Не смешивай узел программы, тему и экзаменационный вопрос; материал, фрагмент и блок; привязку и показатель покрытия. Проход 1 строит программу из материала, проход 2 соотносит блоки материала с темами. Эталонный ответ — образец для сравнения ответа пользователя.

## Границы

Актуальная линия отсечения — в текущем срезе `PLAN.md`, готовность — в `STATUS.md`. Покрытие материала ниже 100% не показывай как дефект: это результат измерения. Не возвращай исключённые функции из старых списков и не меняй решения по стеку без объяснения. Из навыков проекта используй только `.agents/skills/`; `.claude/skills` — локальное подключение, не отдельный источник.
