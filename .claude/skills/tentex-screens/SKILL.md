# Экран Tentex

Этап 1 — главный. Здесь проектируется весь продукт, и из описаний экранов потом механически выпадает схема базы.

## Порядок

**Описал экран → тут же сверстал его на выдуманных данных → пошёл к следующему.**

Не «сначала четырнадцать описаний, потом четырнадцать вёрсток». Вёрстка на заглушках сразу показывает, что описание неполное. На бумаге это не видно.

Описание идёт в `SCREENS.md`, вёрстка — в `frontend/src/screens/<Экран>.tsx` вместо `ScreenStub`.

## Пять обязательных пунктов

1. **Что на экране** — блоки, таблицы, панели, что где лежит
2. **Какие кнопки и действия** — и что происходит по каждому нажатию
3. **Какие состояния** — пусто · грузится · ошибка · внешние модели выключены
4. **Какие данные нужны, чтобы это нарисовать** — вот это потом станет базой
5. **Куда ведут переходы** — с какого экрана на какой

Пятый пункт сверяется с `frontend/src/app/screens.ts`: там лежит реестр всех путей.

## Как выглядит заполненный экран

> **Карта покрытия.** Таблица программы. Строка = узел программы, отступом показана вложенность.
>
> **Колонки:** формулировка · сколько фрагментов привязано и из каких файлов · худшее качество распознавания среди них · уровень цели · есть ли эталонный ответ · сколько раз отвечал и как · статус.
>
> **Сверху:** два числа покрытия, два числа прогресса (пройдено / подтверждено), дней до дедлайна.
>
> **Действия:** клик по строке → Среда темы · клик по статусу → всплывашка «чего не хватает до следующего статуса» · выделение поддерева → поставить уровень цели пачкой · фильтры (только непокрытые, только просроченные, только машинные привязки, вне текущей программы) · сортировки · кнопка «пересобрать программу».
>
> **Состояния:** программы нет ещё → предложение выбрать способ её получить · программа есть, материалов нет → все строки в «нет материала», это нормально, а не ошибка · идёт проход 2 → строки заполняются постепенно, видно счётчик · внешние модели выключены → кнопка пересборки предлагает только офлайновые способы.
>
> **Данные:** дерево узлов (формулировка, тип, родитель, порядок, уровень цели, статус, признак «вне программы»), счётчик привязок по узлу, худший флаг качества, число попыток и их исходы, метрики проекта.

Строка **Данные** — самая ценная. Из неё на этапе 2 собирается схема базы, поэтому пиши поля, а не «нужны данные о покрытии».

## Глубина по экранам

До состояния «по ним можно кодить», в этом порядке:

1. Проекты · 2. Мастер создания проекта · 3. Материалы · 4. Программа · 5. Карта покрытия · 6. Покрытие · 7. Среда темы · 8. Сессия занятия · 9. Просмотрщик источника

Эскизом, дорабатываются перед реализацией: очередь предложений · карточки · план подготовки · инбокс · настройки.

Одинаково глубоко проработанные четырнадцать экранов — это отдельный проект, и половина проработки устареет.

## Границы

- Данные выдуманные, руками в файле рядом с экраном. Никаких запросов к API на этапе 1 — его ещё нет.
- Компоненты берутся из UI-кита, см. скилл `tentex-ui-kit`. Новый компонент — только если в ките такого нет.
- Пустое состояние — не ошибка. Отдельно следи за FR-D17: покрытие материала ниже 100% интерфейс **не** показывает как проблему, это результат работы.
- Про «Среду темы»: в центре — работа над ответом (эталон, твой ответ, разбор). Чат — один инструмент из нескольких на полях, а не механизм в центре. Поставить чат в центр — значит перенести в Tentex потолок virtex.
- Два варианта среды темы (компактная и развёрнутая) уже обещаны в FR-D2, третий тумблер придумывать не надо.

## Готово, когда

Написан `SCREENS.md` по формату выше, и по свёрстанным заглушкам мышкой проходится весь путь: создал проект → загрузил материал → увидел программу → увидел покрытие → открыл тему → ответил на вопрос.
