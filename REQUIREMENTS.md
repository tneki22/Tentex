| **Формально** | «Веб-система подготовки к экзаменам и самостоятельного изучения с автоматическим формированием программы курса и двусторонней привязкой материалов» |

| **Демо-предмет** | Базы данных. Материалы: методичка (расширенная, с перекрёстными связями между главами) и файл с сокращёнными ответами по темам |
| **Лицензия** | MIT |
| **Развёртывание** | Self-hosted / локально, один пользователь на установку |
| **Срок** | Защита в декабре 2026 |

### Правило разрешения конфликтов

Курсовая с защитой первична. Критерий «пригодно для ежедневного использования» применяется **только к сквозному сценарию** «загрузил материал → получил программу → вижу покрытие в обе стороны → занимаюсь по темам». Всё остальное делается по критерию «достаточно для демонстрации на защите».

При выборе между простым и мощным решением выбирается простое, если оно не ломает сквозной сценарий.

### Глоссарий

| Термин | Значение |
|---|---|
| **Тема** | Центральный объект системы. То, что нужно освоить. Может быть экзаменационным билетом, главой учебника или личной целью «разобраться, как работают индексы» |
| **Программа** | Дерево узлов проекта до 4 уровней вложенности. Узел имеет тип: `раздел`, `тема`, `подпункт` |
| **Паспорт цели** | Ответы пользователя о том, зачем он берёт материал и что хочет получить. Вход для всех алгоритмов |
| **Фрагмент** | Кусок материала со ссылкой на файл, страницу и координаты |
| **Блок** | Структурная единица материала: заголовок вместе с подчинёнными ему фрагментами. Единица классификации при соотнесении |
| **Привязка** | Связь «тема ↔ фрагмент» |
| **Среда темы** | Рабочее пространство одной темы: материал, карточки, конспект, история |
| **Активность** | Единица работы над темой (чтение, ответ, карточка, SQL...) |
| **Попытка** | Факт выполнения активности |
| **Сила свидетельства** | Вес активности как доказательства того, что тема освоена: 0, 1, 2 или 3 |
| **Проход 1** | Построение программы из материала: map-reduce по главам |
| **Проход 2** | Соотнесение: полный перебор структурных блоков материала |
| **Агент свободного вопроса** | Модель, пишущая код против API проекта для ответа на произвольный вопрос по всему материалу |

## 1. Ключевые принципы

Инварианты. Если решение нарушает один из них — неверно решение, а не принцип.

**П1. Программа первична, документ вторичен.**
Центральный объект — список тем, которые нужно освоить. Материалы существуют как доказательная база под эти темы. Проект может существовать с программой и нулём материалов — это штатное состояние, а не ошибка.

**П2. Знания не извлекаются — они привязываются.**
Система не строит независимую базу фактов. Она хранит привязки «тема ↔ фрагмент источника (файл + страница + координаты)». Любая производная сущность (карточка, эталонный ответ, задача) сохраняет ссылку на фрагмент-источник и помечается при его исчезновении.

**П3. ИИ действует открыто и обратимо.**
Всё, что породила модель, помечено как машинное, несёт свой источник, отменяется одним движением и хранит историю. Модель применяет изменения сама там, где однозначна, и спрашивает там, где нет. Пользователь никогда не обнаруживает изменение, о происхождении которого не может узнать.

**П4. Детерминированное ядро не зависит от внешних моделей.**
Без интернета и без внешних моделей работают: разбор файлов и OCR, программа по оглавлению и импортом, полнотекстовый и векторный поиск, ручная привязка, чтение, конспект, карточки, тесты, пропуски, свободный ответ с проверкой по терминам, SQL-задачи, повторения по SM-2, план, карта покрытия, статистика.

**Явные исключения, требующие внешних моделей:** построение программы из материала (проход 1), соотнесение материала с темами (проход 2), свободный вопрос, ИИ-судья, генерация активностей, программа из знаний модели (слой 4), распознавание речи, автозаполнение паспорта цели.

Вход A (§2) не задействует внешние модели вообще.

**П5. Пользователь выбирает свой процесс.**
Карточки, повторения, устные ответы, SQL — модули, каждый включается и выключается. Кто-то хочет только читать и выписывать в тетрадь — система должна быть полезна и в этом режиме, и не должна за это упрекать.

**П6. Каждое утверждение системы имеет источник.**
Ссылка на страницу, на попытку, на дату, на слой каталога. Где источника нет — система прямо говорит, что источника нет, вместо того чтобы выдавать уверенное число.

**П7. Данные принадлежат пользователю.**
Локальное хранение, полный экспорт, отсутствие привязки к одному поставщику модели. **Единственное исключение: аудио устных ответов уходит внешнему провайдеру распознавания.** Это записано прямо и показывается пользователю при включении устного ответа.

**П8. Ничто из материала не теряется.**
Покрытие двустороннее: система следит не только за тем, чтобы у каждой темы был материал, но и за тем, чтобы каждый содержательный блок материала был рассмотрен. Нерассмотренного не остаётся по построению (§6.4); неотнесённое показывается пользователю как результат, а не замалчивается.

## 2. Три входа в систему

**FR-E1.** Система поддерживает три способа начать работу. Они различаются не настройками, а тем, какие механизмы запускаются.

| Вход | Что есть у пользователя | Откуда программа | Какие проходы работают |
|---|---|---|---|
| **A. Экзамен** | Список вопросов + файл с ответами | Программа = импортированный список, не строится | Ни одного. Привязки — разбор пар «вопрос → ответ». Полностью детерминированно |
| **B. Учебник** | Большой PDF, программы нет | Строится из материала под паспорт цели (проход 1) | Оба прохода |
| **C. Цель** | Только формулировка цели | Из каталога или знаний модели (слой 4) с меткой «источника нет» | Проход 2 — по мере добавления материалов |

**FR-E2.** Входы соответствуют трём шаблонам проектов (§3.2), но не жёстко: проект, начатый как C, после загрузки учебника может использовать проход 1.

**FR-E3.** Вход C стартует с нулевым покрытием: программа есть, материалов нет, все темы в «Пробелах» (§6.5). Это корректное состояние, а не ошибка. По мере добавления материалов пробелы закрываются.

**FR-E4.** Автоматический поиск материалов в сети не реализуется. Пользователь добавляет учебники и статьи сам.

## 3. Проекты

### 3.1. Проект как пространство обучения

**FR-P1.** Система поддерживает произвольное число независимых проектов. Проект = предмет, курс, экзамен, тема или книга. Содержимое проектов изолировано: своя программа, привязки, настройки, статистика.

**FR-P2.** Проект имеет: название, описание, иконку/цвет, необязательную дату дедлайна, статус (`активный` / `в архиве` / `завершён`), паспорт цели (§5.1), набор включённых модулей (§13).

**FR-P3.** Список проектов показывает по каждому те метрики, которые включены его настройками: покрытие программы, пройдено/подтверждено (§11.3), дней до дедлайна, долг по плану, дату последнего занятия. Отключённые метрики не показываются и не заменяются нулями.

**FR-P4.** Проекты можно архивировать и восстанавливать. Архивный проект не участвует в повторениях и напоминаниях.

**FR-P5. Разделение общего и проектного.** Файл, Страница, Блок, Фрагмент и векторные представления — **общие** для установки, дедупликация по хешу файла. Программа, Привязка, Активность, Попытка, Карточка, Конспект, Повторение — **принадлежат проекту**.

Следствие: один и тот же учебник, добавленный в два проекта, разбирается и OCR-ится один раз. Экспорт проекта включает копии общих файлов, на которые он ссылается.

**FR-P6.** Очередь дня работает внутри проекта. Сквозная очередь между проектами не реализуется (§22).

### 3.2. Шаблоны проектов

**FR-P7.** При создании проекта пользователь выбирает шаблон. Шаблон — **преднастроенный паспорт цели и набор включённых модулей, а не жёсткий класс**: любую настройку можно поменять.

| Шаблон | Вход | Что включено по умолчанию |
|---|---|---|
| **Экзамен по билетам** | A | Программа импортом · свободный и устный ответ · план до даты · повторения · без экрана «Неразобранное» |
| **Учебник** | B | Оба прохода · чтение · карточки · конспект · повторения · оба экрана покрытия |
| **Свободное изучение** | C | Программа из каталога/модели · богатая среда темы · карточки · без плана и дедлайна · мягкие напоминания |

**FR-P8.** Два разных подхода к одному предмету оформляются **двумя проектами**, а не переключением режима внутри одного. Типовой случай: проект «БД — экзамен» с файлом вопросов и ответов, и проект «БД — разбираюсь» с учебником. Решение принято сознательно: переключение режимов внутри проекта усложняет логику без выигрыша.

**FR-P9.** Настройки проекта можно сохранить как пользовательский шаблон.

## 4. Материалы и конвейер обработки

### 4.1. Приём

**FR-M1.** Поддерживаемые форматы: PDF (текстовый и сканированный), DOCX, TXT, MD, изображения (JPG/PNG), вставка текста напрямую, добавление по URL веб-страницы.

**FR-M2.** Материал добавляется через веб (drag-and-drop, выбор файла), через бота (пересылка документа/фото/текста) и из инбокса проекта.

**FR-M3.** Ограничения фиксируются явно и показываются до загрузки: до 500 страниц и до 100 МБ на файл. Превышение — понятная ошибка, а не падение.

**FR-M4.** До запуска обработки система показывает **оценку времени и стоимости**: сколько страниц, сколько из них требуют OCR, сколько примерно займёт разбор, сколько вызовов модели потребуют проходы и во сколько это обойдётся. Оценка стоимости прохода 2 вычисляется точно: число блоков ÷ размер батча × цена вызова. Запуск — по подтверждению.

### 4.2. Конвейер разбора

**FR-M5.** Разбор идёт фоновой задачей в отдельном процессе с постраничным прогрессом и оценкой оставшегося времени. Пользователь может продолжать работать, приостановить задачу и возобновить её.

**FR-M6.** Этапы конвейера:

1. Валидация файла (тип, размер, читаемость, защита паролем)
2. Извлечение структуры документа (для PDF — встроенный outline/закладки)
3. Постраничное извлечение текста
4. **Детекция скана:** если плотность извлечённого текста на странице ниже порога — страница считается изображением
5. Для таких страниц: рендер в растр → предобработка (выравнивание, бинаризация, шумоподавление) → OCR (рус + англ) → оценка уверенности
6. Присвоение странице флага источника текста: `native` · `ocr` · `ocr_low`
7. Разбиение на фрагменты **по структуре** (заголовки, абзацы, списки, таблицы). Для страниц с флагом `ocr` и `ocr_low`, где структура не восстанавливается, применяется деградированное разбиение по абзацам — этот факт помечается на фрагменте
8. **Сборка блоков:** фрагменты группируются в структурные блоки по заголовкам. Блок — единица классификации на шаге соотнесения (§6.4)
9. **Классификация блока:** `содержательный` / `служебный` (титул, оглавление, колонтитул, список литературы, предисловие, выходные данные). Служебные не участвуют в покрытии материала
10. Каждый фрагмент хранит: файл, страницу, координаты, уровень в структуре, флаг качества, ссылку на блок
11. Индексация: полнотекстовый индекс (BM25) + векторные представления

**FR-M7.** Флаг качества виден везде, где показывается фрагмент. Фрагмент со страницы `ocr_low` подсвечен предупреждением и никогда не выдаётся за достоверный текст.

**FR-M8.** Страницу можно открыть в просмотрщике: исходное изображение или страница PDF с подсветкой распознанных фрагментов и их привязок.

**FR-M9.** Текст страницы можно поправить вручную с переиндексацией затронутых фрагментов. **Подтверждённые привязки при этом сохраняются**: система переносит их на новые границы фрагментов и показывает список тех, которые перенести не удалось.

**FR-M10.** Материал можно удалить. Его привязки и производные сущности (карточки, эталонные ответы) помечаются осиротевшими, а не удаляются молча. Пользователь видит, какие темы потеряли покрытие, а их статусы пересчитываются: тема, чей статус держался только на удалённых фрагментах, возвращается в `нет материала` с явным уведомлением.

**FR-M11.** OCR реализуется полностью, но на демо-предмете применять его не к чему: оба имеющихся материала электронные. Для демонстрации используются фотографии страниц бумажного источника. До появления таких материалов ветка OCR может оставаться заглушкой с честным флагом в интерфейсе.

### 4.3. Дозагрузка

**FR-M12.** При добавлении материала в проект с уже собранной программой система показывает **дельту**: какие темы получили новые фрагменты, какие пробелы закрылись, какие фрагменты дублируют уже привязанные, какие содержательные блоки не отнеслись ни к одной теме.

**FR-M13.** Проход 2 при дозагрузке выполняется **только по новым блокам**. Уже классифицированные блоки не пересчитываются.

### 4.4. Длинные задачи

**FR-M14.** Любая задача длительностью более минуты обязана быть **возобновляемой**. Для проходов 1 и 2 чекпоинт — счётчик обработанных единиц («обработано 640 блоков из 1500»); после падения или перезапуска работа продолжается с последнего чекпоинта.

**FR-M15.** Результаты выдаются **прогрессивно**: программа появляется по разделам, привязки — по мере готовности. Пользователь может начать работать с первым готовым разделом, пока остальное досчитывается.

## 5. Формирование программы

> Ключевой раздел системы. Именно здесь определяется, будет ли продукт полезен.

### 5.1. Паспорт цели

**FR-G1.** У проекта есть **паспорт цели** — структурированный ответ на вопрос «зачем я это беру и что хочу получить». Оси паспорта:

| Ось | Варианты |
|---|---|
| **Зачем** | экзамен · рабочая задача · собеседование · общий интерес |
| **Срок** | есть дата · нет даты |
| **Стартовый уровень** | с нуля · что-то знаю · повторяю забытое |
| **Целевой результат** | знать о существовании · понимать · уметь применять · владеть свободно |
| **Фокус** | что важно и что не важно — свободным текстом или отметками по разделам |
| **Формат работы** | только теория · теория и задачи · много практики |
| **Бюджет времени** | минут в день |

**FR-G2.** Паспорт заполняется **формой**, а не диалогом. У формы есть кнопка **«предложить заполнение»**: один вызов модели по беглому обзору материалов или по формулировке цели подставляет значения, пользователь правит. Ветвящееся интервью не реализуется (§22).

**FR-G3.** Паспорт берётся из шаблона проекта, заполняется вручную или автозаполнением. Меняется в любой момент. При изменении система **предлагает** пересобрать программу и план, но не делает этого молча.

**FR-G4.** Паспорт — вход для построения программы, планировщика и генератора активностей.

### 5.2. Четыре способа получить программу

**FR-G5.** Программа проекта — **дерево узлов до 4 уровней вложенности**. Узел имеет тип: `раздел`, `тема`, `подпункт`. Раздел и тема — не разные сущности, а разные типы одного узла; это позволяет и произвольную вложенность, и групповые операции по поддереву.

**FR-G6.** Способы получения программы:

| № | Режим | Как работает | Нужна внешняя модель |
|---|---|---|---|
| 1 | **Импорт списка** | Готовый список билетов: TXT/DOCX/CSV/MD, с распознаванием нумерации | нет |
| 2 | **По оглавлению** | Извлекается структура PDF (outline/закладки) либо распознаётся страница оглавления. Главы → разделы, параграфы → темы | **нет** |
| 3 | **Из материала (проход 1)** | Map-reduce по главам: выделение тем, слияние, устранение дублей (§5.4) | да |
| 4 | **Из каталога** | Типовая программа предмета накладывается на материалы; при отсутствии предмета в каталоге — из знаний модели (§5.5) | зависит от слоя |

**FR-G7.** Режимы комбинируются в любом порядке. Типовая цепочка: вытащил оглавление → сверил с каталогом → дописал руками.

**FR-G8.** Режимы 1 и 2 — гарантированный офлайновый путь. Они обеспечивают работоспособность §5 без внешних моделей и являются резервным путём, если проход 1 прерван или слишком дорог.

**FR-G9. Дедупликация и слияние.** При добавлении темы система предупреждает о похожих и предлагает: объединить, сделать подпунктом существующей, оставить отдельно. Слияние импортированного списка билетов с собранной программой — отдельный экран, где сопоставление показывается парами с обоснованием.

### 5.3. Пересборка программы

**FR-G10. Пересборка не удаляет ничего.** Она показывает **диф** и предлагает три действия: добавить новые темы, объединить похожие, переставить порядок.

**FR-G11.** Тема, отсутствующая в новой версии программы, не удаляется. Она получает признак **«вне текущей программы»**: уходит из плана, очереди дня и метрик покрытия, но сохраняет привязки, карточки, конспект и всю историю попыток. Возврат в программу — одно действие.

**FR-G12.** Обоснование: любое другое поведение означает, что нажатие «пересобрать» может стереть накопленную работу, и пользователь перестанет им пользоваться.

### 5.4. Построение программы из материала (проход 1)

**FR-G13.** Проход 1 — **map-reduce по главам**, а не рекурсивная агрегация:

1. **map:** материал делится на главы (по структуре документа; при её отсутствии — по фиксированному числу страниц). На каждую единицу — один вызов модели: «перечисли темы этой части»
2. **reduce:** списки сливаются, дубли между главами устраняются, темы раскладываются по разделам, определяется порядок изучения

**FR-G14.** Порядок обработки — по порядку глав. Чекпоинт — номер обработанной главы. Ориентировочный объём: около тридцати вызовов на учебник.

**FR-G15.** Каждая предложенная тема несёт ссылки на страницы, из которых она выведена.

**FR-G16.** Паспорт цели влияет на результат: глубина дробления тем и их количество зависят от целевого результата и фокуса.

### 5.5. Каталог эталонных программ

**FR-G17.** Система умеет предлагать программу, опираясь на то, как предмет преподают вообще. Источники организованы **слоями с явным уровнем доверия**:

| Слой | Источник | Когда | Метка |
|---|---|---|---|
| 1 | **Встроенный каталог** | Предмет есть в поставке | «проверенная программа» |
| 2 | **Оглавление классического учебника** | Учебник в материалах или его структура в каталоге | «по структуре учебника *Название*» |
| 4 | **Знания модели** | Всё остальное | «не проверено, источника нет» |

**FR-G18.** Слой 3 (веб-поиск) не реализуется: это отдельная интеграция с парсингом выдачи и разметкой доверия к источникам, а пользы поверх слоя 4 она почти не добавляет.

**FR-G19.** Каждая тема, пришедшая из каталога, хранит свой слой и источник, и они видны в интерфейсе. Так П6 соблюдается даже на слое 4 — система прямо сообщает, что источника нет.

**FR-G20.** Слой 4 отключается тумблером. При выключенном работают слои 1 и 2 — офлайновый путь сохраняется.

**FR-G21.** Встроенный каталог поставляется с системой в виде набора файлов, пополняется вручную и является частью репозитория. На старте наполняется по демо-предмету «Базы данных».

**FR-G22.** Наложение эталонного курса на материалы даёт **сравнение**: какие темы стандартного курса в материалах есть, каких нет, что в материалах есть сверх курса.

### 5.6. Свойства темы

**FR-G23.** Тема имеет: формулировку, **тип узла**, положение в дереве, **уровень цели**, теги, статус, признак «вне текущей программы», эталонный ответ (необязательный), список ключевых пунктов, способ проверки (§9), настройки активностей, источник происхождения (импорт / оглавление / проход 1 / каталог со слоем / вручную).

**FR-G24. Уровень цели** — четыре градации, заменяющие числовой вес:

| Уровень | Что значит | Что делает система |
|---|---|---|
| **Знать о существовании** | Узна́ю термин, понимаю, о чём речь | Одна карточка, один проход, в плане почти не занимает места |
| **Понимать** | Могу объяснить своими словами | Материал и свободный ответ, редкие повторения |
| **Уметь применять** | Могу решить типовую задачу | Плюс задачи, повторения по расписанию |
| **Владеть свободно** | Могу объяснить, вывести, применить в новом | Всё, включая устный ответ, частые повторения |

**FR-G25.** Уровень цели ставится **пачкой по поддереву** одним действием, а не по одной теме. Значение по умолчанию берётся из паспорта цели (ось «целевой результат»).

**FR-G26.** Уровень цели определяет три вещи: набор предлагаемых активностей, численный порог перехода в статус `отработан` (§11.3), долю времени в плане (§12).

**FR-G27.** Эталонный ответ может быть: введён вручную, импортирован из файла с ответами (вход A), собран из привязанных фрагментов, сгенерирован моделью.

**FR-G28.** Ключевые пункты — короткий список того, что должно прозвучать в ответе. Используются детерминированной проверкой, проверкой устного ответа и ИИ-судьёй.

### 5.7. Карта покрытия

**FR-G29.** Главный экран проекта — таблица программы, где у каждой темы показано:

- число привязанных фрагментов и из каких источников;
- худшее качество распознавания среди привязанных фрагментов;
- уровень цели;
- есть ли эталонный ответ;
- сколько раз отвечали и с каким результатом;
- статус: `нет материала` · `есть материал` · `разобран` · `отработан` · `освоен`.

**FR-G30.** Правило перехода между статусами численно и **показывается пользователю по нажатию**: видно, чего именно не хватает до следующего статуса. Пороги выводятся из уровня цели.

**FR-G31.** Фильтры и сортировки: по статусу, разделу, уровню цели; «только непокрытые», «только просроченные», «только машинные привязки», «вне текущей программы».

## 6. Среда темы и привязка материала

### 6.1. Среда темы

**FR-D1.** **Среда темы** — рабочее пространство одной темы. Содержит: формулировку, эталонный ответ, привязанные фрагменты со ссылками, карточки этой темы, личный конспект, историю попыток, статистику, панель свободного вопроса.

**FR-D2.** Состав среды зависит от настроек проекта: в проекте-марафоне она компактна (материал, ответ, история), в проекте свободного изучения — развёрнута.

### 6.2. Прямая привязка: от темы к материалу

**FR-D3.** Сборка материала под тему:

1. Результат прохода 2 (основной источник привязок)
2. BM25-поиск по ключевым словам темы → топ-50
3. Векторный поиск по представлению темы → топ-50
4. Слияние рангов (RRF), склейка соседних фрагментов, дедупликация

**FR-D4.** Шаги 2–4 работают без обращения к внешним сервисам и являются резервным путём, а также движком поиска для свободных вопросов и дозагрузки.

### 6.3. Применение привязок

**FR-D5. Числовой уверенности у привязки нет.** Проход 2 возвращает решение, а не балл; калиброванной вероятности из него не извлечь, и любой порог был бы выдуманным. Обучаемый переранжировщик не реализуется (§22).

**FR-D6.** Правило применения:

- проход вернул **одну тему** → привязка применяется автоматически и помечается машинной;
- вернул **несколько тем** или явное «не уверен» → привязка идёт в очередь предложений.

**FR-D7.** Очередь предложений — вспомогательный инструмент, а не обязательный этап. Работа с темами не блокируется её наличием.

**FR-D8.** В среде темы каждая машинная привязка снимается одним действием («это не по теме»). Отмена обратима.

**FR-D9.** Каждое решение пользователя по привязке записывается в журнал действий (для undo, §19) и в статистику качества привязки.

**FR-D10.** Фрагмент можно привязать вручную: выделить кусок текста на странице в просмотрщике и указать тему.

**FR-D11.** Один фрагмент может быть привязан к нескольким темам. Система показывает это явно.

### 6.4. Обратная привязка: от материала к темам (проход 2)

**FR-D12.** Помимо прямой задачи «найти материал под тему» система решает обратную: **к какой теме относится каждый содержательный блок материала**.

**FR-D13. Единица классификации — структурный блок**, а не фрагмент. Заголовок вместе с подчинёнными абзацами классифицируется целиком, фрагменты наследуют решение блока.

Обоснование: абзац — слишком мелкая единица, соседние абзацы одной секции классифицировались бы независимо и давали бы шум. Блоками получается втрое дешевле по вызовам и точнее по контексту.

**FR-D14. Алгоритм прохода 2:** система идёт по всем содержательным блокам материала **ровно один раз**, батчами по несколько блоков за вызов, и для каждого получает решение. Полнота здесь — свойство конструкции, а не качества модели: непросмотренных блоков не остаётся по построению.

**FR-D15. Исходов классификации три:**

| Исход | Что значит | Куда идёт |
|---|---|---|
| `отнесён к теме` | Блок относится к одной или нескольким темам программы | Привязки |
| `служебный` | Титул, оглавление, колонтитул, список литературы, предисловие | Никуда, в метрику не входит |
| `содержательный, вне программы` | Содержательный материал, которому нет темы в программе | Экран «Неразобранное» |

**FR-D16.** Вводятся две метрики покрытия:

| Метрика | Формула | О чём говорит |
|---|---|---|
| **Покрытие программы** | доля тем, обеспеченных материалом | Хватает ли источников |
| **Покрытие материала** | отнесённые ÷ (отнесённые + вне программы) | Полна ли программа |

**FR-D17. Покрытие материала не обязано стремиться к 100%.** Категория «вне программы» — результат работы системы, а не дефект: именно из неё формируется экран «Неразобранное». Интерфейс не должен подавать значение ниже 100% как проблему.

**FR-D18.** Классификация служебности и отнесения исправима пользователем в обе стороны.

### 6.5. Экраны покрытия

**FR-D19.** Экран **«Пробелы»** — темы, под которые в материалах ничего не нашлось. Для каждой показывается, что именно искали и какой был лучший отвергнутый кандидат.

**FR-D20.** Экран **«Неразобранное»** — блоки с исходом «содержательный, вне программы». Для каждого показывается источник, страница и предложение: создать новую тему, привязать к существующей, пометить как служебное.

**FR-D21.** Оба экрана — равноправные результаты работы системы: «Пробелы» говорят, что не хватает источников, «Неразобранное» — что неполна программа.

### 6.6. Свободный вопрос по всему материалу

**FR-D22.** Свободный вопрос разрешён в среде темы, в сессии и в боте. Ответ всегда сопровождается ссылками на фрагменты. Если релевантного материала нет во **всём материале проекта**, система прямо говорит, что этого в материалах нет, и не выдумывает.

**FR-D23.** Простые вопросы («что такое третья нормальная форма») обслуживаются гибридным поиском (§6.2).

**FR-D24. Сложные вопросы обслуживаются агентом.** Материал **не кладётся в контекст модели**: он остаётся в базе, а модель получает небольшой API проекта (`pages`, `fragments`, `search`, `outline`, `sub_llm`) и пишет против него код, который сам решает, как обойти материал. Ответ копится в переменной и возвращается из неё.

Обоснование: форма таких вопросов заранее неизвестна, фиксированный цикл под них не напишешь. Примеры: «в каких главах упоминается нормализация и чем объяснения различаются», «что есть в методичке про транзакции, чего нет в файле с теорией». Второй — попарное сопоставление двух источников, задача класса, на котором поиск по замеру из [Recursive Language Models](https://arxiv.org/abs/2512.24601) даёт 24.7 против 58.0 у агента.

**FR-D25.** Реализация — библиотека [alexzhang13/rlm](https://github.com/alexzhang13/rlm), исполнение генерируемого кода — в песочнице (§10.4).

**FR-D26.** Перед запуском агента система показывает оценку стоимости вызова. Агент отключается тумблером; при выключенном свободные вопросы обслуживаются только поиском.

## 7. Учебные активности

**FR-A1. Активность** — единица работы над темой. Активность порождает **Попытку**, попытка порождает **Оценку**. Это позволяет считать прогресс одинаково независимо от способа работы.

**FR-A2.** Виды активностей:

| Вид | Что делает пользователь | Как проверяется | Сила свидетельства |
|---|---|---|---|
| **Чтение** | Читает материал темы, отмечает «разобрался» | Самооценка, факт времени | **0** |
| **Карточка** | Вспоминает, открывает обратную сторону | Самооценка (4 градации) | **1** |
| **Тест с вариантами** | Выбирает вариант | Детерминированно | **1** |
| **Пропуски** | Заполняет пробелы в определении | Детерминированно, с нормализацией | **2** |
| **Свободный ответ текстом** | Пишет ответ по памяти | §9 — от терминов до ИИ-судьи | **3** |
| **Устный ответ** | Отвечает голосом | STT → сверка с ключевыми пунктами (§16) | **3** |
| **SQL** | Пишет запрос | Сравнение результирующих множеств (§10) | **3** |

**FR-A3.** Конспект — **отдельная сущность, а не активность** (§13). Он не порождает осмысленной попытки.

**FR-A4. Сила свидетельства** определяет вклад активности в прогресс. Активности силы 0 двигают статус темы, но **не двигают интервалы повторения и не входят в подтверждённый прогресс**. Это не ограничение пользователя, а условие достоверности прогноза.

**FR-A5.** Для каждой темы настраивается, какие активности к ней применимы. Набор по умолчанию берётся из уровня цели и настроек проекта.

**FR-A6.** Активности создаются: вручную, детерминированно из привязанных фрагментов (пропуски — чистый алгоритм), генерацией моделью, извлечением из материала (§7.1).

**FR-A7.** Дистракторы для тестов подбираются из терминов того же раздела по близости — детерминированный алгоритм, внешняя модель не обязательна.

### 7.1. Извлечение задач из материала

**FR-A8.** Система находит в материале **готовые задачи и упражнения** (характерные заголовки, нумерация, форма изложения) и предлагает их как активности с привязкой к теме и ссылкой на страницу.

**FR-A9.** Если в материале есть ответы или решения к этим задачам, они привязываются как эталон. Если нет — задача помечается «без эталона», и проверка ограничивается самооценкой либо ИИ-судьёй.

### 7.2. Сессия занятия

**FR-A10.** Сессия — единый интерфейс для всех видов активностей. Система выдаёт активность, принимает ответ, показывает разбор, идёт дальше. Один каркас, рендерящий блоки под тип активности: формулировка, поле ответа, запись голоса, редактор SQL, разбор, карточка, фрагмент материала, итог сессии.

**FR-A11.** Порядок активностей в сессии определяется очередью дня проекта либо выбором пользователя (раздел, тема, «всё подряд»).

**FR-A12.** Лента сессии сохраняется, к прошлой сессии можно вернуться и перечитать разбор.

## 8. Карточки

**FR-K1.** Карточки — **отдельный раздел проекта** со своим экраном: список, поиск, фильтр по темам и разделам, редактор, массовые операции, режим повторения.

**FR-K2.** Карточка привязана к одной или нескольким темам, но живёт в общем банке проекта. Карточка без темы допустима.

**FR-K3.** Способы создания: вручную, из фрагмента (выделил текст → «в карточку», с автоматической ссылкой на источник), генерацией по теме, массовой генерацией по разделу.

**FR-K4.** **Режим повторения карточек**: выбрать темы, разделы или «всё подряд», задать длину сессии, пройти. Повторение карточек участвует в общем учёте на общих основаниях (§11).

**FR-K5.** Карточка, созданная из фрагмента, помечается осиротевшей при удалении источника (П2, FR-M10).

## 9. Движок проверки ответов

**FR-V1.** Способ проверки настраивается на уровне темы, по умолчанию — из уровня цели и настроек проекта:

| Уровень | Как работает | Требует внешней модели |
|---|---|---|
| **Точное совпадение** | Нормализация (регистр, пробелы, ё/е, пунктуация) и сравнение | нет |
| **Ключевые термины** | Наличие обязательных и отсутствие запрещённых терминов с учётом словоформ | нет |
| **SQL** | Сравнение результирующих множеств (§10) | нет |
| **Семантическая близость** | Векторное представление ответа против эталона, порог | нет (локальная модель) |
| **ИИ-судья** | Оценка по рубрике: покрытые пункты, ошибки, что упущено — с цитатами | да |
| **Самооценка** | Пользователь ставит оценку сам | нет |

**FR-V2.** Уровни комбинируются: сначала дешёвые и детерминированные, внешняя модель подключается, только если они не дали однозначного результата.

**FR-V3.** Результат проверки всегда объясним: показывается, какие ключевые пункты засчитаны, какие нет и почему. Оценка ИИ-судьи сопровождается цитатами из ответа пользователя и из эталона.

**FR-V4.** Пользователь может оспорить оценку одной кнопкой. **Оценка системы и решение пользователя хранятся раздельно, обе.**

**FR-V5.** Система показывает пользователю его собственную долю оспоренных оценок за период как метрику калибровки. Это не упрёк, а информация: систематическое завышение делает прогноз готовности недостоверным.

## 10. SQL и учебная база

**FR-X1.** Проект может содержать банк SQL-задач. Задача имеет: условие, эталонное решение, разбор, теги навыков, сложность, привязку к темам.

**FR-X2. Проверка — сравнение результирующих множеств** (с учётом порядка строк или без, настраивается на задаче), а не сравнение текста запроса.

**FR-X3.** В проекте может быть **учебная база** — схема и наполнение, поставляемые как файл.

**FR-X4.** Учебная база выполняется на **том же движке, что и основная БД системы** (SQLite), в изолированной копии файла, открытой на чтение. Отдельный сервер БД не поднимается, песочница для SQL не требуется.

**FR-X5.** Диалект SQL явно указывается в условии задачи. Места, где диалект существенно отличается от PostgreSQL, помечаются в разборе. Целевой охват — типовые аналитические запросы: соединения, группировки, подзапросы, `EXISTS`, оконные функции, CTE. Планы выполнения и настройка производительности разбираются **теоретически**, без практических задач.

**FR-X6.** Задачи с кодом на Python не реализуются (§22). Архитектура — адаптеры, добавление языка не требует переделки.

**FR-X7.** Результат прогона показывается таблицей: тест, статус, время, ожидалось/получено.

**FR-X8.** Ошибка синтаксиса, таймаут, неверный результат — отдельные, понятно оформленные состояния интерфейса, а не «что-то пошло не так».

**FR-X9.** История решений задачи сохраняется, прошлые попытки можно сравнить.

**FR-X10.** Модель может дать **подсказку следующим шагом**, но не готовое решение, пока пользователь не запросил разбор явно.

**FR-X11. Исполняемые демонстрации.** Система может сгенерировать и выполнить запрос для показа правильного ответа. Результат сохраняется вместе с темой.

### 10.4. Песочница

**FR-X12.** Песочница нужна для двух вещей: исполнения кода, который пишет агент свободного вопроса (§6.6), и исполняемых демонстраций.

**FR-X13.** Изоляция: Docker-контейнер с жёсткими лимитами (время, память, размер вывода). Сеть закрыта для демонстраций и открыта только к шлюзу моделей для агента.

## 11. Повторения и прогресс

### 11.1. Планировщик повторений

**FR-R1.** Алгоритм повторений — **SM-2**, реализованный полностью. Обучаемая модель памяти не реализуется (§22, §25).

**FR-R2.** Повторением считается любая активность с **силой свидетельства 1 и выше**. Устный ответ, SQL, свободный ответ, карточка — всё обновляет память по теме, но с разным весом.

**FR-R3.** Настройки: лимит новых в день, лимит повторов в день, максимальный интервал, поведение при провале, тихие дни, **граница суток** (во сколько начинается новый учебный день — по умолчанию 4:00, чтобы занятия ночью относились к предыдущему дню).

**FR-R4.** Очередь дня собирается алгоритмом с приоритетами: просроченные → по плану → новые, с перемешиванием по разделам и ограничением по прогнозируемому времени (алгоритм А1, §20).

**FR-R5. Прощение долга.** Если пропущено больше N дней, система предлагает не «догнать 200 повторений», а пересобрать очередь по приоритету и списать остаток. Накопленный долг не показывается как красное число без предложения выхода.

### 11.2. Статусы темы

**FR-R6.** Статусы и правила перехода:

| Статус | Условие |
|---|---|
| `нет материала` | привязок нет |
| `есть материал` | есть привязки, попыток не было |
| `разобран` | отмечено «разобрался» или ≥1 успешная попытка любой силы |
| `отработан` | набрано N успешных попыток силы ≥1 |
| `освоен` | `отработан` + последняя проверка успешна + пройдено ≥1 повторение по SM-2 |

**FR-R7.** Порог N выводится из уровня цели:

| Уровень цели | N | Дополнительно |
|---|---|---|
| Знать о существовании | 1 | — |
| Понимать | 2 | — |
| Уметь применять | 3 | — |
| Владеть свободно | 4 | минимум одна попытка силы 3 |

**FR-R8.** Правило перехода показывается пользователю по нажатию на статус (FR-G30).

### 11.3. Два показателя прогресса

**FR-R9.** Прогресс по проекту выражается **двумя независимыми числами**:

| Показатель | Определение | Куда идёт |
|---|---|---|
| **Пройдено** | доля тем в статусе `разобран` и выше | Темп, план, ощущение движения |
| **Подтверждено** | доля тем в статусе `отработан` и выше | Прогноз готовности |

**FR-R10.** Система **не упрекает** за расхождение между показателями. Прочитать и отметить галочкой — законный способ работы.

**FR-R11.** Прогноз готовности (§12) строится **только на подтверждённом**. При недостатке данных выводится «прогноз недоступен: недостаточно данных» вместо числа.

## 12. Планирование подготовки

**FR-S1.** У проекта может быть дата дедлайна. Тогда система строит **план до даты**: раскладывает темы по дням с учётом уровня цели и ограничений (лимит в день, не больше K новых, просроченные вперёд, темы одного раздела рядом). Алгоритм А3, §20.

**FR-S2. Прогноз готовности** — доля программы, которую пользователь будет помнить на дату экзамена при соблюдении плана. Показывается **интервалом, а не точкой**, с указанием, на скольких наблюдениях построен. При недостатке данных не показывается вовсе (FR-R11).

**FR-S3.** При отставании план пересчитывается, и система прямо говорит о последствиях, называя объём работы и предлагая приоритет: какие темы дадут наибольший прирост готовности за оставшееся время.

**FR-S4.** Темы уровня «знать о существовании» и «понимать» не расходуют бюджет плана наравне с «уметь применять» и «владеть свободно». Указание уровня по разделу — основной инструмент управления нагрузкой.

**FR-S5.** Режим без дедлайна: свободный темп, только повторения и мягкая дневная норма.

**FR-S6.** Долг переносится с настраиваемым правилом: догонять сразу, размазать по остатку, простить (FR-R5).

**FR-S7. Календарь нагрузки** вперёд: сколько повторений выпадет на каждый день ближайшего месяца.

**FR-S8.** Сквозная очередь дня между проектами не реализуется (§22). Приоритизация между проектами — задача пользователя, список проектов на главном экране показывает дедлайны и долг.

**FR-U4.** Отключение модуля убирает его из интерфейса полностью. **Данные модуля при этом сохраняются**: включение обратно возвращает всё, что было накоплено.

## 14. Telegram-бот

**FR-B1.** Бот — второй клиент к тому же серверу. Всё, что сделано в боте, немедленно видно в вебе и наоборот.

**FR-B2.** Привязка аккаунта одноразовым кодом из веб-интерфейса.

**FR-B3.** В боте доступны: сессия занятия, разбор ответа, «объясни» и «подсказка», свободный вопрос, карточки и их повторение, прогресс, инбокс, напоминания.

**FR-B4.** В боте **недоступны** функции, нечитаемые в формате чата: редактор SQL, редактирование программы, просмотрщик страницы с координатами, карта покрытия, «Пробелы» и «Неразобранное». Там бот присылает ссылку на веб.

**FR-B5.** Ответ принимается текстом, голосовым сообщением, кнопками самооценки — в зависимости от типа активности.

**FR-B6.** После ответа приходит разбор: оценка, что упущено, цитата из материала со ссылкой, кнопки «дальше», «показать материал», «отложить», «стоп».

**FR-B7.** Сессия прерывается в любой момент без потери прогресса и продолжается в вебе.

**FR-B8.** Типы напоминаний: по плану · по отставанию · по дедлайну · по накопленному долгу · утренняя сводка и вечерний добор.

**FR-B9.** Настройки: время, дни недели, тихие часы, **единый глобальный максимум сообщений в день поверх всех проектов**, отключение по проекту и глобально.

**FR-B10.** Напоминание всегда несёт кнопку немедленного действия («начать», «отложить на 2 часа», «не сегодня»).

**FR-B11.** Антиспам: после трёх подряд проигнорированных напоминаний частота автоматически снижается и бот предлагает изменить расписание.

**FR-B12.** Команда «Прогресс» присылает сводку: покрытие, пройдено и подтверждено, серия дней, что сделано за неделю, ближайший дедлайн, топ-3 просевших раздела.

**FR-B13.** Любое пересланное боту сообщение (текст, фото, документ, ссылка) попадает в **инбокс** выбранного проекта и разбирается: стать материалом, темой, заметкой или карточкой.

**FR-B14.** Сущности, созданные через бота, помечаются машинными и обратимы на общих основаниях (П3).

## 15. Подсистема внешних моделей

### 15.1. Роли

**FR-I1.** Полный реестр задач, где применяются внешние модели:

| Роль | Что делает |
|---|---|
| Автозаполнение паспорта цели | Один вызов, предлагает значения формы |
| Построение программы (проход 1) | Map-reduce по главам |
| Соотнесение материала и тем (проход 2) | Классификация блоков батчами |
| Программа из знаний модели (слой 4) | Один вызов, метка «источника нет» |
| Извлечение задач из материала | Находит упражнения и их решения |
| Генерация активностей | Карточки, тесты, дистракторы |
| Проверка свободного ответа (ИИ-судья) | Оценка по рубрике с цитатами |
| Оценка полноты устного ответа | Какие ключевые пункты прозвучали |
| Агент свободного вопроса | Пишет код против API проекта |
| Объяснения и подсказки | Со ссылками на материал |
| Исполняемые демонстрации | Генерация запроса для показа ответа |
| **Распознавание речи (STT)** | Транскрипт с пословными таймингами. Внешний сервис |

**FR-I2.** Каждую роль можно отключить отдельно. Есть глобальный тумблер «работать без внешних моделей». При выключении соответствующие функции становятся недоступны, и об этом сообщается прямо.

### 15.2. Механизмы обработки материала

**FR-I3. Проход 2 (полный перебор блоков) — основной механизм соотнесения.** Полнота обеспечивается конструкцией: каждый содержательный блок рассматривается ровно один раз.

**FR-I4. Поиск (BM25 + векторы) — вспомогательный механизм.** Применяется для: свободных вопросов простой формы, дельты при дозагрузке, работы без внешних моделей, подсказки кандидатов в интерфейсе. Результат поиска — не ответ, а набор фрагментов со ссылками.

**FR-I5.** Поиск **не используется как основной механизм привязки**. Обоснование: поиск оптимизирует топ-k под запрос и структурно оставляет часть материала непросмотренной (§25).

**FR-I6.** Векторные представления считаются **локальной моделью**, а не через внешний API — иначе нарушается П4.

### 15.3. Провайдеры и стоимость

**FR-I7.** Внешние модели подключаются через **единый OpenAI-совместимый интерфейс** — этого достаточно для OpenRouter, Groq, локальных серверов и большинства провайдеров. Отдельные адаптеры под каждого не пишутся.

**FR-I8.** Модель выбирается под каждую роль отдельно. Роль «агент свободного вопроса» требует модели, уверенно пишущей код; остальные роли работают на дешёвых моделях.

**FR-I9.** Ключи хранятся на сервере в зашифрованном виде и никогда не попадают на клиент.

**FR-I10.** Учёт расхода: токены и стоимость по каждому вызову, сводка по проекту, лимиты (дневной и на операцию) с предупреждением **до** превышения. Цены задаются в конфигурации с указанием даты актуальности — система не выдаёт их за проверенные.

**FR-I11.** Кэширование: одинаковый запрос по неизменившимся данным не оплачивается дважды. Проход 2 при дозагрузке считает только новые блоки (FR-M13).

**FR-I12.** Перед отправкой материала во внешнюю модель система показывает **объём и состав отправляемого** и запрашивает подтверждение при превышении настраиваемого порога.

**FR-I13.** Недоступность провайдера — штатное состояние интерфейса, а не ошибка: система сообщает и продолжает работать в детерминированном режиме.

## 16. Устная речь

**FR-W1.** Устный ответ записывается в браузере или присылается голосовым сообщением в бот.

**FR-W2. Распознавание — внешний сервис (Groq Cloud, Whisper).** Транскрипт запрашивается с **пословными таймингами** (`timestamp_granularities: ["word"]`).

**FR-W3.** Облачное распознавание **вычищает слова-паразиты, запинки и фальстарты**. Это принято сознательно. Метрики по паразитам не реализуются и не имитируются: их отсутствие фиксируется явно, а не скрывается.

**FR-W4.** Метрики, доступные на очищенном транскрипте с таймингами: **темп речи, время до начала ответа, длительность и число пауз, доля молчания**.

**FR-W5. Проверка устного ответа — содержательная:** транскрипт сверяется с ключевыми пунктами темы тем же движком, что и текстовый ответ (§9).

**FR-W6.** Устный ответ и метрики речи — **два независимых модуля**. Замена провайдера распознавания на локальный verbatim-вариант (CrisperWhisper, §22) не требует переделки устного ответа.

**FR-W7.** Исходное аудио сохраняется вместе с попыткой. Политика хранения настраивается: по умолчанию аудио хранится ограниченный срок или до заданного объёма, транскрипт и метрики — бессрочно.

**FR-W8.** Две попытки одной темы можно сравнить рядом: транскрипты, метрики, подсветка различий.

**FR-W9.** При включении устного ответа система показывает, что аудио будет отправлено внешнему сервису (П7).

## 17. Статистика и отчёты

**FR-T1.** По проекту: карта покрытия (обе метрики, FR-D16), пройдено и подтверждено, прогноз готовности, распределение по статусам, время занятий, серия дней, топ просевших разделов.

**FR-T2.** По теме: история всех попыток с оценками, график интервалов, все привязанные фрагменты, все заметки, все карточки.

**FR-T3.** По устным ответам: динамика метрик речи и сравнение попыток (FR-W8).

**FR-T4.** Доля оспоренных оценок за период (FR-V5).

### Алгоритмы для блок-схем записки

**А1. Составление очереди дня.** Отбор просроченных, плановых и новых по проекту; приоритет по дедлайну и уровню цели; лимиты по числу и прогнозируемому времени; перемешивание по разделам; откат при переполнении; прощение долга.

**А2. Соотнесение материала и программы (проход 2).** Обход содержательных блоков батчами; классификация на три исхода; применение привязок при однозначном решении и отправка в очередь предложений при неоднозначном; чекпоинт по счётчику; подсчёт двух метрик покрытия.

**А4 (запасной).** Построение программы из материала (проход 1): map по главам, reduce со слиянием дублей.
**А5 (запасной).** Конвейер разбора материала с автодетекцией сканов и OCR.

## 22. Чего мы НЕ делаем

**Принципиально не входит в продукт:**

- **Не чат с документом.** Свободные вопросы разрешены, но это не главный сценарий и всегда со ссылками на материал.
- **Не универсальная база знаний.** Никакого извлечения «фактов» — только привязки со ссылкой на страницу.
- **Не платформа онлайн-курсов.** Нет авторов, учеников, продаж, проверки преподавателем.
- **Не соцсеть.** Нет лент, лайков, рейтингов, публичных профилей.
- **Не coding-агент.** Песочница выполняет демонстрации и код агента, а не пишет за пользователя решение.
- **Не мобильное приложение.** Мобильный сценарий закрывается ботом и адаптивным вебом.
- **Не многопользовательская система.** Одна установка — один пользователь.
- **Не система, объявляющая ответ верным без объяснения.** Любая оценка объяснима и оспорима.

**Отложено** (реализуется без переделки архитектуры):

| Что | Почему отложено |
|---|---|
| Интервью как ветвящийся сценарий | Форма с автозаполнением даёт почти всю пользу за долю работы |

| Веб-поиск как слой 3 каталога | Отдельная интеграция, пользы поверх слоя 4 почти нет |
| Автоматический поиск материалов в сети | Пользователь добавляет материалы сам |
| Обучаемая модель памяти | За семестр у одного пользователя не набрать выборки с длинными интервалами; вывод был бы недостоверным |
| Обучаемый переранжировщик привязок | Проход 2 не даёт баллов для ранжирования; ранжировать нечего |
| Распознавание рукописных формул | Единственная функция, обязательно требующая внешней модели; используется редко |
| Python-задачи с прогоном тестов | Остаётся SQL. Добавляется адаптером |

## 25. Обоснование ключевых решений

Методичка ТРПС требует прямо: обоснований вида «удобнее» и «целесообразнее» быть не должно — надо пояснить, **чем** удобнее и **почему** целесообразно. Ниже три решения, определяющие архитектуру, с основаниями.

### 25.1. Почему полный перебор блоков, а не поиск

**Основание структурное.** Поиск перебирает *запросы* и возвращает по каждому топ-k. Блок материала, не попавший ни в один топ, не просматривается вообще и молча исчезает. Полный перебор идёт по *блокам* и рассматривает каждый ровно один раз — потерять нечего по построению.

**Основание эмпирическое.** В работе [Recursive Language Models](https://arxiv.org/abs/2512.24601) (MIT CSAIL, 2026) сравниваются подходы к обработке длинного контекста на задачах разной сложности. На OOLONG — задаче, где ответ зависит почти от каждой строки входа, то есть структурно совпадающей с нашей задачей соотнесения, — агент с BM25-поиском набирает **38.0** против **44.0** у модели вообще без поиска и **56.0** у рекурсивного подхода. На OOLONG-Pairs (попарное сопоставление) — 24.7 против 58.0.

Вывод: на задачах, где нужен весь вход, поиск не просто уступает — он хуже отсутствия поиска.

### 25.2. Почему фиксированный проход, а не агент

Форма задач соотнесения и построения программы известна заранее, поэтому цикл пишется один раз инженером. Фиксированный проход выигрывает у агента по четырём осям, каждая из которых для нас обязательна:

| Свойство | Фиксированный проход | Агент |
|---|---|---|
| Повторный запуск на тех же данных | тот же результат | результат меняется |
| Чекпоинт (FR-M14) | счётчик обработанных единиц | естественного чекпоинта нет |
| Оценка стоимости до запуска (FR-M4) | точное число | в источнике разброс до ±$3.25 при среднем $1.10 |
| Блок-схема для записки | рисуется | код порождается в рантайме, схемы нет |

Агент оставлен ровно там, где форма задачи неизвестна и цикл не написать заранее, — на свободном вопросе (§6.6).

### 25.3. Почему SM-2, а не обучаемая модель памяти

Для честного сравнения обучаемой модели с SM-2 и FSRS нужна выборка повторений с интервалами в месяцы. За семестр у одного пользователя основная масса наблюдений придётся на интервалы 1–14 дней, правый хвост будет пуст, и сравнение по log-loss даст шум. Вывод на вырожденной выборке хуже отсутствия вывода, поэтому обучаемая модель отложена, а SM-2 реализуется полностью.

### Сценарии демонстрации на защите

1. **Вход A.** Методичка + файл ответов + список билетов → программа импортом → карта покрытия. Полностью офлайн.
2. **Вход B.** Одна методичка → проход 1 строит программу → проход 2 → экран «Неразобранное»: что в материале есть сверх программы.
3. **Вход C.** «Хочу разобраться в векторных БД» → программа из знаний модели с меткой «источника нет», покрытие 0% → добавление материалов → пробелы закрываются.
4. **Свободный вопрос агентом.** «Что есть в методичке про транзакции, чего нет в файле с теорией?»
5. **Без внешних моделей.** Тумблер выключен: программа по оглавлению, поиск, карточки, тесты, SM-2, план.
6. **Бот.** Напоминание → ответ голосом в Telegram → продолжение в вебе с того же места.
