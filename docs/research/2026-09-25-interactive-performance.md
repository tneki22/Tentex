# Отзывчивость Tentex: замеры и короткие правки

Дата: 25.09.2026. Среда: Windows, Docker Compose, SQLite на bind mount с хоста,
Chrome/Playwright через Vite. В рабочей базе: 44 материала, 100 291 фрагмент,
16 470 фрагментов поискового индекса, 1 228 записей вызовов ИИ, 17 уроков.
Активных фоновых задач при замерах не было. Числа ниже относятся к этой базе
и машине; под OCR, сборкой индекса или другой нагрузкой задержки могут вырасти.

## Что видно пользователю

Один проход Playwright по уже открытому приложению, от клика до появления
содержимого:

| Переход | До правок |
| --- | ---: |
| Проекты → Библиотека | 2,36 с |
| Проекты → Параметры, раздел ИИ | 2,90 с |
| Параметры ИИ → Поиск | 2,99 с |

Это одиночные наблюдения, а не стабильный p95. API измерялся отдельно по
четыре последовательных запроса; здесь приведён диапазон:

| API | Время | Размер | Вывод |
| --- | ---: | ---: | --- |
| Список Библиотеки | 1,19–1,32 с | 34 КБ | Задержка почти целиком на сервере, не в передаче |
| Параметры retrieval | 1,36–2,29 с | 9,7 КБ | Главный блокирующий запрос раздела «Поиск» |
| История ИИ | 1,32–2,07 с | 959 КБ | Блокировала показ всех параметров ИИ |
| Сами параметры ИИ | 0,11–0,14 с | 30 КБ | Готовы намного раньше истории |
| Проект «Сети 2» | 0,16–0,36 с | 674 КБ | Открытие проекта относительно быстрое |
| Обзор уроков проекта | 0,08–0,10 с | 3,4 КБ | Не главный тормоз редактора |
| Урок, 22 блока | 0,13–0,25 с | 11 КБ | Серверное чтение быстрое, но запрос повторялся |
| Эталонный ответ (2 примера) | 0,04–0,09 с | 2,8–4 КБ | Медленные открытия требуют замера конкретной страницы/файла |
| Страница материала, 1370 фрагментов | 0,14–0,19 с | 683 КБ | Большой JSON и много элементов для браузера |

PDF-страница файла ответов: первый запрос растра без кэша — 717 мс,
два следующих — 72 и 51 мс. Это совпадает с текущим механизмом:
первая страница рисуется в WebP и сохраняется; повтор берётся из файла и
браузерного кэша. Для длинного ответа с несколькими ещё не открытыми страницами
эта цена может повторяться.

Ручной разрез после фрагмента на копии базы (свободный проект, урок из
22 блоков) занял 200 мс в сервисе. Через HTTP на копии базы разрез по странице
занял 155 мс в свободном и 146 мс в учебниковом проекте; добавление семи страниц
учебника — 203 мс. Эти операции не объясняют многосекундную задержку одни:
ощущаемая пауза складывается из запроса, последующих чтений и отрисовки страниц.
На первом открытии редактора до правки браузер отправлял четыре GET одного
урока (часть отменялась), после правки — два. Это измерение сделано в Vite
development mode; оно не равно времени production-сборки.

## Небольшие правки в этом срезе

1. Подсчёт готовых материалов retrieval теперь идёт от материалов через
   `EXISTS`. На той же базе оба SQL-варианта дали 28 материалов; в контейнере
   старый запрос занял 1,94 с, новый — 0,19 с в одиночном прогоне. Это влияет
   на каждый GET параметров поиска и на настройку поиска в Библиотеке.
2. Параметры ИИ отображаются после получения настроек; история загружается
   независимо, с собственным состоянием загрузки/ошибки. Ожидаемый выигрыш
   на входе в раздел — около 1–2 с при прежнем объёме истории.
3. Библиотека держит последний список в памяти вкладки. При возврате он
   показывается сразу; в течение 15 с повторный тяжёлый запрос пропускается,
   позже список обновляется без полноэкранной заглушки. Создание, удаление
   и правка метаданных в самой Библиотеке сбрасывают снимок.
4. При открытии редактора устранены лишние эффекты обновления и одновременно
   запрошенный урок читается совместно. Число GET в проверенном переходе
   снизилось с четырёх до двух. После ручного действия убран отдельный
   немедленный GET; обновление через родительский экран осталось. Дополнительный
   эффект на время редактирования пока оценивается в 0,1–0,3 с, но не измерен
   браузерным действием.

Контрольный проход после правок на отдельном фронтенде и копии базы:
Библиотека холодно — 1,93 с, возврат в той же вкладке — 0,74–1,25 с
в четырёх повторах, Параметры ИИ — 0,75 с, Параметры → Поиск — 0,33 с.
Часть разброса библиотеки связана с отрисовкой списка и другими запросами.
Чистый GET retrieval settings на копии базы при запуске на хосте после
первого прогрева занял 10–11 мс (первый — 115 мс). SQL в контейнере
на Windows bind mount: 1,94 с до замены и 0,19 с после замены.

После переноса правок в основной Docker и перезапуска контейнеров один
контрольный проход дал: холодный вход в Библиотеку — 3,14 с, повторный вход
через Проекты — 0,49 с, показ раздела ИИ — 0,77 с, переход ИИ → Поиск —
1,10 с. GET retrieval settings ответил за 0,57 с. Это одиночные замеры;
холодный вход в Библиотеку остаётся основной нерешённой задержкой.

## Следующие варианты

| Приоритет | Работа | Ожидаемый эффект | Объём/условие |
| --- | --- | --- | --- |
| Высокий | Убрать полный пересчёт агрегатов Библиотеки при каждом холодном входе: хранить сводку на материале или обновлять её после обработки | Холодный вход может сократиться примерно на 0,5–1 с; текущий подсчёт фрагментов отдельно занимал 1,5–1,6 с внутри контейнера | Средняя правка, нужны инвалидация при новой ревизии и тесты |
| Высокий | Загружать историю ИИ только при открытии «Истории», с серверной пагинацией | Убрать фоновую передачу почти 1 МБ и обработку 1000 записей при обычном входе в Параметры | Средняя правка контракта и UI; обзорному счётчику нужен лёгкий агрегат |
| Высокий | Разобрать waterfall одного медленного разреза и добавления источника на реальном уроке; использовать уже возвращённый изменённый урок, сократить обновления обзора и правой панели | Вероятно ещё 0,2–0,7 с на действие; подтвердить серией замеров в браузере | Небольшая/средняя правка состояния редактора |
| Средний | Ограничить одновременную отрисовку длинных страниц и растров в уроке/просмотрщике | Ускорение страниц с сотнями фрагментов и несколькими холодными PDF-листами; пока без честной численной оценки | Нужен браузерный профиль конкретного медленного документа |
| Средний | Разбить большой стартовый JS по маршрутам | Меньше работы браузера при первом открытии; текущий основной production chunk — 1,65 МБ, gzip 459 КБ | Средняя правка сборки и проверки переходов |
| Отдельный эксперимент | Ограничить ресурсы worker-контейнера или число одновременных тяжёлых задач, сравнить p95 API/кликов под OCR и индексированием | Сохранить отклик API под нагрузкой ценой более долгого фона | Без активной задачи в этой сессии эффект не измерен; сначала контрольный прогон |

Фоновый worker уже отделён от API процессом, но использует тот же SQLite-файл
и тот же диск. Особенно на Windows bind mount конкуренция за ввод-вывод заметна
даже у коротких SQL-запросов. Менять общие лимиты без пары замеров
«в простое / под задачей» преждевременно.

## Продолжение: разбиение по маршрутам и дерево Уроков (25.09.2026, вечер)

Второй срез той же сессии — холодное открытие рабочей области, вкладок и
экранов левой панели в режиме учебника, плюс поздняя сводка на карточках
«Проектов». Изолированный `vite` на отдельном порту, копия базы не менялась.

**Сделано:**

1. Каждый экран `SCREEN_VIEWS` и вкладки рабочей области (чат, урок, история
   урока, источник учебника, панель материала Уроков) переведены на
   `React.lazy` + `Suspense`; барные импорты из `components/domain` заменены
   на прямые файловые, иначе весь домен подтягивался в общий чанк и код-сплит
   не работал. Production build: главный чанк упал с одного бандла на набор
   чанков по экрану (`Projects` — 12 КБ, `Lessons` — 42 КБ, `ProjectWorkspace`
   — 72 КБ и т.д.; общий `index` — 285 КБ вместо прежнего профиля с одним
   большим `dist-*` под все экраны сразу).
2. `StrictMode` снят в `main.tsx`. В dev-режиме (а `docker compose` у web
   именно dev-сервер Vite на 5173, не prod-сборка) двойной вызов эффектов
   удваивал сетевые запросы и рендер на каждом холодном переходе; в проде
   разницы нет, эффект чисто на реальный контур разработки.
3. «Проекты»: список и сводка (`listProjects` + `listProjectStats`) теперь
   грузятся одним `Promise.all` вместо сводки вдогонку — карточка сразу
   приходит с числом источников и страниц, а не сначала пустая с заглушкой.
4. Найдена и устранена настоящая причина медленных «Уроков»: у крупного
   учебника (в проверенном проекте — 669 узлов программы) дерево рендерится
   не виртуализированным и не скрытым по умолчанию — 540+ строк Уроков с
   Radix `Checkbox`/`Tooltip` каждая. Раньше это дерево рендерилось в том же
   синхронном проходе, что и стейт, отпирающий загрузку обзора уроков
   (`useLessonsOverview`), поэтому сам GET `/lessons/overview` не уходил в
   сеть, пока не отрисуется всё дерево. Замер на проекте «Сети 2» (669
   узлов): GET проекта завершался в 1011 мс, GET обзора уроков не начинался
   до 3676 мс — 2,66 с простоя. После `useDeferredValue` на узлах дерева
   (`frontend/src/screens/lessons/Lessons.tsx`) GET обзора уходит в сеть
   через 39 мс после GET проекта; тяжёлый рендер дерева отложен и больше не
   блокирует загрузку данных. UX (какие разделы раскрыты) не менялся —
   правка только меняет порядок «сеть vs рендер».

**Контрольные замеры после обеих правок** (тот же стенд, изолированный порт):

| Переход | Итог |
| --- | ---: |
| GET `/api/projects/{id}` → GET `/api/projects/{id}/lessons/overview` (до) | 2,66 с простоя между запросами |
| То же после `useDeferredValue` | 39 мс |
| «Проекты»: карточки с сводкой источников | сразу, без пустой паузы |
| Production build: суммарные чанки экрана | код-сплит подтверждён по факту (`build-performance` лог сборки) |

**Что осталось не тронутым:** само дерево из 540+ строк всё ещё рендерится
целиком и без виртуализации — `useDeferredValue` не уменьшает эту работу, а
только не даёт ей блокировать загрузку данных. Если открытие дерева само по
себе (не загрузка данных) останется заметным на очень крупных учебниках,
следующий шаг — виртуализация списка или сворачивание разделов по умолчанию;
последнее меняет UX и требует отдельного решения, не входит в этот срез.

## Продолжение: ответы, поиск и Библиотека (26.09.2026)

Стенд: отдельный worktree `codex/workspace-response-speed`, Vite на 5175,
отдельный API на 8001 с теми же реальными проектами и материалами. Сравнение
API до правки — основной контейнер на 8000. Замеры выполнялись в браузере и
сериями HTTP-запросов; это локальный Windows Docker bind mount, поэтому
холодные результаты могут колебаться при работе диска.

На экзаменационном проекте «НБД» смена вопроса с вкладкой «Ответ» запускала
скрытый `GET /search?strategy=hybrid`. Он шёл около 3 с, а синхронный FTS
в `async` обработчике блокировал event loop API: параллельные ответы ждали
2,2–3,1 с. До правки пять смен вопросов в браузере заняли 2434, 382, 3056,
6776, 3342 мс. Теперь автопоиск идёт только при открытой вкладке «Источник»;
привязки вопроса по-прежнему читаются сразу. Шесть смен после правки:
562, 543, 312, 475, 478, 546 мс; открытие чата после смены вопроса:
562, 358, 464, 448, 339 мс.

Поиск остаётся тяжёлым, поэтому его обработчик выполняется в пуле потоков.
При трёх параллельных прогонах прежний API отвечал на запрос ответа во время
поиска за 2222, 2514, 3058 мс; новый — за 164, 48, 29 мс. Сам поиск на
новом API занимал 3,9–4,9 с. В браузере смена вопроса при работающем поиске
на вкладке «Источник» показала ответ через 234 мс. Долгий поиск кандидатов
остаётся отдельным узким местом открытой вкладки «Источник», хотя содержимое
привязок показывается независимо от него.

Холодный `GET /api/materials` до правки занимал 1,4–3,9 с на реальной базе:
список при каждом входе считал все фрагменты активных ревизий. Миграция `0063`
сохраняет счётчики активных ревизий в `MaterialRevision.summary`; каждая новая
ревизия записывает их при создании. На том же наборе из 44 материалов и
59 902 фрагментов новый API ответил в пяти повторах за 292, 246, 202, 232,
219 мс. Сумма счётчиков сверена с прямым SQL; upgrade → downgrade → upgrade
проверен на копии базы. Для старой ревизии без сводки остаётся подсчёт.

История ИИ раньше загружала почти 1 МБ и до 1000 записей фоном при открытии
Параметров. Теперь запрос идёт только при открытии «Использования», по 20
строк; сервер возвращает число и суммы по всем отфильтрованным записям.
Обзор берёт сегодняшний `run_count` из короткого `GET /settings/ai`.
В браузере прямое открытие обзора заняло 1,35 с без запросов журнала,
«Использования» — 1,28 с с одной страницей журнала. Время включает начальную
загрузку приложения; повторные переходы и API обычно быстрее.

Один проход по левой панели экзаменационного проекта после правки:
«Материалы» 338 мс, «Программа» 661 мс, «Ответы» 974 мс,
«План» 831 мс, «Карточки» 107 мс, «Настройки» 288 мс.
На крупном учебнике «Сети 2» (669 узлов) холодная рабочая область заняла
1,10 с, «Материалы» 398 мс, первый вход в «Программу» 1,67 с,
«Уроки» 302 мс, «Настройки» 235 мс. Пять повторных входов в «Программу»:
854, 889, 1062, 859, 337 мс. Значит, цель менее секунды пока выполнена
для ответов, чата и большинства переходов, но не гарантирована для первого
открытия большой программы и холодного старта приложения.

После завершения полного pytest повторён вход в «Программу» учебника после
трёх перезагрузок его рабочей области: 3908, 1127, 1497 мс. В последнем
проходе GET проекта для «Программы» занял 861 мс, затем понадобилась
отрисовка дерева. Этот экран остаётся выше целевой секунды; текущая правка
не скрывает его задержку.

## Третий срез: SQLite на bind mount, поиск, дерево Уроков, фон (26.09.2026)

Ветка `codex/perf-balance` (включает `codex/workspace-response-speed`). Стенды
на реальной базе: «до» — код `f4f5156` (правки второго среза плюс исправление
миграций), «после» — ветка; web — Vite dev в Docker, как у пользователя, API —
отдельные контейнеры на той же `data/`. Замеры «до» и «после» сняты в простое
(индексация закончилась), по три прогона каждого экрана: холодный — новый
контекст браузера, повторный — вход тем же контекстом. «Полезное» — момент,
когда на экране нет `LoadingState`/скелетонов и есть текст. Серверные цифры —
пять последовательных HTTP-запросов, медиана.

### Что подтвердилось

1. **Чтение базы с Windows bind mount — главный общий тормоз.** Копия базы
   590 МБ через Online Backup API читалась 177 с (~3,3 МБ/с при случайном
   чтении). Тот же запрос перевода фрагментов в куски на копии внутри
   контейнера — 65 мс, на bind mount — 5–11 с. `NullPool` давал каждому
   запросу новое соединение с пустым кэшем страниц: повтор одного запроса на
   новом соединении — 97–167 мс, на том же — 2–3 мс.
2. **Поиск кандидатов в проекте** (вкладка «Источник», поиск в «Уроках»):
   `_chunk_lookup` делал `json_each(fragment_ids)` по всем кускам активного
   индекса и ради этого читал их длинный текст и вектор; лексический поиск
   тянул полные строки страниц и материала — у учебника в каждой из сотен
   строк разбиралось оглавление на ~120 КБ JSON; `visual_page_locators`
   делал `DISTINCT` по той же строке материала.
3. **Правая панель «Уроков»** запускала гибридный поиск при каждой смене
   темы, хотя открывается на «Предложено»: на стенде «до» этот скрытый запрос
   шёл 17,9 с (медиана шести входов) и держал поток API.
4. **Дерево «Уроков»** (учебник «Сети 2», 540 строк тем): рендер — одна
   длинная задача 2,08–2,20 с в dev-режиме, из них ~1 с — Radix `Checkbox`,
   ~0,65 с — Radix `Tooltip` в каждой строке. Выбор темы перерисовывал всё
   дерево: 0,52–0,65 с блокировки на клик.
5. **Простаивающий воркер** брал SQLite-writer на каждой попытке захвата:
   три полосы раз в 0,75 с, медиана 32 мс (максимум 89 мс) под writer, то
   есть около 13% времени запись API могла ждать его.
6. **Фоновая индексация** (retrieval_index, e5-base, 37 материалов):
   эмбеддинг одного запроса в простое — 31–33 мс, под индексацией — 316–988 мс;
   модельный сервис занимал ~10 ядер. Под той же нагрузкой экзаменационная

### Что изменено

- Миграция счётчиков ревизий перенумерована в `0064`; новая `0065` —
  покрывающий индекс `(index_id, material_id, revision, sort_order,
  fragment_ids, id)`. `_chunk_lookup` ограничен материалами выдачи и
  упорядочивает куски в Python; проверка «материал в индексе» — `EXISTS`.
  Выдача поиска на четырёх запросах в двух проектах совпала со старой по

- Лексический поиск берёт от страницы только номер и не читает `outline` и

- API держит пул SQLite-соединений (`TENTEX_SQLITE_POOL_SIZE=8` в compose,
  LIFO, 64 МБ кэша страниц на соединение). Воркер и скрипты остаются на
  коротких соединениях: восстановление копии подменяет файл базы, а пул API
  оно само закрывает. SQLite сбрасывает кэш соединения при любой чужой записи
  в WAL, поэтому устаревших данных нет; в простое за 60 с посторонних записей
  не было.
- Воркер: чтение «есть ли что брать» до резервирования writer.
- «Уроки»: строки дерева мемоизированы, обработчики постоянны;

- История ИИ загружается, когда её панель оказалась в окне.

## Четвёртый срез: лишние записи при открытии и пул поиска (26.09.2026, вечер)

После третьего среза экзаменационная рабочая область держалась на 2,1–3,6 с.
Причина была не в самом поиске: временный замер фаз внутри обработчика показал,
что поиск в браузере шёл 1,4–1,6 с (лексическая часть 310 мс, гибрид 1,2 с),
а тот же запрос через curl — 0,2 с (46 и 150 мс). Первый визит после
перезапуска был быстрым, следующие — медленными.

**Причина:** чат рабочей области через 0,8 с после открытия отправлял
`PUT …/draft` с только что загруженным черновиком, а урок — `POST …/progress`
с уже сохранённым блоком. Сервер писал их, поднимал `updated_at` сессии и
резервировал writer. Любая запись в WAL сбрасывает кэш страниц у всех
соединений API, и поиск следующего открытия читал базу с bind mount.
Побочный дефект: простое открытие чата поднимало его в списке «недавних».

**Исправлено:**

- Черновик чата (экзамен, проектные чаты, поиск Библиотеки) и позиция чтения
  урока без изменений не пишутся и не резервируют writer. Изменённый черновик
  сохраняется как прежде (проверено: запись есть, текст сохранён, у
  неизменённого `updated_at` не сдвинулся). Во время прогона всех экранов в
  базу больше не пишет ни одно открытие.
- Поисковые GET (`/projects/{id}/search`, `/retrieval/search`,
  `/library/search`, `/materials/{id}/search`) берут соединения из
  отдельного пула на 2 соединения. Пачка из 19 GET рабочей области раньше
  разбирала общий пул, и поиск попадал на соединение с холодным кэшем:
  поиск параллельно с четырьмя запросами экрана на свежем API — 3,1 и 1,5 с,
  теперь 0,5 и 0,27 с. Восстановление копии закрывает оба пула.

### Что осталось

- **Холодное чтение с bind mount.** Первый запрос после перезапуска API или
  после записи фоновой задачи идёт с диска: первый поиск на новом соединении
  2–3 с, поиск по теме учебника — 5–6 с. Первый вход в рабочую область
  экзамена после перезапуска API — 3,6 с. Радикальное решение — держать
  `tentex.sqlite` в Docker-томе, а не в `./data` на Windows; нужно решение
  пользователя.
- **Один процесс API.** Весь Python API идёт одним процессом uvicorn
  (`--reload`), CPU-работа параллельных запросов делит один GIL: тяжёлый экран
  рядом с поиском растягивает оба (прямой поиск 0,3 → 1,7 с на фоне
  «Покрытия» учебника). Несколько процессов требуют вынести из процесса
  состояние восстановления копии, режима обслуживания и потоковых ответов —
  это не быстрая правка.
- **Эмбеддинг запроса под индексацией** — 0,3–1 с вместо 30 мс: пакет
  индексации и запрос делят потоки torch одного процесса. Приоритет
  интерактивных запросов в `retrieval-model` не сделан: цифры укладываются в
  цель, а мелкие пакеты замедлят саму индексацию.
- «Карточки» и «План» грузят полную программу ради названия и модулей
  (у учебника 690 КБ); сервер отдаёт её за 42 мс, выигрыш мал.
- Под записью фоновой задачи кэши соединений API сбрасываются, так что
  под нагрузкой ответы ближе к холодным.
