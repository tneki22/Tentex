# Промпт агенту: подготовительная вертикаль перед этапом 3

Ты работаешь в репозитории Tentex. Нужно сначала самостоятельно продумать, затем в этой же задаче реализовать подготовительную вертикаль перед этапом 3: **настоящий экран «Настройки проекта» и минимальный общий фундамент, который этап 3 затем переиспользует**.

Не начинай с кода. Сначала прочитай полностью `AGENTS.md`, релевантные части `PLAN.md`, `REQUIREMENTS.md` (§3.1–3.3, §5.1, §13, §18, §21–22), `SCREENS.md`, `DESIGN.md`, `docs/architecture/stage-2-core.md`, затем текущие модели/API проекта и экраны `Program`/`ProjectWorkspace`. Для поиска кода сначала используй codebase-memory-mcp; если индекс отсутствует — проиндексируй репозиторий. Учитывай грязный worktree и не меняй чужие несвязанные правки.

Используй `skill-router`, затем минимально необходимые `tentex-screens`, `tentex-ui-kit`, `writing-plans`/`executing-plans` и `verification-before-completion`. Ponytail не применяй к проектированию экрана: это прямо запрещено `AGENTS.md`. Не создавай новый визуальный язык и сначала проверь `/ui-kit` и существующие примитивы.

## Результат задачи

После выполнения по настоящему маршруту `/projects/:projectId/settings` можно открыть активный проект из SQLite, изменить поддерживаемые ядром настройки, сохранить их одной транзакцией, перезагрузить страницу и увидеть те же значения. Экран зарегистрирован в `views.ts`, доступен из проектной навигации и имеет честные loading/error/404/readonly/saving/saved/validation/unsaved состояния.

Вместе с экраном сделай только три логичных предварительных основания для этапа 3:

1. Один небольшой клиент `frontend/src/api/projects.ts` над нативным `fetch`: общий `request<T>()`, `getProject(projectId)` и `updateProjectSettings(projectId, command)`. Не добавляй React Query, axios, repository-классы, глобальный store или генератор клиентов.
2. Выровняй уже существующие контракты, которые экран обязан использовать:
   - `Project.color` во всех слоях — `int | null` с допустимым диапазоном `1..8`; добавь узкую Alembic-миграцию с безопасным значением `1` для прежних неизвестных строк;
   - `GoalLevelValue` — те же значения, что `TargetOutcome`: `awareness | understanding | application | mastery`, без второго словаря `know | understand | apply | master`.
3. Подключи ссылку «Настройки» в существующих проектных навигациях `Program` и `ProjectWorkspace`. Не оживляй остальные mock-данные этих экранов — это этап 3.

Не добавляй второй экран ради объёма. Глобальные `/setup` («Параметры установки») уже свёрстаны и относятся к моделям, боту, резервным копиям и хранилищу. Только проверь и зафиксируй в документации, что это другая область; не делай её настоящей раньше соответствующих подсистем.

## Что именно редактируется на экране

### Проект

- название — обязательно после `trim`;
- описание;
- иконка из существующего `PROJECT_ICONS`;
- цвет из восьми существующих `--project-color-*`;
- необязательный дедлайн.

`template_key`, `workspace_variant`, `status` и `sort_order` экран не меняет. Вариант рабочего пространства нельзя переключать настройкой: разные подходы — разные проекты (FR-P8).

### Паспорт цели

Используй существующий `GoalPassport`, не создавай новую сущность и не складывай паспорт в JSON:

- `subject`, `purpose`, `scope`;
- `starting_level`, `current_knowledge`;
- `target_outcome`;
- `goal`, `success_criterion`, `important`, `excluded`;
- `study_format`;
- `minutes_per_day`, `days_per_week`, `session_minutes`;
- экзаменационные `exam_format`, `expected_item_count`, `instructor_requirements` показывай только для `workspace_variant=exam`.

После изменения паспорта покажи спокойное пояснение: программа автоматически не перестраивается. Не добавляй кнопку модельной пересборки до этапа 7.

### Модули

Редактируй только существующие `ModuleKey`: `plan`, `lessons`, `cards`, `repetitions`, `oral_answers`, `sql`. Подписи и пояснения русские. На сохранении убери дубли и нормализуй порядок по порядку enum. Не создавай настройки каждого модуля «на будущее».

### Поздние разделы

Модели и лимиты проекта, напоминания, пользовательский шаблон, экспорт и резервные копии сейчас не имеют полного серверного контура. Не имитируй их переключателями и успешными сообщениями. Покажи один компактный блок «Появятся позже» с точными этапами/зависимостями либо не показывай его, если после проверки `SCREENS.md` это читается лучше.

## Серверный контракт

Добавь один маршрут:

`PUT /api/projects/{project_id}/settings`

Команда содержит только:

```json
{
  "project": {
    "name": "Базы данных — экзамен",
    "description": "Подготовка к зимней сессии",
    "icon": "database",
    "color": 3,
    "deadline": "2026-12-18",
    "enabled_modules": ["plan", "cards", "repetitions", "oral_answers"]
  },
  "goal_passport": {
    "subject": "Базы данных",
    "purpose": "exam",
    "scope": "whole",
    "starting_level": "familiar",
    "current_knowledge": "Знаю SQL, путаюсь в нормальных формах",
    "target_outcome": "application",
    "goal": "Уверенно ответить на вопросы и решить задачи",
    "success_criterion": "Не менее 80% пробного билета без подсказок",
    "important": "Транзакции, индексы, нормализация",
    "excluded": "Администрирование СУБД",
    "study_format": "theory_and_practice",
    "minutes_per_day": 45,
    "days_per_week": 5,
    "session_minutes": 45,
    "exam_format": "tickets",
    "expected_item_count": 30,
    "instructor_requirements": "Показывать ход решения"
  }
}
```

Ответ — актуальный `ProjectDetail`. Сохранение Project и GoalPassport выполняется в одной транзакции. Разрешено менять только `active` проект; `draft` продолжает изменяться через ревизионный API мастера, `archived/completed` экран показывает без редактирования. Не добавляй отдельный запрос на каждый Switch и не вводи optimistic update: форма сохраняется одной кнопкой, успешный серверный ответ становится новым исходным состоянием.

Ошибки границы: 404 для отсутствующего/draft маршрута; 409 для архивного или завершённого проекта; 422 для неверных enum, пустого имени, цвета вне `1..8` и неверных числовых ограничений паспорта. Не добавляй revision к Project только ради этой локальной однопользовательской формы.

## UX и доступность

- `PageHead`, `Card`, `Field`, `Switch`, `RadioCards`, `Button`, `LoadingState`, `ErrorState`, `ProjectChip` и остальные подходящие элементы переиспользуй из UI-кита.
- Для иконки/цвета используй доступную `RadioGroup`/`RadioCards` семантику либо нативные radio; выбор должен работать клавиатурой и иметь видимый focus.
- Кнопка сохранения disabled, пока форма не изменена, невалидна или запрос идёт.
- При уходе со страницы с изменениями используй нативный `beforeunload`; не строй собственный роутер-блокер, если установленный router не даёт готового стабильного API.
- Серверную ошибку сохранения покажи рядом с действиями формы, введённые значения не стирай.
- Не вводи toast: по правилам Tentex его сознательно нет. Используй короткий inline-статус «Сохранено».
- На узком окне форма складывается в одну колонку; отдельный мобильный режим не нужен.

## Порядок работы

1. Создай короткий исполняемый план в `docs/superpowers/plans/2026-08-06-pre-stage-3-project-settings.md` с точными файлами и проверками.
2. Реализуй backend-контракт, миграцию и расширь `backend/scripts/check_stage2.py` одним сценарием: сохранение всех групп полей, restart, повторный GET, сохранение прежних `status/template/variant/sort_order`, 409 для архивного проекта и `PRAGMA foreign_key_check`.
3. Реализуй API-клиент и экран, зарегистрируй route и проектные ссылки. Не переносись на живые данные в Projects/Program/Workspace целиком.
4. Перезапусти `web`, проверь прямой маршрут настоящего active project в браузере, включая клавиатуру, тёмную/светлую тему, 404 и несохранённые изменения.
5. Только после свежих проверок обнови документацию фактами реализации:
   - `SCREENS.md` — полноценные пять пунктов экрана и чёткое отличие от `/setup`;
   - `PLAN.md` — отдельная завершённая подготовительная вертикаль перед этапом 3; из этапа 3 убрать реализацию Настроек и оставить только их переиспользование;
   - `REQUIREMENTS.md` — не переписывать весь документ, только устранить реальное противоречие между проектными Настройками и Параметрами установки, если оно осталось;
   - `docs/architecture/stage-2-core.md` — зафиксировать фактический PUT-контракт, миграцию цвета и проверку после restart;
   - `frontend/src/app/screens.ts` — обновить summary/depth экрана, если принятый словарь глубины это допускает.

## Проверка и ограничения

Обязательно выполни свежими запусками:

```bash
python backend/scripts/check_stage2.py
cd backend && python -m ruff check .
npm run typecheck
npm run build
docker compose restart web
```

После перезапуска проверь экран в браузере. Не утверждай «готово» без фактических результатов. Не создавай коммит и не форматируй несвязанные файлы. Не добавляй upload/OCR, импорт программы, архивирование, undo, новые сущности, модели, бот, напоминания, экспорт, пользовательские шаблоны или данные будущих этапов.

В финале дай: что реализовано; какие документы обновлены после реализации; результаты команд; какие поздние настройки сознательно не имитировались.
