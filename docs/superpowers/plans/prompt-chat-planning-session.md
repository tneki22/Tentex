## Задача

Составить план реализации вкладки «Чат» экзаменационной Рабочей области в **двух отдельных
итерациях**, которые будут выполняться как две раздельные агентские сессии. Не пиши код —
только план. Используй скилл `writing-plans`.

Возьми `skill-router` в начале, чтобы не тащить лишние скиллы.

## Граница между итерациями — реши сама, но по этим ограничителям

**Итерация 1 (Срез C) должна давать вот этот результат** (это цитата из «Готово, когда»
в `PLAN.md`, не придумывай другую планку):

> в чате можно ответить на вопрос билета и получить разбор с цитатами, при выключенных
> моделях работают детерминированные ступени, а история попыток по вопросу видна вне чата.

Ориентировочный (не окончательный — уточни при планировании) состав итерации 1.
Внутри самой итерации 1 разбей работу на два последовательных под-этапа —
сначала механика чата, потом проверка поверх неё — так план проще читать и
проще остановиться после первого под-этапа, если не хватит времени на сессию:

**1a. Базовая механика чата** (без проверки ответа):
- сущности `ChatSession`, `ChatMessage` (с `payload_kind`/`payload`) — миграция;
- один навык — форма ответа (`payload_kind: answer_form`), отправка `Сдать ответ`,
  сообщение сохраняется и видно в ленте;
- лента сообщений с потоковым Markdown достаточно простая, без палитры `/`, без
  персоны/строгости, без диктовки, без билета, без доспроса, без возражения.

**1b. Проверка ответа поверх готовой механики**:
- сущности `Attempt`, `Grade` из «Ядро занятий» `PLAN.md`;
- движок проверки лесенкой `FR-V1`/`FR-V2`: точное совпадение → ключевые термины →
  ИИ-судья (через существующий `ModelGateway`) → самооценка при выключенных моделях;
- вердикт (`payload_kind: verdict`) с тремя полосами «Засчитано/Упущено/Неверно» и
  привязкой цитат к тексту ответа (`FR-V3`);
- история попыток по вопросу видна **вне чата** — где именно (панель вопроса, «Вопросы
  экзамена» или отдельная вкладка) реши в плане, это открытый вопрос.

Опиши оба под-этапа как отдельные проверяемые шаги внутри одного раздела плана
«Итерация 1», каждый со своим «готово, когда». Это не третья сессия — оба
под-этапа всё ещё исполняются вместе, одной сессией написания кода, если хватит
времени; разбивка нужна только чтобы было где остановиться и показать
промежуточный результат.

**Итерация 2 (Срез D)** — по `PLAN.md`: персона и строгость, режим билета (`/билет`,
несколько вопросов подряд со сводкой), доспрос по упущенному пункту с «Итогом ветки»,
задачи внутри чата (`/задание`), возражение «Не согласен». Из целевого `SCREENS.md`
согласуй туда же: полную палитру навыков (`+`/`/`), диктовку, чипы контекста с
раскрытием точного состава, сокращённую память раздела, контрол экзаменатора в шапке,
переключатель модели `Auto`/явная.

Если по ходу чтения найдёшь кусок функциональности, который логически не влезает ни
туда, ни туда — не запихивай силой, вынеси отдельным пунктом «не входит ни в одну
итерацию, отдельное решение» и объясни почему.

## Формат плана

Для каждой итерации отдельно:

- сущности и миграция (имена полей, не абстрактные типы);
- эндпоинты бэкенда (метод, путь, request/response по образцу существующих в
  `backend/app/projects/router.py` или `backend/app/bindings/router.py`);
- фронтенд-компоненты и где именно в `ProjectWorkspace.tsx` они встают;
- явный список того, что НЕ входит в эту итерацию (чтобы вторая сессия не спорила
  заново с первой);
- критерий «готово, когда» — конкретный сценарий ручной проверки в браузере, не общие
  слова;
- как итерация проверяется: `npm run typecheck && npm run build`, `docker compose
  restart web`, ручной проход в `preview_start`. Тестового фреймворка на бэке нет —
  если в плане появляется новая логика уровня движка проверки лесенкой (нетривиальная
  и легко ломаемая), заведи для неё pytest-тест по аналогии с
  `backend/tests/test_ai_gateway.py`, а не сплошное покрытие.

## Ограничители, чтобы план не разросся

- Один человек, 10–15 часов в неделю на весь проект — не только на чат. Планируй так,
  чтобы итерация 1 была реалистичным объёмом одной агентской сессии с проверкой, а не
  многодневной эпопеей.
- Готовое вместо своего: движок лесенки проверки — детерминированная логика + вызов
  существующего `ModelGateway`, не пиши собственный оценщик с нуля там, где это уже
  решено на уровне архитектуры шлюза.
- Не проектируй `Activity` — по `PLAN.md` («Ядро занятий: что берём сейчас») она прямо
  исключена как преждевременная абстракция. `Attempt.program_node_id` указывает на узел
  программы напрямую.
- Не трогай учебниковый чат — обе итерации только для `exam`-конфигурации проекта.
