## Шаг 3. Правки самого прохода (без новых экранов)

Цель — меньше «Ждут уточнения» и меньше мусора в опорах. Модельные запросы меняются только
в пункте 3.5. Каждый пункт — отдельный коммит с регрессионным тестом в
`backend/tests/test_coverage.py` (там уже есть фикстуры снимка и FakeTransport).

### 3.1. Описанная картинка — текст

Сейчас `research.py:117` пишет `"inspected": []`, и `validation._unavailable_visual`
считает **любой** фрагмент `image` непросмотренным: связь снимается, часть блока
становится `unresolved: visual_unavailable`. На «Матлогике» это 34+ из 53 «Ждут уточнения».

Сделать: изображение с проверяемым текстом — обычный текстовый фрагмент. Признак брать
из `MaterialFragment.visual` через `app/materials/image_meta.meta_from_json` (описание
модели, `text_only`, ручная правка), а не по префиксу текста. Удобнее всего — в
`snapshots._unit` отдавать такой фрагмент с `kind="paragraph"` (или добавить в `Unit`
флаг `described`), тогда `_unavailable_visual` и `_supports_target` не меняются.
Картинка без описания и заглушка `image_meta.is_placeholder` остаются
`visual_unavailable`.

Тест: блок из абзаца, описанной картинки и картинки-заглушки → связь описанной картинки
публикуется, заглушка даёт `visual_unavailable`, исход блока `mixed_resolved`/`linked`.

### 3.2. Номер страницы не идёт в пакет как содержание

Разбор PDF делает «27» отдельным фрагментом, модель честно размечает его. Правило то же,
что в `passages.PAGE_NUMBER` (`^\s*\d{1,4}\s*$`): вынести его в одно место
(например, `app/coverage/validation.py` или общий модуль разбора) и
- в `packets.build_packet_specs` не отправлять такие фрагменты модели, а в
  `validation` считать их частью `service` без вызова;
- в `lessons/editing._bind_fragments` не создавать для них привязки.

Тест: блок «27» + абзац → в пакете один фрагмент, «27» — `service`, у урока с диапазоном
через номер страницы нет привязки к «27».

### 3.3. Диапазон с частями не роняет решение

`protocol.py:191`: диапазон `B3…B7` с `parts` получает `error: range_with_parts`, и
служебный хвост Фофанова (литература, выходные данные — 5 блоков) висит в «Ждут
уточнения». Сделать: разложить `parts` по блокам диапазона (фрагмент принадлежит ровно
одному блоку из `task_input`) и развернуть каждый блок со своими частями; ошибка остаётся,
только если часть ссылается на фрагмент вне диапазона.

Тест: диапазон из трёх блоков с частями `service` → три блока `service`, без `invalid_decision`.

### 3.4. Упоминания и уроковые привязки — не опоры

Сейчас любая активная привязка темы идёт как сигнал:
- `lessons/candidates._bindings` (ИИ-урок, вес 0,7) — включая `mention`, `reference` и
  привязки, созданные самим уроком (`mechanism=lesson`, `semantic_kind is None`). Урок
  кормит сам себя, а оглавление тянет «Содержание»;
- `retrieval/search.py:622` (`RetrievalScope.LINKED_TOPIC`, чат «Связано с темой») берёт
  `block_id` всех не снятых привязок — упоминание тянет в контекст весь блок оглавления.

Сделать в обоих местах одно условие: `semantic_kind == "content"` **или** ручная привязка
не из урока (`status == MANUAL and mechanism != LESSON`); скрытые решением — исключить так
же, как `interaction` (`hidden`). Условие — одна функция рядом с `ACTIVE_STATUSES`, а не
две копии.

Тест: у темы content, mention и lesson-привязка → в кандидатах и в `ScopeFilter.block_ids`
только блок content.

### 3.5. Широкая родительская тема — не корзина

У «Деревья и структуры данных» ≈70% содержательных отрезков Фофанова не про деревья
(стек, очередь, дек, B-деревья, хеширование), исход `outside_program` не использован ни
разу. Сделать правило в промпте первичного обзора (`research.py`, текст правил — там же,
где «список, который объясняет»): блок со своим заголовком и своим предметом, которому
подходит только широкая родительская тема, — `outside_program` с названием предлагаемой
темы в `reason`. Проверка — как у правила про списки
(`test_rules_separate_a_plan_from_a_list_that_explains`): тест на текст правила и живой
замер на двух-трёх блоках Фофанова (АТД «дек», хеширование) до и после.

## Шаг 4. «Собрать с ИИ» из выбранных кусков

Новый генератор не нужен: «Собрать урок» уровней «Черновик / Обычный / Подробный»
(`lessons/ai_build.py`, `ai_steps.py`, диалог `frontend/src/screens/lessons/LessonBuildDialog.tsx`)
уже строит план, шаги и рецензию из кандидатов `lessons/candidates.collect`. Сейчас
выбор человека туда не попадает: проход 2 даёт слабый сигнал 0,7, а диапазон оглавления
забирает фрагменты первым.

### 4.1. Бэкенд

- `LessonAiOrder` (`lessons/ai_schemas.py`) получает
  `pinned: list[LessonPinnedRange] = Field(default_factory=list, max_length=20)`, где
  `LessonPinnedRange = {material_id, from_fragment_id, to_fragment_id}` — ровно то, что
  несёт кусок (`EvidenceSummary.from_fragment_id/to_fragment_id`).
- `candidates.collect(session, node, material_ids, pinned=())` добавляет закреплённые
  **первыми**: `pool.add(source, rows, score=1.1, signal="выбрано человеком", outline=True)`
  — `outline=True` уже гарантирует, что кусок не вытесняется поиском и лимитом
  `MAX_CANDIDATES`. Строки диапазона — через существующий `_rows` по фрагментам между
  `from` и `to` в порядке чтения (как `add_fragments`). Материал закреплённого куска
  добавляется в `sources`, даже если его не выбрали в диалоге.
- Оглавление и поиск при закреплённых кусках: новый флаг `pinned_only: bool = True` —
  тогда `collect` не зовёт `_outline`, `_bindings` и `_search`, урок строится только из
  выбранного. С `False` поиск добавляет к ним своё. `basis` (`sources`,
  `sources_and_model`, `model_only`) не трогать: он про то, может ли модель писать от
  себя, а не про отбор кусков.
- Промпт плана: в `header()` сигнал «выбрано человеком» уже виден модели; добавить в
  правила плана одну строку «куски с сигналом „выбрано человеком“ обязательны и идут в
  порядке книги». Рецензент проверяет, что все закреплённые попали в урок.

Тест (`backend/tests/test_lesson_candidates.py`, сборка — `test_lesson_ai_build.py`): два
закреплённых куска второго материала при `pinned_only=False` и диапазоне оглавления → оба в
кандидатах с `in_outline`, в порядке книги, с сигналом «выбрано человеком»; неверный
диапазон (`from` после `to`, чужой материал) → 422 с кодом.

### 4.2. Фронтенд

- В панели выбора кусков (`evidence-selection-bar` во вкладке «Источник» —
  `screens/workspace/TextbookSourcePanel.tsx`, и в «Предложено» —
  `screens/lessons/LessonSuggestedTab.tsx`) рядом с «В урок» — кнопка «Собрать с ИИ»
  (иконка `Sparkles`), доступна при выбранных кусках и включённых внешних моделях.
- Она открывает существующий `LessonBuildDialog` для темы с `pinned` из выбранных
  кусков в порядке книги (`inReadingOrder`). В диалоге сверху список «Выбранные куски ·
  N» (название, материал, страницы) с возможностью снять кусок; остальные поля диалога
  без изменений. Из Рабочей области после запуска — переход в «Уроки» на задачу, как
  сейчас делает запуск из «Уроков».
- Типы: `LessonAiOrder` в `frontend/src/api/lessons.ts`.

Проверка: `npm run typecheck`; Playwright-сценарий на подставленном API в духе
`frontend/coverage-i5.spec.ts`: отметить два куска → «Собрать с ИИ» → в запросе
`pinned` из двух диапазонов в порядке книги. Живой прогон «Черновика» по «СКНФ и СДНФ»
с кусками Афанасьева стр. 26–29 и Игошина (после шага 3) — один платный запуск, его
делает пользователь.

Не делать в шаге 4: новый режим генерации, отдельную очередь, автоматический выбор
кусков без человека.
