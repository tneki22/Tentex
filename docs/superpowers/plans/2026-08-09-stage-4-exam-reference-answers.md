# Этап 4: эталонные ответы и полный офлайн-сценарий экзамена

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task with review checkpoints.

**Цель:** закрыть подтверждённые хвосты этапа 3, привязать эталонные ответы к стабильным `ProgramNode.id` и довести экзаменационный сценарий от вставки списка вопросов до чтения эталона в рабочей области без ИИ и без преждевременной реализации этапа 5.

**Архитектура:** эталонный ответ хранится отдельной 1:1-сущностью, чей составной внешний ключ указывает на `(project_id, program_node_id)`. Импорт текста ответов использует только точное нормализованное совпадение заголовка с текущим названием учебного узла; пользователь подтверждает либо редактирует результат. Карта покрытия получает отдельный агрегирующий read-model, а Рабочая область загружает только ответ выбранной темы. Файлы, `Material`, страницы, фрагменты, привязки и OCR в этот этап не входят.

**Стек:** FastAPI, SQLAlchemy, Alembic, SQLite/WAL, Pydantic v2, React, TypeScript, Vite, существующий UI-кит Tentex и Radix.

1. `backend/app/projects/importer.py` воспринимает строку `Вопросы:` как отдельный вопрос в формате «только вопросы». Это воспроизводится на обычном вводе `Вопросы:\n1. Индексы\n2. Транзакции` и даёт три вопроса вместо двух.
2. `frontend/src/screens/ExamWizard.tsx` после возобновления черновика теряет отображаемые счётчики импорта и предупреждения, хотя программа и состояние черновика сохранены.
3. Мастер экзамена не предупреждает о расхождении между ожидаемым и фактически распознанным количеством пунктов, хотя это записано в детальном плане этапа 3.
4. Часть паспорта цели существует в состоянии, но молча сохраняется значениями по умолчанию: стартовый уровень, целевой уровень и формат подготовки нельзя выбрать. Критерий успеха всегда упоминает решение задачи даже для теоретического экзамена. Для `Exam-NDB` это уже неверно: его README прямо говорит, что задач в билетах нет.
5. В `TextbookWizard.tsx` аналогично скрыты обязательные решения паспорта цели: охват, срок, стартовый и целевой уровни, критерий успеха, формат и модули.
6. Поиск по дереву программы не сохраняет всю цепочку предков для совпадений на глубине 3–4: в Рабочей области проверяются только непосредственные дети, а в Программе плоская фильтрация вообще отрывает найденный узел от иерархии.
7. `ProjectWorkspace.tsx` не реагирует на смену `?topic=` внутри уже открытого проекта, потому что загрузочный эффект зависит только от `projectId`.
8. После удаления узла или undo создания экран Программы может оставить выбранным уже скрытый узел.
9. Быстрые повторные перестановки карточек в `Projects.tsx` отправляют несколько optimistic PUT независимо; при изменившемся порядке ответа более старый запрос может закончиться позже нового. Это пограничный риск, а не воспроизведённая потеря данных, но его дешёво закрыть сериализацией мутаций.

Это не разрушает базовую архитектуру этапа 3: модель проекта, стабильные UUID узлов, optimistic revisions, архивирование, undo и SQLite/WAL реализованы последовательно. Поэтому не требуется переделывать этап 3 — нужен ограниченный ремонт перед добавлением эталонов.

```text
вставить список вопросов

  -> вставить текстовые блоки ответов
```

Импорт эталонов выполняется только в уже активном экзаменационном проекте через Карту покрытия. В мастер черновика ответы не добавляются: иначе повторный импорт программы потребует уже сейчас решать идентификацию и reconcile узлов, а это противоречит простой архитектуре этапа 4.

## Контракт данных этапа 4

Добавить отдельную сущность `ReferenceAnswer`, а не раздувать `ProgramNode`:

```python
class ReferenceAnswer(Base):
    __tablename__ = "reference_answers"

    project_id: Mapped[UUID]
    program_node_id: Mapped[UUID]
    text: Mapped[str]
    origin_kind: Mapped[ReferenceAnswerOrigin]       # manual | import
    match_method: Mapped[ReferenceAnswerMatchMethod] # manual | exact_title
    matched_title: Mapped[str | None]
    is_confirmed: Mapped[bool]
    is_active: Mapped[bool]
    revision: Mapped[int]
    source_label: Mapped[str | None]
    created_at: Mapped[datetime]
    updated_at: Mapped[datetime]
```

Инварианты:

- составной первичный ключ и внешний ключ: `(project_id, program_node_id) -> program_nodes(project_id, id)`;
- непустой `text`, `revision >= 0`;
- ручной ответ создаётся с `origin_kind=manual`, `match_method=manual`, `is_confirmed=True`;
- импортированный ответ создаётся с `origin_kind=import`, `match_method=exact_title`, `is_confirmed=False`, `matched_title=<название в момент импорта>`;
- bulk-import никогда не перезаписывает существующую активную или снятую запись;
- удаление мягкое (`is_active=False`), чтобы демо-seed не воскресил удалённый пользователем ответ;
- переименование, перенос и undo узла не перепривязывают ответ: UUID остаётся канонической связью;
- статус «нужно проверить» вычисляется, если нормализованный `matched_title` больше не совпадает с текущим названием узла;
- снятый вместе с узлом ответ сохраняется и снова становится видимым при восстановлении узла.

Производные статусы интерфейса:

```python
ReferenceAnswerStatus = Literal[
    "missing",
    "auto_matched",
    "confirmed",
    "needs_review",
    "manual",
]
```

Приоритет вычисления: нет активной записи → `missing`; изменилось название импортированного узла → `needs_review`; ручное происхождение → `manual`; подтверждён → `confirmed`; иначе → `auto_matched`.

## Контракт импорта ответов

Парсер знает названия текущих учебных узлов и использует их как разделители блоков. Он не делает нечёткое сопоставление и не назначает ответы по позиции.

Нормализация заголовка:

```python
def normalize_answer_heading(value: str) -> str:
    value = unicodedata.normalize("NFKC", value).casefold().replace("ё", "е")
    value = LEADING_NUMBER_OR_QUESTION_RE.sub("", value)
    value = value.strip(" \t\r\n.:;—–-")
    return " ".join(value.split())
```

Алгоритм:

1. Построить индекс `normalized_title -> [ProgramNode]` только для текущих учебных узлов.
2. Строка, совпавшая ровно с одним названием, открывает блок ответа.
3. Последующие строки до следующего известного заголовка составляют ответ; одиночный префикс `Ответ:` удаляется.
4. Дубликат названия в программе даёт `ambiguous`, а не автоматическую привязку.
5. Текст до первого известного заголовка и неизвестные заголовки возвращаются в `unmatched_sections`.
6. Пустые блоки не создаются и возвращаются в предупреждениях.
7. Уже существующий ответ возвращается в `skipped_existing`; импорт его не меняет.

Ограничение запроса — 1 МиБ, как и у импорта программы.

## HTTP API этапа 4

```text
GET    /api/projects/{project_id}/coverage-map
GET    /api/projects/{project_id}/program-nodes/{node_id}/reference-answer
PUT    /api/projects/{project_id}/program-nodes/{node_id}/reference-answer
POST   /api/projects/{project_id}/program-nodes/{node_id}/reference-answer/confirm
DELETE /api/projects/{project_id}/program-nodes/{node_id}/reference-answer
POST   /api/projects/{project_id}/reference-answers/import
```

`GET .../reference-answer` возвращает слот с `answer: null`, а не 404: отсутствие ответа — нормальное состояние темы.

```python
class ReferenceAnswerWrite(BaseModel):
    expected_revision: int | None
    text: Annotated[str, StringConstraints(strip_whitespace=True, min_length=1)]

class ReferenceAnswerConfirm(BaseModel):
    expected_revision: int

class ReferenceAnswerImport(BaseModel):
    raw_text: Annotated[str, StringConstraints(strip_whitespace=True, min_length=1, max_length=1_048_576)]
    source_label: str | None = None
```

`expected_revision=None` означает create-only. Изменение существующей записи требует точной ревизии; конфликт возвращает `409 stale_reference_answer_revision`. Создание поверх существующей активной или снятой записи тоже возвращает явный конфликт, а реактивация выполняется обычным `PUT` с текущей ревизией.

Карта покрытия возвращает только фактически реализованные данные:

```python
class CoverageMapRow(BaseModel):
    node_id: UUID
    parent_id: UUID | None
    kind: ProgramNodeKind
    title: str
    position: int
    is_current: bool
    target_level: TargetLevel | None
    answer_status: ReferenceAnswerStatus
    answer_preview: str | None
    answer_revision: int | None

class CoverageMapTotals(BaseModel):
    study_nodes: int
    with_answer: int
    confirmed: int
    needs_review: int
    missing: int
```

Не добавлять нулевые поля материалов, качества OCR, попыток и прогресса: они появятся на своих этапах.

6. manual create/update, stale revision `409`, confirm и soft delete/reactivate;
7. rename узла переводит импортированный ответ в `needs_review`, move сохраняет связь;
8. remove/restore узла сохраняет ответ;
9. карта корректно считает `with_answer`, `missing`, `confirmed`, `needs_review`;
10. demo-seed повторяется идемпотентно и не восстанавливает снятый пользователем ответ;
11. учебник, архивный и завершённый проект отклоняют запись.

## Критерии готовности

Этап 4 считается завершённым, только если одновременно выполнено следующее:

- ввод `Вопросы:` не создаёт ложный узел, паспорт цели не сохраняет важные решения скрыто, глубокий поиск и query-навигация работают;
- эталон связан со стабильным `ProgramNode.id` и переживает rename, move, remove/restore и перезапуск;
- bulk import полностью детерминирован, не использует ИИ, не делает fuzzy/позиционного сопоставления и ничего не перезаписывает молча;
- Карта покрытия показывает реальное наличие эталонов и статусы, но не изображает ещё не реализованные материалы, попытки и OCR;
- выбранный эталон читается в Рабочей области;
- demo-seed идемпотентен и уважает пользовательские изменения;
- проверки этапов 2, 3 и 4, Ruff, typecheck, lint и build проходят;
- полный текстовый экзаменационный сценарий пройден браузером после `docker compose restart web`;
- документация честно говорит, что загрузка файлов и материальное покрытие начнутся на этапе 5.
