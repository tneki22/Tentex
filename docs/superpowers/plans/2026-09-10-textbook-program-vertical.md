## Что входит в вертикаль

1. Импорт оглавления в программу — офлайновый путь, ноль вызовов модели.
2. Чат построения программы с дифами — режим «С ИИ» шага 4 мастера.
3. Один редактор программы на две точки входа: шаг мастера и раздел проекта.
4. Честные заглушки вместо битых путей учебникового проекта.
5. Тест-цикл на 3–4 учебниках.

**Не входит:** проход 2 и привязки, Уроки, Занятия, векторный поиск, учебниковый чат
по теме. Соответствующие exam-гейты снимаются в своих вертикалях, а не здесь:
`bindings/service.py:58` (`bindings_require_exam_project`), `exam/chat.py:62`
(`chat_exam_only`), `preparation/data.py:40` (`preparation_exam_only`).

## Что уже есть и переиспользуется

### Модель программы почти готова

`ProgramNode` (`backend/app/models.py:865`) уже несёт всё, что нужно учебниковому
дереву, — новых полей почти не требуется:

| Поле | Назначение в этой вертикали |
|---|---|
| `goal_role` (`GoalRole`: `target` / `prerequisite` / `related`) | Роль темы в цели при узком охвате (FR-G16.1) |
| `target_level` (`TargetOutcome`) | Уровень цели, по умолчанию из паспорта |
| `is_in_current_program` | «Вне текущей программы» — FR-G11, ничего не удаляем |
| `needs_material` | «Нужно найти материал по теме» |
| `origin_kind` (`OriginKind`) | **`OUTLINE`, `PASS1`, `CATALOG` объявлены, но нигде не присваиваются** — присваиваются только `MANUAL`, `IMPORT`, `MODEL`. Импорт оглавления ставит `OUTLINE`, диф модели — `MODEL` |
| `origin_note` | Объяснение модели или подпись источника |
| `origin_material_id` | Из какого материала пришла тема |

Валидатор варианта уже есть: `projects/program.py:141` `_validate_variant()` — у
textbook `exam_kind` обязан быть `null`.

**Единственная недостающая пара полей** — страницы источника для FR-G15
(«тема несёт ссылки на страницы, из которых она получена»): `origin_page_from`,
`origin_page_to`, оба nullable `Integer`.

### Оглавление уже лежит в базе

Парсить заново ничего не надо.

- `Material.outline` (`models.py:523`, JSON) — закладки PDF, извлекаются
  `materials/parsers/native.py:56` `extract_outline()` через `PyMuPDF.get_toc(simple=False)`.
  Заполняется в `materials/worker.py` и после сборки Typst.
- `materials/library.py:147` `_recognized_outline()` — запасной источник: фрагменты
  с `element_kind == "heading"` активной ревизии, уровень из `structure_level` (1–4).
- `materials/library.py:168` `_outline()` возвращает `(items, source)` с приоритетом
  `embedded` → `recognized` → `none`. `OutlineSource` — `materials/schemas.py:284`,
  `OutlineItem {level, title, page}` — `schemas.py:300`.

**Сборка плоского списка в дерево уже написана** — `PdfOutline.tsx:23` `buildTree()`
(стек по уровням). Серверная версия повторяет ту же логику; не изобретать вторую.

### Модель чата переиспользуется целиком

`ChatSession` / `ChatMessage` / `ChatToolRun` (`models.py:1443`–`1558`) уже дают
стриминг, `payload_kind` + `payload` JSON, снимок контекста, override модели,
область памяти и черновик композера. Новую таблицу заводить не надо.

`ChatSession.section_scope_node_id` ложится на «область контекста: вся программа /
раздел / тема» из FR-G9.4 без изменений.

### Tool поиска по учебнику готов

`chat_tools/registry.py` регистрирует `search_project_materials` поверх FTS5/BM25
(`bindings/service.py` `search_project_materials`). Поиск **не гейтится вариантом
проекта** — проверяется только существование проекта, поэтому в учебниковом он уже
работает. Именно им пользуется сценарий «программа по моей цели».

### Роль ИИ — одна строка, без миграции

`ai/roles.py:53` `ROLE_SPECS`. Настройки роли создаются лениво через
`PUT /api/settings/ai/roles/{role}` (`AiRoleSetting` имеет `role: str` как PK), так что
миграции новая роль не требует. Все 15 существующих ролей — `exam_*` или транспортные;
эта будет первой учебниковой.

### Фоновая задача

`BackgroundJob` с диспетчеризацией по `kind` — контракт в
`docs/architecture/background-jobs.md`. Долгая первая сборка программы обязана идти
через него, иначе уход с экрана теряет результат (ровно та проблема, ради которой
единая очередь и делалась).

## Работа 1. Импорт оглавления

Новый модуль `backend/app/projects/program_outline.py`.

**Чтение кандидатов.** Взять `_outline(session, material)` из `materials/library.py`,
собрать дерево по уровням, вернуть кандидатов с `level`, `title`, `page`, признаком
источника (`embedded` / `recognized` / `none`) и предлагаемым `node_type`.

**Применение.** Уровень → тип узла: `1 → section`, `2 → topic`, `3–4 → subpoint`.
Каждому узлу: `origin_kind=OriginKind.OUTLINE`, `origin_material_id`, `origin_page_from`
(страница записи) и `origin_page_to` (страница следующей записи того же или более
верхнего уровня минус один), `goal_role=GoalRole.TARGET`, `target_level` из
`GoalPassport.target_outcome`, `exam_kind=None` (иначе `_validate_variant` отвергнет).

Всё в одной транзакции: +1 к ревизии программы, одна запись в `ProjectActionLog` →
undo одной командой (NFR-5). Повторный импорт того же оглавления не должен создавать
дубли молча — сверять по `(origin_material_id, title, origin_page_from)`.

**Эндпоинты.**

| Метод | Путь |
|---|---|
| `GET` | `/api/projects/{project_id}/program/outline-candidates?material_id=` |
| `POST` | `/api/projects/{project_id}/program/import-outline` |

Гейт: только `WorkspaceVariant.TEXTBOOK` и активный проект либо черновик — симметрично
exam-only проверке импорта в `projects/program.py:692` («Импорт доступен только в
активном экзаменационном проекте»).

## Работа 2. Чат построения программы

**Новые значения enum.**

- `ChatMode.PROGRAM = "program"` (`models.py:298`)
- `ChatPayloadKind.PROGRAM_DIFF = "program_diff"` (`models.py:289`)

> ⚠️ Обе колонки объявлены через `enum_type(..., native_enum=False, create_constraint=True)`
> — за каждым значением стоит CHECK-констрейнт. **Миграция обязана пересобрать
> констрейнт**, иначе вставка нового значения упадёт. Ровно на этом уже спотыкались:
> `needs_input` упёрся в старый CHECK, переживший расширение перечисления (миграция
> 0043, см. `STATUS.md`, обновление 09.09.2026).
>
> Там же второй урок: `migrations/env.py` снимает `PRAGMA foreign_keys` на время
> прогона — если пересборка таблицы делается вручную, проверить, что каскады после
> миграции живы.

**Контекст запроса.** Паспорт цели (`scope`, `goal`, `target_outcome`, `important`,
`excluded`, `deadline`, темп), оглавление каждого источника с числом страниц по главам,
роли и приоритеты источников из `ProjectMaterial`, текущее дерево программы. Состав
показывается пользователю до отправки и сохраняется снимком в `ChatMessage.context_snapshot`
— как в экзаменационном чате.

**Роль ИИ `study_program_assistant`** в `ROLE_SPECS`:
`modality=text`, `required_capabilities={streaming, structured_output}`,
`cache_policy=none`, `allow_request_model_override=True`,
`prompt_version="study-program-v1"`.

Одна роль на весь чат: она и строит программу с нуля, и правит существующую. Два
стартовых сценария («по оглавлению» / «по моей цели») — это разные заготовки первого
сообщения и разный акцент в системном промпте, а не две роли.

**Долгая первая сборка** — `BackgroundJob` нового `kind` (например `study_program_build`),
с прогрессом по источникам и главам, отменой и чтением результата через
`GET /background-jobs/{id}/result`.

## Работа 3. Применение дифа

`POST /api/projects/{project_id}/program/diff/apply` принимает id сообщения, список
выбранных операций и `expected_program_revision`.

Операции: `add`, `rename`, `move`, `set_goal_level`, `remove_from_program`.

Выполняются существующими сервисами `projects/program.py` **одной транзакцией**:

- созданные и изменённые узлы получают `origin_kind=OriginKind.MODEL` и `origin_note`
  с объяснением модели;
- `remove_from_program` ставит `is_in_current_program=False` и **ничего не удаляет**
  (FR-G11): привязки, карточки, конспект и история остаются;
- одна запись в `ProjectActionLog` на всё применение → отмена одной командой
  (FR-G10.1);
- расхождение ревизии — отказ с перечитыванием, а не молчаливое применение поверх.

Отдельная таблица предложений не нужна: диф живёт в `ChatMessage.payload` при
`payload_kind = program_diff`, состояние принятия — там же.

## Приёмка

**Автоматическая.**

1. `cd backend && python -m pytest` и `python -m ruff check .` — зелёные, вывод показан.
   Новые тесты: сборка дерева из плоского оглавления (включая пропуски уровней и
   мусорные записи), применение и undo импорта, повторный импорт без дублей,
   применение частичного дифа, отказ при устаревшей ревизии.
2. `npm run typecheck && npm run build` — зелёные.
3. `docker compose restart api web` — без этого правка не считается проверенной.

**Живой сценарий** (`preview_start` с конфигурацией `full` — нужны api и worker):

1. Создать учебниковый проект из реального PDF с закладками.
2. Шаг 4, режим «Вручную»: импортировать оглавление, отменить импорт, импортировать
   заново с другой глубиной и снятыми ветками.
3. Переключиться в «С ИИ»: попросить убрать раздел и добавить тему из оглавления,
   принять половину дифа, отменить применение.
4. Проверить, что переключение «Вручную ↔ С ИИ» ничего не теряет.
5. Утвердить программу, создать проект, открыть раздел «Программа» — это тот же
   редактор с тем же деревом.
6. Пройти по всей навигации проекта: ни один пункт не ведёт в редирект.
7. Скриншот шага 4 в обоих режимах.

**Замер качества** — отдельно от приёмки, по разделу 12 `TEXTBOOK_MODE.md`. Результат
в `docs/research/`; он же решает, нужен ли полный проход 1.
