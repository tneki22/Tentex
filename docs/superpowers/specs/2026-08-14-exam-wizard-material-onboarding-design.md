# Восстановление мастера экзаменационного проекта

Дата решения: 14 августа 2026 года.

Визуальный источник истины — тег `ui-stage-1-baseline`, экран
`frontend/src/screens/ProjectWizard.tsx`. Фактические возможности системы берутся
из текущих API этапов 2–5 и документов `SCREENS.md`, `REQUIREMENTS.md` и
`docs/architecture/`. Этот документ фиксирует, как вернуть исходный интерфейс,
не потеряв появившееся позднее живое поведение.

## Проблема

Мастер сейчас обещает, что загрузка файлов появится на этапе 5, хотя файловый
конвейер этапа 5B уже работает. На шаге «Что у вас уже есть» доступны только
вопросы, а карточки эталонных ответов и учебных материалов заблокированы. В итоге
экзаменационный сценарий искусственно сводится к вставке текста и не выполняет
исходное обещание интерфейса этапа 1.

Это не новая продуктовая концепция. Полный интерфейс был свёрстан в
`ui-stage-1-baseline`, но при подключении мастера к реальным API в коммите
`2b399d5` его восстановили частично. Стили исходных карточек, панелей загрузки и
итоговой истории сохранились, поэтому макет можно вернуть без редизайна.

## Решение

Возвращается исходная пятишаговая экзаменационная ветка:

1. формат экзамена;
2. какие материалы уже есть и мнение системы;
3. добавление вопросов, готовых ответов и учебных материалов;
4. паспорт цели;
5. проверка того, что будет создано.

Визуальная структура, порядок блоков, размеры карточек, переключатели
«Файлы / Текст» и итоговая композиция берутся из baseline. Текущий
`WizardChrome`, живой черновик, восстановление после перезагрузки, контроль
ревизий и реальные переходы после создания сохраняются.

Рекомендуемый путь — узко расширить существующие контракты материалов для
чернового проекта. Не создаётся отдельный универсальный механизм импорта и не
копируется файловый конвейер внутрь мастера.

### Рассмотренные альтернативы

| Подход | Решение |
| --- | --- |
| Разблокировать две карточки, но оставить только текстовый импорт вопросов | Отклонён: визуально убирает заглушку, но не возвращает маршруты исходного мастера |
| Вернуть baseline и подключить его к существующим `Material`, `ProjectMaterial` и воркеру | Выбран: сохраняет интерфейс и повторно использует готовый конвейер |
| Сделать новый единый API «прими всё и создай проект» | Отклонён: скрывает состояния обработки, дублирует существующие сервисы и усложняет возобновление |

## Шаг 1. Формат экзамена

Возвращаются четыре карточки:

- «Список вопросов»;
- «Вопросы и задачи»;
- «Билеты»;
- «Точного списка пока нет».

Выбор сохраняется в `WizardDraft.state`; карточка заранее не выбирается. Для
первых трёх вариантов список вопросов или билетов становится основным источником
Программы. Четвёртый вариант остаётся экзаменационным проектом с пустой
Программой: официальный список можно импортировать позже на экране «Вопросы
экзамена».

«Точного списка пока нет» не подменяет режим проекта. На следующем шаге учебный
материал становится обязательным, а интерфейс честно объясняет: до появления
прохода 1 система сохранит и разберёт источники, но не построит по ним
предварительную Программу автоматически. Рядом даётся нейтральная подсказка, что
для систематического изучения конкретной методички лучше соседний сценарий
«Изучение по учебнику».

## Шаг 2. Что уже есть

Исходная сетка карточек возвращается целиком:

- список вопросов или билетов — включён по смыслу выбранного формата;
- готовые ответы — независимый выбор;
- учебные материалы — независимый выбор.

Для варианта без точного списка учебные материалы включены и обязательны. У
каждой карточки остаются подпись, иконка и видимый выбранный статус.

Под сеткой система сразу показывает детерминированное мнение, без внешнего ИИ:

| Выбор | Мнение системы |
| --- | --- |
| Только список | Этого достаточно для создания Программы; ответы и источники можно добавить позже |
| Список + ответы | Лучший маршрут для тренировки: вопросы станут Программой, ответы — эталонами |
| Список + материалы | Программа будет готова сразу; источники сохранятся для поиска и ручной привязки |
| Всё вместе | Система отдельно разберёт структуру, эталоны и источники и разложит их по назначению |
| Точного списка нет | Создадим пустую экзаменационную Программу и сохраним источники; официальный список можно добавить позже |

Текст мнения не обещает векторный поиск, проходы 1–2 или автоматическое
распределение учебных материалов. Доступные сейчас возможности называются
прямо: разбор, просмотр, лексический поиск и ручная привязка.

## Шаг 3. Добавление материалов

Для каждого выбранного назначения показывается отдельная исходная панель
загрузки. Панели не смешивают роли и не просят пользователя самостоятельно
раскладывать файлы после создания.

### Вопросы, задачи или билеты

Допускается один основной источник:

- файл PDF, DOCX, TXT, MD или изображение;
- либо вставленный текст.

Файл сразу загружается в черновой проект с назначением `exam_structure` и
запускается в быстром режиме разбора. После готовности пользователь видит
предварительную структуру и может импортировать её в черновую Программу. Для
текста повторно используется существующий `wizard-drafts/{id}/exam-import`.

Серверный импорт файла должен стать безопасным для черновика: проверять
`draft_revision` и `program_revision`, заменять именно черновую Программу и
записывать исходный материал. Активный проект через этот маршрут не изменяется.

### Готовые ответы

Допускается один файл или один текстовый документ с назначением
`reference_answers`. Ограничение «один файл ответов на проект» сохраняется и
видимо объясняется в интерфейсе.

После активации проекта материал обрабатывается в фоне. Заголовки ответов
сопоставляются со стабильными `ProgramNode.id`, а найденный текст заполняет
эталонные ответы. Если материал уже был разобран в Библиотеке, после активации
сразу вызывается повторная привязка к новому проекту, а не ожидается повторный
разбор физического файла.

### Учебные материалы

Можно добавить несколько файлов с назначением `study_source`. В мастере у них
доступны понятные роли источника: основной, дополнительный или справочный. После
создания они находятся в «Материалах», доступны в Просмотрщике, лексическом
поиске и для ручной привязки к темам.

До реализации отложенных проходов учебный файл не обещает автоматического
заполнения Программы или умной раскладки по темам. Это ограничение показано
спокойной информационной подписью, а не блокирует загрузку.

### Состояния и ошибки

Файлы загружаются на сервер сразу, пока проект остаётся черновиком. Строка файла
показывает загрузку, ожидание, обработку, готовность и ошибку. Перезагрузка
страницы восстанавливает строки из `ProjectMaterial`, а выбранные назначения,
текстовые поля и режимы ввода — из `WizardDraft.state`.

Ошибка одного файла не очищает другие панели. Переключение «Файлы / Текст» при
непустом вводе и снятие карточки с уже добавленным материалом требуют явного
подтверждения. Ошибки API сохраняют машинный `code` и `context`, чтобы интерфейс
мог отличить дубликат файла ответов, конфликт ревизии и сбой обработки.

## Шаг 4. Паспорт цели

Живой паспорт цели сохраняется без изменения доменной модели. Восстанавливается
baseline-компоновка полей, но значения читаются и пишутся через текущий API
черновика. Переход дальше невозможен, пока обязательные поля паспорта невалидны.

## Шаг 5. Проверка и создание

Возвращается исходная итоговая история: формат экзамена, выбранные входы,
Программа, источники и краткое мнение системы. Пользователь может вернуться к
любому разделу, исправить импортированную структуру и увидеть, что будет сделано
после нажатия основной кнопки.

Создание выполняется в таком порядке:

1. сохранить последнюю ревизию черновика и паспорта;
2. убедиться, что обязательный основной источник импортирован, либо явно выбран
   разрешённый маршрут с пустой Программой;
3. активировать проект;
4. запустить готовые к обработке ответы и учебные источники;
5. для уже разобранного файла ответов немедленно запустить сопоставление;
6. открыть созданный проект.

Сбой фонового запуска ответов или источника после активации не откатывает уже
созданный проект. Пользователь получает конкретное предупреждение и действие
«Открыть Материалы», где обработку можно продолжить. Повторное нажатие не должно
создавать второй проект или повторно прикреплять тот же материал.

## Контракты и изменения кода

### Фронтенд

- `ExamWizard.tsx` возвращает пять исходных поверхностей и управляет их живыми
  состояниями.
- Повторно используется визуальный язык baseline и существующие классы из
  `layout.css`; новые токены и параллельный UI-kit не создаются.
- Панель добавления материалов выносится в небольшой доменный компонент только
  если это сокращает дублирование трёх одинаковых состояний.
- `useWizardDraft` получает ревизионно-безопасный файловый импорт Программы и
  сохраняет состояния новых полей.
- API материалов передаёт структурированные ошибки до экрана, не превращая их
  в одну строку.
- Кнопки, карточки и переключатели остаются клавиатурно доступными; ошибка
  связана с конкретным контролом и не сообщается только цветом.

### Бэкенд

- Существующая загрузка `Material` в черновой проект повторно используется для
  всех трёх назначений.
- Добавляется draft-safe preview/import разобранной структуры экзамена. Он
  использует текущий парсер, но применяет результат через замену черновой
  Программы и проверяет обе ревизии.
- Ограничение единственного файла ответов и существующий автолинк сохраняются.
- Схема БД не меняется, если все состояния интерфейса помещаются в
  `WizardDraft.state`; новая таблица для мастера не нужна.
- Внешний ИИ не добавляется: мнение системы и классификация входов полностью
  детерминированы.

## Намеренные отличия от baseline

Baseline был моковым и позволял свободно рисовать несколько источников без
серверных ограничений. В живой версии один основной файл структуры и один файл
ответов являются каноническими; учебных источников может быть несколько. Это
делает замену и повторный запуск однозначными и соответствует текущей модели.

Любое дополнительное отличие в порядке блоков или основных взаимодействиях
допустимо только после согласования и должно быть записано в
`docs/ui/stage-1-interface-baseline.md`.

## Регрессионный аудит после восстановления

Восстановление считается завершённым только после отдельной проверки того, что
поздние коммиты не потеряли важное поведение и что baseline не затёр их обратно.

### Исторический аудит

Сравниваются baseline, текущая ветка и все последующие изменения, затронувшие
мастер, материалы или Программу. Обязательно проверяются как минимум:

- `19717f3` — оболочка живого мастера;
- `2b399d5` — частичное восстановление экзаменационной ветки;
- `a1ee118` — живая учебниковая ветка;
- `fce8973` — исправления Материалов и привязок;
- `4a7d43f` — шлюз ИИ и группировка экзаменационной Программы.

Особо сохраняются: возобновляемые черновики, конфликты ревизий, удаление
черновика, учебниковая ветка, активация с пустой Программой, единственный файл
ответов, автопривязка ответов, Просмотрщик, поиск и ручные привязки, корректный
маршрут после успешного создания.

Результат аудита — короткая таблица «baseline / позднее изменение / итоговое
поведение» в архитектурном документе реализации. Найденная потеря либо
исправляется в этой же задаче, либо явно записывается как отдельный дефект с
причиной, почему её нельзя безопасно включить.

### Автоматическая проверка

- фронтенд: `npm run typecheck`, `npm run build`, `npm run lint`;
- бэкенд: `python -m ruff check .` и релевантные pytest-проверки;
- сквозные проверки этапов 2, 3, 4 и 5, ручных привязок и экзаменационного чата,
  если затронут их общий контракт;
- отдельный сквозной сценарий мастера: файл вопросов → разбор → импорт в
  черновик → активация → файл ответов → автозаполнение эталонов;
- отдельный сценарий «Точного списка пока нет»: пустая Программа + сохранённый
  и запущенный учебный материал;
- возобновление обоих сценариев после перезагрузки на середине загрузки.

### Визуальная проверка

После `docker compose restart web` вручную проходят все комбинации материалов,
светлую и тёмную темы, широкое окно и ширину 390 px. Проверяются клавиатура,
фокус, ошибки файла, возврат между шагами, перезагрузка черновика и повторная
попытка создания. Ключевые шаги сравниваются с `ui-stage-1-baseline`, а не только
с текущим урезанным экраном.

## Критерии готовности

- Ни на одном шаге нет обещания «появится на этапе 5».
- Пользователь до создания добавляет вопросы, ответы и несколько учебных
  материалов, а система сама назначает им правильное место.
- Мнение системы меняется сразу и не обещает отложенные возможности.
- Все четыре формата экзамена работают, включая проект без точного списка.
- Файлы и ввод переживают перезагрузку; конфликт и ошибка не теряют данные.
- Вопросы образуют черновую Программу, ответы после активации образуют эталоны,
  учебные материалы появляются в Материалах.
- Визуальная иерархия соответствует этапу 1, а поздние живые функции проходят
  отдельный регрессионный аудит.
