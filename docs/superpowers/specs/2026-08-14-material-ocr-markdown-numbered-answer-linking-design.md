# OCR, Markdown и связь файла ответов с вопросами

Дата решения: 14 августа 2026 года.

Задача относится к экзаменационному режиму, экрану «Материалы проекта» и вкладке
«Обработка». Она чинит один сквозной путь: файл → структурированный Markdown →
вопросы или разделы ответов → безопасная связь с Программой. Содержимое файлов
пользователя при разведке не читалось; проверялись только типы элементов, размеры,
координаты, шрифтовые признаки, нумерация и агрегированные количества.

Источники поведения: `REQUIREMENTS.md` FR-M4.2 и FR-M7.2, раздел «Материалы
проекта» в `SCREENS.md`, `PLAN.md` (этап 5 и список отложенных режимов),
`docs/architecture/materials-viewer-and-answers-autolink.md`.

## Подтверждённая причина

Текущий native-разбор PDF строит элементы несколькими эвристиками по размеру
шрифта, номеру в начале строки и отступу. Любая короткая строка вида `N. ...`
становится заголовком. Таблицы отдельно не извлекаются, а уровни списка
восстанавливаются только по нескольким маркерам и отступу строки.

На текущем файле ответов это даёт 443 заголовка, 1 340 абзацев и только 3 пункта
списка, хотя геометрический анализ находит 17 таблиц на 16 страницах. Все 443
заголовка затем становятся самостоятельными блоками, и автосвязь ошибочно считает
каждый подпункт кандидатом на вопрос.

В файле списка вопросов находятся 19 нумерованных строк: основной непрерывный ряд
`1…16` и отдельный ряд `1…3` в конце с другим оформлением. Импорт создаёт 20
вопросов, потому что вводная строка до первого номера тоже принимается за вопрос,
а последний ряд — за продолжение основного списка. Паспорт проекта ожидает 16
элементов; после ручного удаления в Программе активны именно 16 вопросов.

## Рассмотренные варианты

| Подход | Решение |
| --- | --- |
| Расширить регулярные выражения текущего парсера | Отклонён: можно подогнать под один PDF, но таблицы, колонки и следующий вид подпунктов снова потеряются |
| Отправлять страницы внешней модели | Отклонён: базовый разбор обязан работать офлайн; результат был бы платным и недетерминированным |
| Подключить локальный layout-разбор и отдельно проверять нумерацию | Выбран: готовая библиотека восстанавливает Markdown, а предметная логика отвечает только за границы вопросов и безопасную связь |

Для текстового слоя PDF используется официальный `PyMuPDF4LLM` поверх уже
принятого в проекте PyMuPDF. Он умеет выдавать структурированный Markdown и JSON
с координатами, восстанавливает порядок чтения, таблицы, списки и inline-стили.
Официальное описание: <https://github.com/pymupdf/pymupdf4llm> и
<https://pymupdf.readthedocs.io/en/latest/pymupdf4llm/>.

## Решение

### 1. Режим «Быстро» становится layout-aware

Новый адаптер в `backend/app/materials/parsers/` преобразует результат
`PyMuPDF4LLM` в существующий единый контракт `ParsedPage`:

- `markdown` — готовый Markdown страницы;
- `plain_text` — тот же текст без разметки для поиска и детерминированных
  механизмов;
- `elements` — `heading`, `paragraph`, `list`, `table`, `formula` или `image` с
  нормализованным bbox и уровнем структуры;
- `quality = native` для исправного текстового слоя;
- диагностические сигналы для таблиц, формул и деградированной структуры.

Для текстового PDF layout-разбор вызывается без встроенного OCR. Сканированные
страницы по-прежнему идут в существующий PP-OCRv5. Это не второй OCR-движок и не
скрытая отправка наружу: режим «Быстро» остаётся локальным CPU-маршрутом, но
использует правильный document parser для страниц с текстовым слоем.

Воркер, ревизии страниц, перенос ручных привязок, индексация и хранение картинок
не меняют границ. Адаптер обязан работать постранично, чтобы сохранились
чекпоинты и возобновление фоновой задачи.

Если layout-библиотека не может разобрать страницу, задача не должна молча
возвращаться к старой эвристике для всего документа. Страница получает точную
диагностику и безопасный fallback текущего native-разбора; в интерфейсе видно,
что структура этой страницы деградировала.

### 2. Импорт списка вопросов учитывает серии номеров

Для плоского списка вопросы выделяются не по правилу «любая непустая строка», а
по сериям маркеров:

1. текст до первой нумерованной или маркированной позиции считается вводной
   частью, а не вопросом;
2. непрерывная серия `1, 2, 3, …` образует основной список;
3. сброс номера создаёт новую серию, а не продолжает предыдущую;
4. `GoalPassport.expected_item_count`, если задан, проверяет выбор серии;
5. если ровно одна серия совпадает с ожидаемым числом, она выбирается;
6. если подходящих серий несколько, есть пропуск или ожидаемое число расходится,
   импорт ничего не обрезает молча — предпросмотр показывает конфликт.

Ненумерованный текст после выбранного маркера остаётся продолжением формулировки.
Форматы с билетами и отдельными секциями вопросов/задач сохраняют свои правила;
серии определяются внутри каждой секции.

Для текущего файла результатом становится серия `1…16`; вводная строка и
отдельная хвостовая серия `1…3` не попадают в Программу. В предупреждении видны
количество пропущенных вводных строк и дополнительные серии, но их содержимое не
теряется из исходного Материала.

### 3. Файл ответов связывается сначала по проверенному номеру

Существующее exact/fuzzy-сопоставление заголовков сохраняется для файлов, где
формулировки действительно повторяют вопросы. Добавляется второй,
детерминированный путь для другого формата заголовков.

Из блоков документа собираются кандидаты верхнего уровня. Главный заголовок
ответа должен:

- иметь номер;
- принадлежать одной устойчивой серии верхнего уровня;
- идти в возрастающем порядке;
- не повторять номер внутри выбранной серии.

Подзаголовки, вложенные нумерованные пункты, списки и таблицы не открывают новый
ответ. Они включаются в тело текущего раздела до следующего главного номера.

Номер ответа сопоставляется с номером вопроса в текущем порядке Программы. Для
текущего проекта проверенная общая часть — `1…16`; последующие ответы файла не
считаются ошибкой и остаются несвязанными, потому что соответствующих вопросов в
Программе нет.

Номер используется автоматически только при выполнении всех защит:

- серия начинается с 1 или явно совпадает с диапазоном Программы;
- общая часть непрерывна;
- число найденных разделов не меньше числа связываемых вопросов;
- текущий порядок вопросов однозначен;
- заголовочное сходство не указывает на явное противоречие.

При пропуске, дубле, перестановке или двух равноправных сериях автосвязь по номеру
не выполняется. Интерфейс показывает ограниченный отчёт и оставляет ручной выбор;
неверная тихая связь хуже несвязанного ответа.

Для происхождения добавляется явный метод `numbered_order` в
`ReferenceAnswerMatchMethod`. Такой эталон остаётся в состоянии «требует
проверки», пока пользователь его не подтвердил. Для нового enum-значения нужна
миграция существующего CHECK-ограничения; отдельная таблица не создаётся.

Повторный запуск остаётся идемпотентным: автоматически созданные связи этого
файла пересобираются, ручные привязки и подтверждённые или исправленные ответы не
перезаписываются.

### 4. Вкладка «Обработка»

Готовый файл больше не показывает одинокую кнопку «Разобрать заново». На её месте
постоянный раздел `OCR`:

- выбранный режим `Быстро · локально`;
- пояснение, что текстовый слой разбирается без распознавания, а страницы-сканы
  проходят PP-OCRv5;
- число страниц, сканов, `ocr_low`, таблиц и нарушений структуры;
- основное действие `Запустить заново`;
- остальные режимы видимы, но недоступны с причинами из `PLAN.md`.

Режимы сверх «Быстро» не оживляются этой задачей. «Учебник», «Облако»,
«Максимум» и «Эксперт» остаются отложенными, как зафиксировано в текущем плане.

Для файла ответов раздел переименовывается из «Эталонные ответы» в `Ответы из
файла`. Тексты действий:

- `Связать с вопросами` вместо `Привязать заново`;
- `Импортировать ответы текстом` вместо `Импортировать эталоны текстом`.

Пояснение сообщает порядок механизма: номер → точный заголовок → близкая
формулировка → ручной выбор. Итоговый отчёт различает связанные вопросы,
дополнительные ответы вне Программы и неоднозначные разделы; сотни подпунктов не
показываются как сотни «не найденных вопросов».

Это согласованное пользователем изменение состава вкладки относительно текущей
живой реализации. Причина фиксируется также в
`docs/ui/stage-1-interface-baseline.md`, а фактический контракт — в
`docs/architecture/materials-viewer-and-answers-autolink.md` и `SCREENS.md`.

## Ошибки и безопасное поведение

- Сбой одной страницы сохраняет уже готовые чекпоинты и указывает номер страницы.
- Отсутствие layout-зависимости — ошибка конфигурации установки, а не пустой
  успешный результат.
- Переразбор создаёт новую ревизию и переносит привязки существующим механизмом.
- Изменившаяся Программа требует нового отчёта связи; старый порядок не
  переиспользуется вслепую.
- Ответ вне диапазона Программы нейтрален: это содержимое файла, а не дефект.
- Подтверждённый или вручную исправленный эталон автоматика не перезаписывает.
- Исходный PDF никогда не изменяется.

## Проверка

### Автоматические сценарии

1. PDF-фикстура с заголовками, вложенным списком, двумя колонками и таблицей
   превращается в Markdown с тем же порядком и элементом `table`.
2. Список `вводная строка → 1…16 → отдельная серия 1…3` даёт 16 вопросов и
   предупреждение о пропущенных частях.
3. Несколько подходящих серий при одинаковом ожидаемом числе блокируют импорт.
4. Файл ответов с 16 главными разделами и множеством вложенных нумерованных
   подпунктов создаёт 16 разделов, а не сотни.
5. Нарушенная серия `1, 2, 4` не связывается по порядку.
6. `numbered_order` создаёт непроверенный эталон, повторный запуск идемпотентен,
   подтверждённый или ручной ответ сохраняется.
7. Старые exact/fuzzy/resolved-title сценарии продолжают проходить.

Проверки: профильные pytest-тесты материалов, сегментации, импорта и
автопривязки; `python backend/scripts/check_stage5.py`,
`python backend/scripts/check_manual_binding.py`, `python -m ruff check .`,
`npm run typecheck`, `npm run build` и `npm run lint`.

### Проверка на текущем проекте

После переразбора проверяются только агрегаты и пользовательский просмотр:

- таблицы представлены Markdown-таблицами;
- вложенные пункты остаются списками;
- число главных разделов ответа соответствует проверенной номерной серии;
- с вопросами связываются только номера `1…16`;
- вводная строка и хвостовая серия списка вопросов не создают узлы;
- исходный файл доступен без изменений.

Файл пользователя не добавляется в git и не становится тестовой фикстурой.

### Визуальная проверка

После `docker compose restart web` проверяются светлая и тёмная темы, состояния
готового файла, фоновой обработки, ошибки и недоступных режимов. В браузере
проходится сценарий: открыть файл → «Обработка» → увидеть `OCR` → запустить
`Быстро` → открыть текст → `Связать с вопросами` → увидеть итог для 16 вопросов.

## Надёжность и пределы решения

Layout-разбор существенно надёжнее текущих эвристик для цифровых PDF с таблицами,
колонками и оформленными списками, потому что использует готовую модель структуры,
а не объявляет любой номер заголовком. Однако PDF не хранит понятия «вопрос» и
«подпункт» как доменные сущности, поэтому стопроцентной гарантии для произвольного
файла нет.

Связь по номеру надёжна при совпадающем порядке и непрерывной нумерации. Защиты
намеренно уменьшают автоматическое покрытие ради отсутствия тихих ошибок. Если
автор файла переставил ответы, повторил номер, пропустил вопрос или использовал
две равноправные серии, система остановит автоматическую связь и попросит выбор.

После реализации пользователю отдельно передаётся короткая оценка надёжности:
какие признаки проверяются автоматически, какие файлы проходят хорошо и в каких
случаях результат обязательно просматривать вручную.
