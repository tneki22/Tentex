# Подготовительная вертикаль. Лексический поиск и ручная привязка

Вертикаль даёт первую настоящую связь между программой и материалом — руками, без единого вызова модели. Пользователь листает методичку, отмечает, какой кусок текста относится к какому вопросу экзамена, и видит эту связь с обеих сторон: в Материалах у фрагмента и в Рабочей области у вопроса. Лексический поиск (FTS5/BM25) — движок, который делает вторую сторону возможной: найти кандидатов по формулировке вопроса, а не листать 200 страниц глазами.

План: `docs/superpowers/plans/2026-08-11-pre-stage-6-search-and-manual-binding.md`.

## Граница вертикали

**Входит:** сущность привязки, FTS5-индекс с русской лемматизацией, поиск по материалам проекта, ручная привязка от материала к вопросу и от вопроса к материалу через поиск, снятие с отменой, счётчик «сколько фрагментов у вопроса», перенос привязок при коррекции текста страницы, предупреждение при удалении материала.

**Не входит и не имитируется:** проход 2, автоматические привязки, очередь предложений (этап 8); метрика «покрытие материала» и «Неразобранное» (этап 8, без прохода 2 считать нечего); векторный поиск, `sqlite-vec`, эмбеддинги, RRF (этап 6); поиск внешних источников (этап 10); учебниковый раздел «Привязки» (спроектирован эскизом в `SCREENS.md`, реализация — после этапа 7); «Настройки программы у проекта» — отдельная следующая задача.

Только экзаменационный проект. Учебниковая ветка получает эскиз отдельного раздела `/projects/:projectId/bindings`, но не реализацию: в учебнике связывается программа с учебником целиком, а не ответ с вопросом — это работа над деревом, а не над документом одного файла, и своей программы у учебника пока нет (этап 7).

## Морфология и лексикон

`backend/app/materials/lexicon.py`: `normalize` (токены — буквы и цифры, нижний регистр), `tokenize_with_positions` (то же с позициями в исходном тексте, для подсветки), `lemmatize` (pymorphy3 для кириллицы, латиница и числа — как есть, `ё` сведено к `е`), `index_text` (леммы через пробел для колонки индекса), `query_terms` (леммы запроса без стоп-слов).

`MorphAnalyzer()` создаётся один раз на процесс (глобальный singleton, ленивая инициализация): конструктор стоит около секунды и мегабайты памяти. Разбор отдельного токена кешируется `functools.lru_cache`. Короткий собственный список стоп-слов, без внешних наборов. Зависимость `pymorphy3` + `pymorphy3-dicts-ru` зафиксирована в §23 требований и добавлена в `requirements.txt`.

## Поисковый индекс

`fragment_search` — contentless-таблица FTS5 (`text`, `lemmas`, `fragment_id UNINDEXED`, `material_id UNINDEXED`, `tokenize = "unicode61 remove_diacritics 2"`) плюс обычная таблица-спутник `fragment_search_map(fragment_id, material_id, rowid)` для адресного удаления строк по материалу. `MATCH` идёт по колонке `lemmas`; ранжирование — `bm25(fragment_search, 0.0, 1.0)` (вес только у лемм). `fragment_id`/`material_id` внутри индекса и таблицы-спутника хранятся как `UUID.hex` (32 символа без дефисов) — тот же формат, в котором SQLAlchemy `Uuid` хранит эти колонки в основных таблицах, поэтому конвертация в обе стороны детерминирована.

`backend/app/bindings/search.py`:

- `reindex_material(session, material_id)` — удаляет старые строки материала и пишет заново по текущей активной ревизии (`MaterialPage.revision == Material.active_parse_revision`). Вызывается в **той же транзакции**, что и запись фрагментов: из `materials.worker._finish` (первый разбор) и `materials.service.update_page_text` (коррекция), а также отдельной командой `POST /materials/{id}/reindex`;
- `delete_material_index(session, material_id)` — вызывается из `materials.service.delete_library_material` перед физическим удалением материала;
- `search_fragments(session, material_ids, query, limit=50)` — лемматизирует запрос, ищет топ-N по `bm25`, догружает метаданные (страница, блок, материал) обычным SQLAlchemy-запросом, группирует соседние совпадения одного блока в один результат (диапазон страниц, объединённый список `fragment_ids`), подсвечивает совпадения на сервере по позициям токенов в исходном `text` — `snippet()` здесь не подходит, потому что `MATCH` идёт по `lemmas`, а показывать читателю нужно исходный текст.

Реальный замер: материал 169 страниц (`Exam-NDB/Подготовка к экзамену НБД.pdf`) разбирается за ~4 с; поиск после прогрева процесса укладывается в 16–170 мс на запрос — с запасом от бюджета NFR-4 (300 мс).

## Сущность привязки

`Binding` (`backend/app/models.py`), таблица `bindings`:

| Поле | Смысл |
| --- | --- |
| `project_id`, `program_node_id` | составной внешний ключ на `(ProgramNode.project_id, ProgramNode.id)`, каскад при удалении узла |
| `fragment_id` | внешний ключ на `MaterialFragment`, каскад при удалении (== при физическом удалении материала) |
| `material_id` | денормализация: фильтр «привязки этого файла» без трёх join, каскад при удалении материала |
| `block_id` | заполняется только при привязке «блок целиком»; для точечной привязки — `null` |
| `status` | `manual` · `confirmed` · `machine` · `removed` · `orphaned` — только `manual` и `removed`/`orphaned` создаются в этой вертикали |
| `mechanism` | `manual` (выделение в документе) · `search` (принята из результатов поиска) · `pass_two` (этап 8, не создаётся) |

`UniqueConstraint(project_id, program_node_id, fragment_id)`: повторный запрос на существующую пару идемпотентен и возвращает ту же строку; запрос на строку в статусе `removed` — оживляет её (`status = manual`), не создавая вторую запись.

`status` и `mechanism` — разные оси: `status` описывает жизненный цикл (активна/снята/осиротела), `mechanism` — происхождение (вручную или из поиска). Обе ручные привязки этой вертикали получают `status = manual` независимо от `mechanism`.

## Сервис и отмена

`backend/app/bindings/service.py`:

- `create_bindings` — принимает либо `fragment_ids[]`, либо `block_id` (ровно один источник, проверяется `model_validator`); при `block_id` резолвит все фрагменты блока на сервере. Проверяет: узел — учебный (`topic`/`subpoint`) и не архивный, проект — активный экзаменационный, каждый фрагмент/блок принадлежит материалу, подключённому к проекту, и находится в активной ревизии. Одно действие — одна запись в общем журнале `ProjectActionLog` (Р1 плана): undo снимает всю пачку сразу;
- `remove_binding` / `restore_binding` — мягкое снятие и явное возвращение, каждое тоже пишет запись в журнал;
- `apply_undo(session, project_id, action_type, data)` — вызывается из `projects.program.undo_last_project_action` для типов действий `binding_create` и `binding_remove`. Симметрично просто: отмена `binding_create` переводит перечисленные в `inverse_data` привязки в `removed`, отмена `binding_remove` — обратно в `manual`. Новых механизмов undo не появилось: используется тот же `POST /api/projects/{id}/actions/undo`, что и для узлов программы;
- `list_bindings` / `get_summary` — читающие запросы для вкладки «Привязки» и вкладки «Источники» Рабочей области; `get_summary` агрегирует по узлу число активных привязок, число материалов-источников и худшее качество (`native < ocr < ocr_low`) — тот же `NodeBindingSummary`, что выводится в инспекторе Программы.

Бэкенд-функции, которые сами читают из БД, не оборачиваются в `with session.begin()`, если могут быть вызваны после другого чтения в той же сессии в рамках одного запроса (например, `material_delete_preview` сначала читает материал, затем зовёт `binding_count_for_material` и `affected_projects_preview`) — SQLAlchemy 2.0 иначе бросает `InvalidRequestError` на вложенный `begin()`. Пишущие операции (`create_bindings`, `remove_binding`, `restore_binding`, `reindex_material`) остаются самостоятельными транзакциями, как и в остальном бэкенде.

## Перенос при коррекции страницы (Р6)

`materials.service.update_page_text` пересобирает фрагменты и блоки **всего материала** заново при правке текста одной страницы (так работал конвейер уже на этапе 5: `build_blocks` учитывает заголовки соседних страниц). Поэтому перенос привязок затрагивает все страницы материала, не только отредактированную.

`bindings.service.transfer_bindings_on_revision(session, material_id, fragments_by_page_old, fragments_by_page_new)`:

1. для каждой страницы — точное совпадение нормализованного текста (`" ".join(text.split())`) между старыми и новыми фрагментами;
2. для фрагментов, оставшихся без пары: если общее число фрагментов на странице не изменилось — совпадение по порядковому номеру;
3. что осталось без пары — привязка получает `status = orphaned`, `fragment_id` не трогается (старый фрагмент остаётся в базе, FK валиден).

Не изменившиеся страницы совпадают по тексту 1:1 всегда — иначе изменился бы весь конвейер разбора, а не только правка. Ответ `PUT .../pages/{n}` — `PageCorrectionRead {page, transferred_bindings, orphaned_binding_ids}`; фронтенд показывает оба числа в уведомлении, а список `orphaned` доступен через `GET /bindings?status=orphaned`.

## Предупреждение при удалении (Р7)

`GET /api/materials/{id}/delete-preview` расширен полями `binding_count` (активные привязки материала во всех проектах) и `affected_projects[]` — для каждого проекта, где материал используется, список узлов, которые **потеряют весь материал**, если этот файл удалить (т.е. других активных привязок к этим узлам от других материалов нет). `DELETE /api/projects/{id}/materials/{materialId}` (отвязка от одного проекта, не физическое удаление) использует ту же вычислительную функцию `affected_projects_preview` и дополнительно каскадно убирает привязки именно этого проекта (`delete_project_material_bindings`) — привязки других проектов, использующих тот же файл, не затрагиваются.

## HTTP API

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/projects/{id}/search?q=&material_id=&node_id=&limit=` | лексический поиск по активным ревизиям материалов проекта; `already_bound` при переданном `node_id` |
| `GET /api/projects/{id}/bindings?node_id=&material_id=&page=&status=` | список привязок с раскрытым фрагментом; без `status` — только активные |
| `GET /api/projects/{id}/bindings/summary` | `NodeBindingSummary[]` по всем узлам с активными привязками |
| `POST /api/projects/{id}/bindings` | создать пачкой (`fragment_ids[]`) или блоком (`block_id`) |
| `DELETE /api/projects/{id}/bindings/{binding_id}` | мягкое снятие |
| `POST /api/projects/{id}/bindings/{binding_id}/restore` | вернуть снятую |
| `POST /api/projects/{id}/materials/{material_id}/reindex` | пересобрать индекс материала вручную |

Коды ошибок: `bindings_require_exam_project`, `binding_requires_study_node`, `material_not_in_project`, `block_revision_stale`, `fragment_revision_stale`, `binding_already_removed`, `binding_not_removed`, `binding_no_fragments` — все со стандартным конвертом `ProjectDomainError`.

## Интерфейс

**Материалы** (`frontend/src/screens/Materials.tsx`): правая панель — три вкладки «Привязки» · «Обработка» · «Файл» (общий набор для любого файла; «Вопросы» и «Ответы» из целевого дизайна сюда не возвращаются — у них есть «Вопросы экзамена» и «Карта покрытия»). Вкладка «Привязки»: три нейтральных числа, строка активного вопроса со стрелками и диалогом выбора (поиск по дереву программы), переключатель списка «Страница»/«Документ», карточка выбранного фрагмента с действиями. Режим привязки в документе (кнопка + `B`): клик по фрагменту привязывает/снимает, `Shift+клик` — диапазон, `Enter` — привязать выбранное, `Ctrl+Z` — отменить последнее через общий журнал, `Esc` — снять выделение/выйти из режима; у заголовка блока — «Привязать блок целиком» (или «Привязать всё равно» для служебного блока). Привязанный фрагмент получает подложку, линию слева и пин независимо от режима.

**Рабочая область** (`ProjectWorkspace.tsx`), вкладка «Источники» экзамена (до 01.09.2026 называлась «Материал»): список привязанных фрагментов с переходом в Материалы на нужную страницу и фрагмент (`?page=&focus=`), «Это не по теме»; явное поле поиска, предзаполненное формулировкой темы, без автозапуска; результаты с подсветкой и кнопкой «Привязать», уже привязанные — помечены. Честное пустое состояние «Для этого вопроса материал ещё не привязан». Привязки с `mechanism: "answers_file"` (см. `docs/architecture/materials-viewer-and-answers-autolink.md`) в этот список не попадают — они принадлежат файлу эталонных ответов и показаны во вкладке «Ответ».

**Программа** (`Program.tsx`): в «Что связано» вместо заглушки — реальное число фрагментов и файлов или нейтральное «Материал не привязан», ссылка «Привязки в материалах».
