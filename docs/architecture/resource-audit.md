# Комплексная проверка ресурсов — 30.09.2026

Продолжение [первого аудита](resource-usage.md), ветка `codex/resource-usage`.
Windows/Docker Desktop; основная установка — 54 материала, 4722 страницы,
активный E5-индекс 7406 кусков. Мутации разбора и сборки индекса выполнялись в
изолированном Docker-проекте `tentex-resource-audit`. Основная БД использовалась
для чтений и PDF-оценки. Образ предыдущего коммита `1181f12` работал отдельно с
SQLite backup и исходниками/моделями, смонтированными только для чтения.

## Изменения

- Компактная строка в «Состоянии»: ОЗУ/CPU API, worker и retrieval-model,
  включая дочерние процессы. Сбор cgroup не запускает модели, не обращается к
  Docker socket и не пишет в SQLite. Границы суммы и разбивка — в подсказке.
  [Контракт](system-status.md#ресурсы-серверов).
- При загрузке файла API больше не обходит PDF в event loop. В дочерний процесс
  передаётся путь, а назад — счётчики и оглавление. PDF читается из локальной
  временной копии. Печатное оглавление также вычисляется там, результат остаётся
  в ограниченном кэше. Процесс закрывается после 60 с простоя и вместе с lifespan.
- `native.inspect` явно закрывает PDF; проверка UTF-8 у TXT/MD потоковая.
- Просмотр сохраняет прежние три открытых PDF при листании, затем отпускает их
  после 600 с простоя (`TENTEX_PDF_PREVIEW_IDLE_SECONDS`). Активный рендер владеет
  собственной ссылкой, поэтому таймер не закрывает документ посреди работы.
  Готовые растры на диске продолжают открываться без повторного рендера.
- `retrieval_index`/`retrieval_exhaustive` занимают прежние AI-слоты, но работают
  в освобождаемом пуле процессов. Большие снимки корпуса не остаются в supervisor.
  Таймер тот же, что у local/cloud: штатно 600 с. Остальные AI-задачи — в потоках.
- Холодная загрузка retrieval-моделей объединена: `lru_cache` сам допускает
  одновременные вычисления одного промаха. Замок находится снаружи кэшей и
  защищает только получение/загрузку модели, inference остаётся параллельным.
- Инвентарь изображений читает только нужные колонки страниц, получает ID
  фрагментов одним запросом и ищет только колонтитулы-картинки. Сопоставление
  всех текстовых строк ему не нужно. Полный поиск колонтитулов также использует
  верхние оценки `SequenceMatcher` для безопасного отсева перед точным ratio;
  порог, геометрия и итоговые группы сохраняются.
- В Settings удалены дублирующая PDF-настройка и неиспользуемый
  `heavy_process_idle_seconds`; действующие таймеры описаны выше и в первом аудите.

Профиль старого инвентаря показал 1,27 млн вызовов `_matches`, из них 222 тыс.
`SequenceMatcher.ratio`. Почти всё CPU уходило на текстовые колонтитулы.
Сам профилировщик увеличивал время до ~238 с; обычный HTTP-запрос занимал ~85 с.
Это отдельная от PDF-оценки причина нагрузки, а не утечка моделей OCR.

Широкий проход включал сводки проектов, материалы, покрытие, подготовку,
крупные страницы, внутридокументный поиск и инвентарь изображений: 178 сочетаний
маршрута/контрольного запроса до и после. Ответы 409/422 для неприменимых режимов
и 404 у неразобранной страницы были одинаковы. В раннем перечне были ошибочные
`/program` и `/lessons`; чтение программы исправлено на карточку проекта,
а уроков — на `/lessons/overview`
в воспроизводимом скрипте и исключены из сравнения задержек. 500-х не получено.
Финальные чтения: 144 успешных маршрута и 31 ответ 409/422 либо отсутствие
неразобранной страницы; карточки всех 15 проектов также проверены отдельно.

Поиск сохранил первые места/locators. Локальные lexical, semantic и hybrid
стратегии отдельно прогнаны на этих трёх запросах; повторная выдача стабильна.
Точность векторов в первом аудите не менялась; текущая правка загрузчика не
меняет pooling, dtype, нормализацию или код вычислений.

Замер не доказывает одинаковую задержку всех операций: некоторые чтения стали
медленнее в этой выборке, в частности большая карточка на ~0,31 с. У двух API
разные файлы БД на bind mount, разные прогретые страницы и фоновый опрос.
Показатели зависят от Docker/Windows I/O; это не чистый микробенчмарк изменённой
функции. Существенное ускорение инвентаря и стабильность поиска подтверждены
прямыми результатами. Жёсткого ограничения RAM, уменьшения числа слотов и
снижения качества модели не вводилось.

Дополнительный контроль двух API на **одном и том же SQLite backup**, с теми же
mount и восемью чередующимися повторами, убрал разницу большой карточки:
1740,5 → 1744,5 мс (+0,2%). Материалы 61,0 → 58,1 мс, задачи 48,3 → 44,9 мс,
coverage/issues 409,9 → 390,2 мс, состояние 190,1 → 204,1 мс,
подготовка 804,7 → 844,2 мс. Поиск 193,4/204,6/232,5 → 183,0/208,8/209,0 мс,
первые locators те же. Оставшиеся различия невелики, но это по-прежнему замер
на одной машине с фоновой нагрузкой, а не гарантия для всех сценариев.

## Разбор файлов и освобождение памяти

Настоящие задачи worker, без платных вызовов:

| Источник | Разбор до готового состояния, с |
| --- | ---: |
| TXT | 5,98 |
| Markdown | 17,50 |
| DOCX, 100 абзацев | 6,56 |
| PDF с текстом, 3 страницы из реальной книги | 9,31 |
| PDF-скан, 2 страницы | 62,48 |
| JPEG-скан | 22,56 |
| Typst с формулой | 7,22 |
| WAV с синтезированной русской речью, локальный Whisper tiny | 9,35 |

Все восемь задач завершились; максимальный health во время этих разборов —
около 80 мс. Для облачного конвейера отдельно выполнены 36 сочетаний:
PDF с текстом / PDF-скан / DOCX / JPEG × `economy/auto/page` ×
`skip/text/describe`. Ответ внешнего recognizer подменён; штатный конвейер,
нативное извлечение и подготовка вырезов настоящие. Это проверяет маршрутизацию,
процессы и память, но не качество конкретного облачного провайдера.

Таймер процессов в изолированном контуре сокращён до 5 с, в основной установке
оставлен 600 с. Через простой пулы закрылись, крупные дочерние PID исчезли.
Во время OCR/native обработки память временно возрастает примерно до 1–2 ГиБ.
Проверены также ошибка, отмена, пауза/продолжение и публикация ревизии тестами.

Создан настоящий локальный E5-индекс на восьми тестовых материалах: 33 куска,
полный запуск 29,38 с, обработчик внутри процесса ~22,8 с. После выгрузки
worker занял ~142 МиБ. E5 inference в тестовом режиме выгрузился; счётчики
загруженных моделей обнулились. Qwen3 Reranker 0.6B реально ранжировал два
места за 10,31 с с холодной загрузкой, релевантное получило 0,999, нерелевантное
~0,000032; после простоя `loaded_rerankers=0`.

Освобождение PID и `docker stats` не обязаны совпасть мгновенно: Linux оставляет
файловый кэш, в том числе активные страницы файлов, которые Docker включает в
working set. В облачном stress-процессе было ~574 МиБ до, пик ~1082 МиБ,
~615 МиБ после, при `pool.loaded=false`. Это не означает оставшиеся веса в
живом Python-процессе. Нельзя обещать нулевую память после работы: остаются
supervisor, ограниченные кэши БД/словаря и намеренно прогретый поиск.

После всей серии основной контур держался примерно в диапазоне 1,35–1,5 ГиБ
с прогретой E5. Разовый пик и память браузера/VM в эту цифру не входят.
При завершении аудита пользователь запустил облачный разбор основной книги;
замер в это время не считается idle, работающий worker не перезапускался.
В ветке появился отдельный коммит `41a54d9` обработки визуальных областей PDF;
финальный точечный набор включает его тесты вместе с осмотром и просмотрщиком.

## Проверки и обнаруженные старые проблемы

- Полный backend-прогон по явному запросу: **1076 passed, 2 failed**, ~15 минут.
- Оба падения повторены отдельно на текущем дереве и на образе `1181f12`:
  `test_exam_chat_turns.py::test_budget_beyond_the_model_window_is_refused`
  (явный слишком большой контекст не отклоняется) и
  `test_study_tasks.py::test_open_answer_waits_without_models_then_judge_checks`
  (`ai_judge_invalid_source`, ответ фикстуры не подтверждён источником).
  Они не вызваны ресурсной правкой. Для подготовки к GitHub это отдельный
  незакрытый пункт; тесты не ослаблены и ошибки не скрыты.
- После правок: 201 затронутая проверка материалов, очереди, retrieval,
  SQLite contention и состояния; 53 проверки изображений/worker/управления;
  финальные 9 проверок колонтитулов — прошли. Эти наборы пересекаются.
- Новые счётчики, spawn осмотра, кэш просмотра и совместная холодная загрузка:
  18 точечных проверок прошли. Ruff по изменённым файлам — прошёл.
- После отдельной PDF-правки `41a54d9`: финальные 58 проверок осмотра,
  оглавления, кэша просмотра, метрик, загрузчика моделей и PDF-областей прошли.
- Docker build (TypeScript + Vite включены) — прошёл. Панель проверена в
  Playwright, свежая навигация без ошибок console; светлая и тёмная темы.

Это не полный E2E всех пользовательских сценариев: не было платных облачных
вызовов, живого полного разбора 1003 страниц и многосуточного soak. Все сложные
подсистемы проверены тестами, перечисленные тяжёлые пути — дополнительно живыми
замерами. Не следует выдавать это за гарантию любого размера корпуса/нагрузки.

## Дальнейшая оптимизация поиска

Основная RAM — веса и runtime E5 (~0,7–0,8 ГиБ), а не векторы 7406 кусков
(~22,75 МБ). Сейчас оставлен прогрев, поскольку повторная холодная загрузка
стоит секунд. Первая очередь дальнейшего исследования:

1. ONNX float32, затем динамический INT8 экспорт E5; проверить RAM, холодный
   старт, throughput и Recall/MRR на существующем контрольном корпусе.
   [Sentence Transformers описывает ONNX/quantization](https://www.sbert.net/docs/sentence_transformer/usage/efficiency.html),
   [ONNX Runtime — ограничения и проверку точности](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html).
   Ожидается уменьшение весов/runtime, но выигрыш на этой машине и сохранение
   качества пока не измерены. В этой правке формат и точность не менялись.
2. Закрепить только активные embedding/reranker; освобождать экспериментальные
   модели после benchmark/смены профиля. Сейчас ограничены отдельные LRU, но
   два вида backend могут держать несколько наборов весов одновременно.
3. Маленький кэш query-векторов по версии профиля, шаблону, pooling и тексту
   запроса — сокращает повторный inference без кэширования устаревшей выдачи.
   Это прежде всего CPU/latency, а не освобождение весов.
4. Подобрать размер batch и число CPU-потоков на больших текстах. Пакет 512
   разрешён runtime и может дать большой пик активаций; текущие профили обычно
   шлют 32, Qwen CPU — 4. Не снижать общий throughput без измерения.

Менять точный vector search или квантизировать сам индекс первым шагом невыгодно:
его доля RAM мала, а изменение порогов/выдачи потребует отдельной проверки.
Полный предпросмотр колонтитулов большой книги тоже остаётся кандидатом для
дальнейшего ускорения; инвентарь больше не платит за него.

## Воспроизводимость

```sh
python backend/scripts/profile_resources.py --deep --repeats 3 --output output/resource-usage/profile.json
python backend/scripts/profile_resources.py --query "нормальная форма" --strategy lexical --strategy semantic --strategy hybrid
docker stats --no-stream
```

Логи и метрики этой машины — в игнорируемом `output/resource-usage/`:
`full-tests.log`, `final-targeted.log`, `images-tests.log`, `pdf-stress.json`,
`live-files.json`, `cloud-workloads.json`, `live-index.json`, `reranker-live.log`,
`controlled-compare.json`, `identical-db-compare.json`, `inventory-comparison.txt`.
Локальные фикстуры и SQLite backup не включены в Git. Тестовые контейнеры
и временный образ предыдущей версии удалены после проверки.
