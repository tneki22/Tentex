# Память и контейнерный запуск

Продолжение аудита: тяжёлые запросы, режимы файлов, строка ресурсов и дальнейшая
оптимизация поиска — [`resource-audit.md`](resource-audit.md).

## Измерения 30.09.2026

Проверялось на Windows/Docker Desktop, на основной SQLite и файловом хранилище.
В Библиотеке 54 материала и 4722 страницы; активный E5-индекс — 7406 кусков.
Цифры ниже — `docker stats` после работы и в простое, а не пик обработки или
вся память Docker Desktop/браузера. Это замер одной машины, не минимальные
системные требования.

| Сервис | До правки, МиБ | После работы и простоя, МиБ |
| --- | ---: | ---: |
| API | ~1260 | ~330–390 |
| worker | ~914 | ~139–160 |
| retrieval-model с прогретой E5 | ~831 | ~718–831 |
| web | ~250 | ~3 |
| SearXNG | ~183 | ~183 |
| Всего | ~3,36 ГиБ | ~1,35–1,53 ГиБ |

Экономия в этом сценарии — около 55–60%. После новой тяжёлой задачи worker
сохраняет прогрев десять минут; его уменьшение не обязано быть мгновенным.

Сравнение со старым `tentex-fresh` оказалось некорректным: его API был
`unhealthy`, старт падал с `FileExistsError: /data`, worker был остановлен.
Создан отдельный временный чистый контур с исправной пустой БД: все пять
сервисов работали и занимали суммарно ~550 МиБ без загруженных моделей.
Его тестовые данные отделены от основной установки; старый Fresh не менялся.

Разница рабочего пустого и заполненного контура теперь объясняется прежде
всего прогретой моделью, снимком индекса и кэшами SQLite. Само наличие
установленных моделей на диске не загружает их в RAM.

## Что изменено

Обычный `docker compose up --build -d` отдаёт готовый фронтенд через nginx.
Node/Vite, наблюдение за файлами и автоперезагрузка API включаются отдельно:

```sh
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build
```

nginx сохраняет SPA-маршруты, `/api`, загрузки файлов, передачу SSE без
буферизации и повторное разрешение адреса API через Docker DNS. После изменения
фронтенда штатную сборку обновляют `docker compose up -d --build web`.

До правки API-контейнер держал три крупных Python-процесса с RSS примерно
505/395/496 МиБ. Режим `--reload` и постоянный ProcessPoolExecutor диагностики
PDF мешали освобождению памяти после работы/перезагрузок. Штатный запуск
убирает reloader; диагностический процесс закрывается через минуту простоя и
при завершении lifespan. Небольшой результат оценки остаётся в LRU-кэше API:
повторный запрос не будит процесс.

`local` и `cloud` worker теперь используют ленивые дочерние процессы. Серия
задач переиспользует OCR/разметчик, затем весь процесс завершается после
простоя. Это освобождает и веса, и память импортированных нативных библиотек,
которую нельзя надёжно вернуть одним удалением Python-ссылки. В последующей
правке индексирование и исчерпывающий поиск также перенесены в освобождаемый
пул; остальные AI-задачи работают в потоках. Число слотов, checkpoint, lease/heartbeat, публикация
ревизии и восстановление задач не изменены. Проверка установки PaddleOCR
использует `find_spec`, не импортируя OCR ради наличия пакета.

`app/process_pool.py` не выгружает пул с работающими или ожидающими задачами.
Следующая задача отменяет таймер; callback отменённого таймера не может
закрыть новый пул. Сбой дочернего процесса возвращается через Future;
следующая задача получает новый пул, а очередь сохраняет восстановление
по истёкшему lease. Механизм использует штатные `spawn`, Future и shutdown
из [concurrent.futures](https://docs.python.org/3.13/library/concurrent.futures.html).

Общие соединения API теперь имеют кэш SQLite 16 МиБ вместо 64 МиБ. Отдельный
поисковый пул сохраняет 64 МиБ на соединение, оба размера настраиваются.
При пуле 8+2 предел постоянных кэшей снижен с 640 до 256 МиБ. Это бюджет,
не обязательно занятая память; временные overflow-соединения в него не входят.
WAL, mmap=0, число соединений и прогрев снимка retrieval не менялись.

## Почему модель поиска остаётся в памяти

У E5 холодная загрузка в этом окружении занимает около 15 секунд. Выгружать
её по умолчанию означало бы снова ждать при первом поиске после перерыва.
Поэтому штатный режим сохраняет прогретые веса и не добавляет отдельный
inference-процесс. Поиск и RAG продолжают пользоваться той же моделью.

Для машин с малой памятью доступна явная настройка выгрузки: положительное
`TENTEX_RETRIEVAL_MODEL_IDLE_SECONDS` переносит inference в ленивый дочерний
процесс, завершаемый по таймеру. HTTP-сервис остаётся доступным, `/health` не
загружает веса и не продлевает таймер. Первый поиск после выгрузки снова
требует холодной загрузки. После неё результаты не меняются.

SearXNG оставлен работающим: разница ~100 МиБ до запросов и ~183 МиБ после
запросов мала относительно моделей. Отключение сервиса или сокращение его
параллельности ухудшило бы поиск в интернете без подтверждённой выгоды.

| Переменная | По умолчанию | Назначение |
| --- | ---: | --- |
| `TENTEX_PDF_ESTIMATE_IDLE_SECONDS` | 60 | Выгрузка процесса диагностики PDF |
| `TENTEX_WORKER_PROCESS_IDLE_SECONDS` | 600 | Выгрузка local/cloud-пулов после завершения всей работы |
| `TENTEX_RETRIEVAL_MODEL_IDLE_SECONDS` | 0 | 0 — сохранять веса; положительное число — выгружать inference после простоя |
| `TENTEX_SQLITE_CACHE_KIB` | 16384 | Кэш обычного постоянного соединения API |
| `TENTEX_SQLITE_SEARCH_CACHE_KIB` | 65536 | Кэш поискового соединения |

Изменённые переменные окружения Compose применяются через
`docker compose up -d`, а не только `restart`.

## Проверки и ограничения

- 146 профильных pytest: процессы и их восстановление, оценка PDF, очередь,
  lease/SQLite-конкуренция, управление разбором, retrieval, подбор материалов,
  парсер PDF/OCR, фоновые предложения и состояние установки. Ruff по изменённым
  Python-файлам; конфигурации обычного и dev Compose валидны.
- Production-сборка frontend: TypeScript + Vite внутри Docker. Playwright CLI:
  Проекты, Библиотека, Параметры и просмотр проблемного PDF; проверка ошибок
  console. nginx отдельно передал первый SSE-кадр за ~31 мс при задержанном
  втором кадре и принял загрузку 2 МиБ, превышающую стандартный предел nginx.
- На основной БД три запроса hybrid возвращали те же top-5 chunk/material ID.
  Прогретые медианы до: 252/209/236 мс; после: примерно 170–210 мс.
  Векторы E5 совпали точно (`max abs diff = 0`). Это небольшой контрольный
  набор, не статистическое доказательство ускорения всех запросов.
- При сравнении общих кэшей 16/64 МиБ список материалов отвечал за ~74/86 мс,
  панель задач ~55/51 мс. Разброс коротких GET заметен; устойчивой общей
  регрессии на выбранных экранах не обнаружено. Поисковый кэш не уменьшался.
- Реальный PDF 46 страниц: первая оценка 24,7 с, повтор 0,03 с с тем же
  результатом; параллельный `/api/health` — медиана 19 мс, максимум 75 мс.
- Реальный скан на отдельной тестовой БД: локальный PP-OCRv5 завершил разбор
  за ~29 с. Рабочая память поднималась примерно до 1–2 ГиБ, после выгрузки
  стала ~160 МиБ. Для этой проверки таймер сокращён до 5 секунд; штатный
  таймер — 600. Модели взяты из существующего дискового кэша.
- Опциональный inference-процесс также проверен с таймером 5 секунд:
  частые healthcheck не помешали выгрузке, повторная загрузка сохранила векторы.

Рабочие пики OCR/PDF и нескольких одновременных задач остаются. Отдельные
процессы могут увеличивать рабочий пик по сравнению с общими библиотеками
одного процесса; жёсткие RAM-лимиты не вводились. После долгого перерыва
local/cloud снова импортируют библиотеки и прогревают OCR в фоне, поэтому
первый разбор получает стартовые накладные расходы. Серия задач сохраняет
прогрев. Браузерный heap, вся VM Docker Desktop, длительный soak-test и
платные вызовы облачных моделей этим прогоном не покрывались.

Повторный read-only замер:

```sh
docker stats --no-stream
python backend/scripts/profile_resources.py --query "нормальная форма" --output output/resources.json
```

`--query` явно включает поиск через настроенный backend embeddings, который
может быть локальным или внешним. Без него скрипт читает только обычные GET.
В отчёт попадают задержки и отпечатки выдачи, не тексты материалов или секреты.
