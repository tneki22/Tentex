# Этап 4. Эталонные ответы и офлайновый экзаменационный путь

Этап завершает первый полезный сценарий Tentex без файлов, OCR и моделей: пользователь создаёт экзаменационный проект, получает стабильную программу, добавляет эталонные ответы и читает их по вопросам в Рабочей области. Все данные живут в SQLite и переживают перезапуск.

## Граница этапа

В этап входят только экзаменационные эталоны. Загрузка материалов, страницы, фрагменты, блоки, OCR и привязки начинаются на этапе 5. «Карта эталонов» сейчас является утилитарным реестром ответов, а не окончательным дизайном будущей карты покрытия материалов.

Учебниковый проект не принимает эталоны через этот API: его честное состояние по-прежнему остаётся черновиком до появления материалов. Архивный или завершённый экзаменационный проект можно читать, но нельзя изменять.

## Данные и целостность

`ReferenceAnswer` хранится в таблице `reference_answers` и однозначно принадлежит паре `(project_id, program_node_id)`.

- составной внешний ключ ведёт на `(ProgramNode.project_id, ProgramNode.id)` и не позволяет связать ответ с узлом другого проекта;
- удаление узла каскадно удаляет его ответ, а удаление проекта удаляет его программу и ответы;
- текст непустой, `revision >= 0`;
- `origin_kind`: `manual` или `import`;
- `match_method`: `manual` или `exact_title`;
- `matched_title` хранит формулировку, по которой импорт связал ответ с узлом;
- `is_confirmed` отделяет автоматически найденную связь от принятой пользователем;
- `is_active` реализует мягкое удаление ответа и позволяет безопасно восстановить слот;
- `revision` защищает запись от потерянного обновления в двух вкладках.

Ответ связан именно со стабильным `ProgramNode.id`: перемещение узла не влияет на связь. Если после точного импорта пользователь переименовал вопрос, статус становится `needs_review`, пока связь не будет подтверждена снова. Ручной ответ не зависит от формулировки.

## Статусы ответа

| Статус | Смысл |
| --- | --- |
| `missing` | активного ответа нет |
| `auto_matched` | импорт точно совпал с текущим заголовком, пользователь ещё не подтверждал связь |
| `confirmed` | импортированная связь подтверждена и заголовок с тех пор не менялся |
| `needs_review` | подтверждённый или автоматически найденный заголовок больше не совпадает с текущим |
| `manual` | ответ добавлен или изменён вручную |

Статус вычисляется из канонических полей ответа и текущего заголовка узла, поэтому отдельная колонка статуса не может устареть.

## API

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `GET` | `/api/projects/{project_id}/coverage-map` | preorder-список узлов, статусы и сводные числа для текущей программы |
| `GET` | `/api/projects/{project_id}/program-nodes/{node_id}/reference-answer` | слот ответа выбранного учебного узла |
| `PUT` | тот же маршрут | создать, изменить или вернуть ответ с `expected_revision` |
| `DELETE` | тот же маршрут | мягко убрать ответ с проверкой ревизии |
| `POST` | `.../reference-answer/confirm` | подтвердить точное автоматическое сопоставление |
| `POST` | `/api/projects/{project_id}/reference-answers/import` | разобрать общий текст и создать только отсутствующие ответы |
| `DELETE` | `/api/projects/{project_id}` | навсегда удалить проект и принадлежащие ему данные |

Конфликты возвращают стабильные коды: `stale_reference_answer_revision`, `reference_answer_exists`, `reference_answer_missing`, `project_read_only`, `reference_answers_require_exam_project` и `reference_answer_requires_study_node`.

## Импорт без ИИ

Импорт — детерминированный разбор пар «заголовок → последующий текст».

1. Заголовки программы нормализуются через Unicode NFKC, `casefold`, замену `ё` на `е`, снятие номера/слова «Вопрос» или «Задача» и конечной пунктуации.
2. Строка входного текста, которая после той же нормализации точно совпала ровно с одним учебным узлом, начинает секцию ответа.
3. Текст до следующего распознанного заголовка становится ответом; префикс `Ответ:` снимается.
4. Пустые, неизвестные и неоднозначные секции возвращаются отдельными списками и не теряются молча.
5. Активный ручной, подтверждённый или пришедший из другого источника слот импорт не
   перезаписывает. Мягко удалённый слот, найденный тем же импортом, восстанавливается,
   иначе одна и та же запись могла иметь страницы источника, но оставаться «без ответа».

Нечёткое сопоставление и модель здесь сознательно отсутствуют: сомнительная связь хуже явного `unmatched`.

## Интерфейс

`/projects/:projectId/coverage-map` показывает нейтральную сводку, фильтруемый preorder-список и редактор выбранного ответа. Процент не используется и отсутствие материала не выдаётся за дефект. Массовый импорт показывает количество созданных, пропущенных, неизвестных, неоднозначных и пустых секций.

Рабочая область загружает эталон выбранного вопроса отдельно и поддерживает прямую ссылку `?topic={ProgramNode.id}`. Вкладка материала остаётся честной заглушкой этапа 5.

Демонстрационный экзаменационный проект содержит четыре коротких эталона. Повторный запуск не перезаписывает пользовательские изменения и не воскрешает демонстрационный проект после явного удаления.

## Проверка

```bash
python backend/scripts/check_stage2.py
python backend/scripts/check_stage3.py
python backend/scripts/check_stage4.py
python -m ruff check backend
npm run typecheck
npm run build
```

`check_stage4.py` поднимает отдельную временную базу и проверяет миграцию, импорт, все статусы, rename/move узла, оптимистическую блокировку, мягкое и полное удаление, архивный и учебниковый запреты, идемпотентность демо и отсутствие сирот по внешним ключам.

## Готовность к этапу 5

Этап 5 может опираться на уже стабильные `Project.id`, `ProgramNode.id`, транзакционные миграции и полный lifecycle проекта. Новые сущности материалов должны добавляться рядом, а не менять контракт эталонов. Карта материалов впоследствии сможет объединить статусы эталона с покрытием «программа ↔ материал», не перенося и не дублируя сами ответы.
