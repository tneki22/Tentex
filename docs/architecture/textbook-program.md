# Программа учебникового проекта

Фактический контракт вертикали «Программа учебника»: часть 1 (11.09.2026, ручной
редактор и офлайновый импорт оглавлений) и часть 2 (12.09.2026, чат построения
программы с дифами). Части независимо датированы ниже, часть 1 не переписана.

## Данные узла

`ProgramNode.basis_kind` отвечает только на вопрос, основан ли узел на оглавлении:

- `outline` — у узла есть хотя бы один проверенный пункт оглавления;
- `custom` — узел создан вне оглавления, в части 1 вручную.

`origin_kind` остаётся независимым происхождением последнего создания или изменения.
Ручное переименование либо перемещение outline-узла ставит `origin_kind=manual`, но
не меняет `basis_kind` и не удаляет диапазоны.

Диапазоны лежат в `program_node_source_page_ranges`: проект, узел, материал, снимок
названия источника, стабильный ключ пункта, `page_from`, `page_to`. Диапазон идёт до
страницы перед следующим пунктом того же или более высокого уровня; последняя ветвь
заканчивается на последней полной странице материала. Один узел может получить
несколько диапазонов в следующих вертикалях; API уже возвращает список.

## Состояние оглавлений мастера

Шаг 3 хранит не один выбранный результат, а словарь
`WizardDraft.state.outlines_by_material_id`. Ключ — id материала, значение содержит
источник обнаружения, стабильные ключи пунктов, проверенные формулировки и страницы.
Старый `state.outline` читается как совместимый одиночный черновик, но больше не
записывается.

## Импорт

`POST /api/projects/{project_id}/program/import-outlines`

```json
{
  "expected_program_revision": 7,
  "sources": [
    {
      "material_id": "11111111-1111-1111-1111-111111111111",
      "items": [
        {
          "outline_item_key": "1111:embedded:0:7:1",
          "level": 1,
          "title": "Сетевые модели",
          "page": 7,
          "selected": true
        }
      ]
    }
  ]
}
```

Сервер проверяет учебниковый вариант проекта, принадлежность каждого материала,
уникальность ключей, страницы и каскад выбранных родителей. Источники применяются по
`ProjectMaterial.priority`, а не по порядку JSON. Пропуск уровня не создаёт
искусственного узла: пункт становится ребёнком ближайшего предыдущего пункта меньшего
уровня либо корнем.

Стабильная пара `(material_id, outline_item_key)` узнаёт повторный импорт. Видимый
узел не дублируется; выведенный из программы узел возвращается с тем же id. Новые
корни каждого источника добавляются друг за другом без обёрток с именами файлов.
Операция увеличивает `program_revision` один раз и создаёт одно действие
`outline_import`; если изменений нет, ревизия не меняется.

Ответ — обычный `ProgramChangeResult`. Конфликт ревизии — `409 stale_program_revision`,
чужой материал и разорванный выбор — доменная ошибка `program_invariant`.

## Массовый вывод и undo

`POST /api/projects/{project_id}/program/remove-all` принимает
`{"expected_program_revision": 8}` и возвращает `ProgramChangeResult`. Все видимые
узлы получают `is_in_current_program=false`; строки узлов и диапазонов не удаляются.
Одна запись `program_remove_all` возвращает всю программу одним обычным
`POST /api/projects/{project_id}/actions/undo`.

Undo импорта также меняет только видимость созданных или возвращённых узлов. Поэтому
повторный импорт после undo восстанавливает прежние id и не создаёт дублей.

## Интерфейс

`TextbookProgramEditor` используется шагом 4 мастера и разделом активного проекта.
Он владеет поиском, тремя представлениями, CRUD, перемещением, контекстным меню,
диалогами импорта и массового вывода. Родитель передаёт только шапку, текущий снимок
программы и адаптер выполнения команды; экзаменационный редактор не изменён.
В мастере выбор узла остаётся внутренним. Раздел проекта может управлять им через
`selectedNodeId`/`onSelectedNodeChange`: поэтому `?topic=` и строка «Последние изменения»
открывают тот же узел без второго редактора. Проектный экран использует стандартную
`project-side-panel`; пять строк строятся из видимых узлов по `updated_at`, а
`latest_undoable_action` отдельно показывает последнее отменяемое действие.

Диалог показывает все материалы проекта, включая спокойные строки без оглавления,
все уровни оглавления, каскадные чекбоксы, общий счётчик и предупреждение о совпавших после
нормализации путях. Совпадения не объединяются автоматически.

## Часть 2. Чат построения программы с дифами (12.09.2026)

`TextbookProgramEditor` получил `mode: "manual" | "ai"` и `aiContent`: тулбар
(«Отменить», переключатель режима, «Импортировать программу из оглавления»,
«Удалить все») общий для обоих режимов и остаётся смонтированным всегда — в режиме
`ai` контентная область (Дерево/Текст/Вопросы, поиск, CRUD) заменяется на чат слева
(2/3) и read-only `ProgramTreePreview` справа (1/3), собираемые вызывающей стороной
(`TextbookWizard.tsx`, `Program.tsx`), а не самим редактором.

### Сессия и контекст

Чат — обычный `ChatSession`/`ChatMessage` с `mode=program`, но `program_node_id`
теперь допускает `NULL`: сессия привязана к проекту целиком (составной FK с NULL не
проверяется, доп. миграции не нужно). Общая раскладка сообщений/черновика/подсчёта
вынесена из `app.exam.chat` в `app.chat.common` (`append_message_row`, `message_read`,
`save_draft_text`, `message_counts`) — `exam/chat.py` теперь тонкая обёртка над ней,
поведение и тесты не изменились.

Контекст (`program_chat.build_program_context`) — паспорт цели, **только оглавление** каждого
`ProjectMaterial` (с оригинальным `outline_item_key`, тем же форматом, что у
`frontend/.../outlineState.ts`) и текущее дерево. `ChatSession.context_flags` для этого
режима: `profile`, `primary_sources`, `secondary_sources`, `reference_sources`
(дефолт — всё включено, кроме справочных). Манифест-записи источников несут
`flag_key`/`label` (новые опциональные поля `ManifestEntryRead`, exam их не
заполняет) — фронтенд группирует по ним чипы. Контекст обрезается по
`SEND_MESSAGE_CONTEXT_CHARS` (40 000 символов), источники сверх бюджета помечаются
`reason=context_budget_exceeded`, а не обрубаются молча.

Полный текст материалов в обычное сообщение и в сборку «по оглавлению» не передаётся:
блок `<source_outlines>` прямо сообщает модели, что внутри карта содержания, а не
основные источники. Фрагменты текста появляются только в отдельном сценарии «по моей
цели» как короткие результаты локального поиска.

### Роль и схема ответа

`study_program_assistant` (`ai/roles.py`) — `structured_output`, с
`allow_request_model_override`: модель и её параметры выбираются слева в
композере (`ChatModelControl` → `ChatModelPicker`, тот же виджет, что в
экзаменационном чате) и хранятся в `ChatSession.model_override` /
`model_parameters` — таблица сессий общая для обоих режимов чата. `streaming`
не требуется: ответ приходит одним структурированным вызовом. Выбор
подхватывает и фоновая первая сборка (`_run_build_call`). Настройка через
`PUT …/program-chat/sessions/{id}/settings`; прежний запрет override снят,
когда выбор переехал из Параметров в чат. Ответ — одна схема `ProgramChatReply {summary, pros, cons, operations}`.
`operations` — дискриминированный по `op` union: `add, rename, move, change_type,
set_goal, set_visibility, merge`. `add` — единственная операция, создающая узлы;
вложенные `children` описывают целое поддерево одним элементом. Остальные операции
ссылаются только на существующие `node_id` — поэтому каждая верхнеуровневая операция
независима сама по себе, без отдельного резолвера зависимостей.

### Два сценария сборки

`POST .../sessions/{id}/build {scenario: "outline"|"goal", expected_program_revision}`
ставит `BackgroundJob(kind=ai_program_build)` в очередь (202). `outline` — один вызов
с оглавлениями и деревом. `goal` — сначала короткий вызов «дай до 5 поисковых
запросов», затем `search_project_materials` по каждому (один `ChatToolRun` на всю
пачку), и лишь потом основной вызов с результатами поиска в контексте. Если
сериализованные оглавления превышают `SINGLE_CALL_OUTLINE_CHARS` (24 000), источники
делятся на до `MAX_BUILD_PACKETS` (2) сбалансированных пакета — каждый пакет
коммитится в `job.checkpoint["packets"]` сразу после вызова модели, поэтому падение
между пакетами не теряет уже готовую часть: повторный `POST .../build` на ту же
сессию находит `FAILED`-задачу с частичным checkpoint и переводит её обратно в
`QUEUED` тем же `job.id`, а не создаёт новую. Прогресс — честные `done`/`total`
(число пакетов + слияние), не имитация построчного заполнения дерева. По готовности
воркер сам дописывает `ChatMessage` (роль `assistant`, `payload_kind=program_diff`) —
результат виден в истории чата, а не только через `GET /background-jobs/{id}`.
`ai_program_build` не входит в `REVIEW_REQUIRED_KINDS`: разбор предложения — сам чат,
отдельный экран на панели фоновых задач не нужен.

Итеративные сообщения (`POST .../sessions/{id}/messages`) — синхронный
(без стрима) вызов той же роли: одна структурированная реплика за ход. Инструмент
поиска зарегистрирован для `program` в `chat_tools/registry.py`, но петля итеративных
сообщений его не вызывает — используется только оркестрацией сценария «по цели».

### Применение диффа

`basis_kind` выводится сервером, не доверяя модели: `add.outline_ref` (material_id +
outline_item_key) перепроверяется против настоящего оглавления материала тем же
способом, что и импорт части 1 (`_prepare_items`-подобный расчёт границы страницы);
совпал — `basis_kind=outline` + запись в `program_node_source_page_ranges`; не
совпал или отсутствует — `basis_kind=custom`, для темы/подпункта дополнительно
`needs_material=true`. `merge` — первый узел списка выживает (получает `title`, если
задан), остальные скрываются `is_in_current_program=false`, их диапазоны страниц
переносятся на выжившего (кроме точных дублей `outline_item_key` — те остаются на
месте) — ничего не удаляется (FR-G11).

`POST .../proposals/{message_id}/apply {selected: [индексы], expected_program_revision}`
применяет выбранные операции одной транзакцией и одной записью `program_chat_apply`
(полный undo — снимок позиций всех узлов + затронутых полей + список созданных id +
перенесённые диапазоны, восстанавливается тем же
`POST /api/projects/{id}/actions/undo`, что и остальные учебниковые действия).
Невыбранные операции остаются `pending`; при следующем apply/reject сервер проверяет,
что их `node_id`/`node_ids` ещё существуют — если узел исчез (например, его поглотил
принятый `merge`), операция помечается `conflicted` и больше не выбираема: нужен
новый диф. Несовпадение `expected_program_revision` — `409 stale_program_revision`,
карточка остаётся в истории. `POST .../proposals/{message_id}/reject` просто
помечает сообщение `rejected`, ревизию не трогает.

`set_visibility` меняет видимость всего поддерева от указанного узла, как ручное
удаление или возврат ветви. Поэтому одна выбранная операция не оставляет видимых
потомков под скрытым родителем; undo восстанавливает прежнее состояние каждого узла.

### Известные упрощения

- Живой предпросмотр (`ProgramTreePreview`) показывает неизменённые строки нейтрально,
  добавления зелёным, удаления красным, а переименование — как красную старую и зелёную
  новую формулировки. Фактическое новое положение узла при `move` до применения не
  пересчитывается.
- Переключатель «Составить программу автоматически» на шаге 3 мастера
  (TEXTBOOK_MODE.md §3: выбирает стартовый под-режим шага 4 по доступности внешних
  моделей) не реализован — `TODO.md` NEXT-07.
- Переключатель области контекста (вся программа / раздел / тема) не построен на
  фронтенде: `ChatSession.section_scope_node_id` и `PUT .../context` его принимают,
  но UI всегда работает с контекстом всей программы.
- Инструмент поиска не вызывается моделью на лету в обычной переписке (`gateway`
  не поддерживает live tool-calling в этом проекте) — поиск происходит только
  внутри фиксированной оркестрации сценария «по моей цели» при первой сборке.
- Апрув диффа проверяет, что узлы, на которые ссылаются невыбранные операции,
  ещё существуют и видимы, но не отслеживает более тонкие ручные правки (например
  переименование того же узла вручную, пока диф висел) — конфликт на уровне
  значения полей не определяется, только на уровне существования/видимости узла.
