# Настройки распознавания: фактический контракт

Дата фиксации: 01.09.2026. Раздел «Распознавание» доведён до конца в границах,
оставшихся после резки GPU-контура «Учебник» (снят при стабилизации экзамена —
причина и что было в `docs/archive/gpu-ocr-textbook.md`, тег `gpu-ocr-last`): конфиг и
статус, реальная докачка моделей с Hugging Face. Режимов ровно два — «Быстро»
(работает) и «Облако» (честная заглушка). Управления железом, GPU-сервисом и
движков «Максимум»/«Эксперт» в продукте больше нет.

## Инварианты

- Реестр движков `backend/app/ocr/engines.py:OCR_ENGINES` — единственный источник
  списка режимов: ключ, заголовок, описание, компромисс, где исполняется
  (`worker` / `cloud`), можно ли настраивать. Новый настраиваемый движок добавляется
  одной записью реестра плюс веткой в `settings.read_settings`, не переделкой
  роутера, схем или экрана. Этот же реестр читает `LibraryProcessingPanel.tsx` в
  Библиотеке — второго списка режимов в проекте нет.
- Ровно две записи реестра: `fast` (`runtime="worker"`, настраиваемый) и `cloud`
  (`runtime="cloud"`, `configurable=False`, `unavailable_reason="Ещё не подключено.
  Появится вместе с отправкой файлов наружу."`). Третьего, GPU-режима «Учебник», в
  реестре больше нет.
- `OcrEngineConfig.mode` — обычная строка, а не FK на перечисление: для
  незаконфигурированного `cloud` строки в БД нет — `read_settings` берёт его описание
  и причину недоступности прямо из реестра.
- Разделение по моменту применения: всё **живо** — следующий разбор материала читает
  сразу. `OcrSettings.quality_threshold`, `OcrSettings.raster_scale`,
  `OcrEngineConfig(mode="fast").language`/`.model_id` подхватываются без перезапуска
  чего бы то ни было. Раздел «применяется только при перезапуске сервиса» исчез вместе
  с GPU-контуром — конфигурировать вообще нечего, кроме `fast`, а он читается из БД на
  каждую задачу воркера.
- `OcrSettings.default_mode` типизирован как `ParserMode` (enum, единственное значение
  `fast`) на уровне колонки — сохранить в БД любое другое значение невозможно даже в
  обход Pydantic (миграция `20260901_0030_drop_textbook_ocr_mode.py` сузила CHECK до
  `{"fast"}`). `raster_scale` ограничен `CheckConstraint IN (1.5, 2.0, 3.0)` и тем же
  набором в Pydantic (`Literal[1.5, 2.0, 3.0]`).
- «Быстро» доступен всегда: `paddleocr`/`paddlepaddle` стоят только в образе воркера
  (`requirements-worker.txt`), не в API (`requirements-dev.txt`). Проверять их
  наличие из процесса API нельзя — это будет проверка не того процесса, который
  реально исполняет разбор. Единственный настоящий живой сигнал для «Быстро» —
  непустая ли `data/models` (общий bind-mount с воркером); текст страницы всё равно
  разбирается и без единой скачанной модели — модели нужны только сканам.
- Модели распознавания не входят в поставку и не проверяются на достоверность
  внутри Tentex — доверие исходит из единственного разрешённого источника: репозитории
  организации PaddlePaddle на Hugging Face (`backend/app/ocr/catalog.py:SOURCE_URL`),
  подтверждённой самим Hugging Face. Список файлов и их размеры каталог не хранит —
  спрашивает у Hugging Face API при каждой установке, поэтому прогресс на экране настоящий,
  а не оценка по захардкоженной константе.

## Хранение

Миграция `20260825_0022_ocr_settings.py` (новых таблиц Фазам 2–3 не потребовалось —
вся докачка моделей выводится из файловой системы и внешнего API на лету), сужена
миграцией `20260901_0030_drop_textbook_ocr_mode.py`, снявшей GPU-режим из CHECK-
ограничений `materials`, `processing_tasks`/`background_jobs`, `material_revisions` и
`ocr_settings`:

- `ocr_settings` — singleton (`id=1`, как `ai_settings`): `default_mode`,
  `quality_threshold`, `raster_scale`, таймстампы;
- `ocr_engine_configs` — по одной строке на настраиваемый движок (`mode` — PK). Сейчас
  это ровно одна строка (`fast`): `enabled`, `model_id`, `device`, `language`,
  `executor`, `extra` JSON, `updated_at`. `extra` пуст — GPU-сервис, единственный
  потребитель этого поля (адрес и таймаут), снят вместе с контуром «Учебник»;
- сид: `id=1` с дефолтами (`fast`, 0.75, 2.0) и одна строка `fast`
  (`language="ru"`, `model_id="PP-OCRv5"`).

Установленность модели — не флаг в БД, а факт на диске: `downloads.installed(spec)`
проверяет, что у каждого репозитория набора есть файл весов (`.pdiparams` /
`.safetensors` / `.pdmodel` / `.bin` тяжелее 1 МБ) в `data/models/official_models/<repo>`
(раскладка `paddlex` — то, что ищет PaddleX). Для будущих наборов в кеше Hugging Face
установленность подтверждает отдельный маркер `.tentex-complete`: один уже скачанный
файл весов не может выдать недокачанную модель за установленную. Прогресс активной загрузки живёт в памяти процесса API
(`downloads._jobs`, по потоку на набор) и теряется при перезапуске API — начатая, но
не оконченная загрузка после рестарта считается незавершённой и продолжается заново
кнопкой «Установить», а не автоматически.

## Каталог и установка моделей

`backend/app/ocr/catalog.py:OCR_MODELS` — статическое описание каждого набора
(заголовок, когда выбирать, репозитории и их размеры, лицензия, требования к
устройству/видеопамяти/оперативной памяти, предупреждения). Сейчас в каталоге один
набор — `fast-ru` (движок `fast`, CPU, русский/английский/украинский/белорусский).
Размеры — оценка для раздела «Ваш компьютер»; реальный прогресс загрузки берётся из
Hugging Face API.

`backend/app/ocr/downloads.py`:

- `start_install(model_key)` — фоновый `threading.Thread`, качает каждый репозиторий
  через `huggingface_hub.snapshot_download` с восемью параллельными потоками и Xet.
  Байтовый callback обновляет прогресс на экране внутри большого файла, а не только
  после его конца;
- `cancel_install(model_key)` — ставит `threading.Event`; callback прерывает загрузку
  при следующем полученном фрагменте. Недокачанное содержимое остаётся в кеше и кнопка
  «Продолжить загрузку» возобновляет его;
- `remove(model_key)` — удаляет папки репозиториев, но не трогает те, что нужны
  другому установленному набору;
- `engine_ready(engine)` — установлен ли хоть один набор движка.

## API

`backend/app/ocr/router.py`, префикс `/api/settings/ocr`:

- `GET ?refresh=<bool>` — снимок: глобальные настройки, движки реестра (каждый — с
  живым статусом и вложенным списком моделей каталога). Параметр `refresh` остался в
  сигнатуре ради обратной совместимости фронтенда, но больше ничего не сбрасывает —
  30-секундный кеш `hardware.probe()` снят вместе с определением железа;
- `PUT` — глобальные настройки, всегда полным объектом;
- `PUT /engines/{mode}` — настройки одного движка, тоже полным объектом; 404
  (`ocr_engine_not_found`) на неизвестный ключ, 409 (`ocr_engine_not_configurable`) на
  `cloud`;
- `POST /models/{key}/install` — запускает фоновую загрузку, отвечает сразу
  (сама загрузка идёт в потоке, прогресс — следующим `GET`);
- `POST /models/{key}/cancel`, `DELETE /models/{key}` — отменить активную загрузку,
  удалить установленный набор (409 `ocr_model_busy`, если загрузка ещё идёт).

Эндпоинтов `POST /service/start`, `POST /service/stop` и схем `OcrGpuRead`/
`OcrHardwareRead`/`OcrServiceRead` в продукте больше нет — они управляли только
GPU-контейнером «Учебника».

Единый ответ `OcrSettingsRead` — источник и для раздела настроек, и для панели
обработки материала в Библиотеке: `settings.engine_ready(session, mode)` отвечает на
вопрос «можно ли прямо сейчас разбирать этим движком» одинаково в обоих местах, иначе
кнопка «Подготовить материал» и статус движка в настройках разъехались бы.

Поле `readiness` (`ready` / `downloading` / `needs_models` / `error` / `unavailable`)
заменяет собой то, что раньше было одной серой строкой статуса: интерфейс подбирает
цвет и заголовок по машинному значению, произвольный текст (`status_detail`) идёт
отдельной строкой под ним. Значения `needs_service` и `starting` остаются в типе
`Readiness` (`backend/app/ocr/schemas.py`) объявленными про запас — их использовал
только GPU-сервис «Учебника», сейчас их не возвращает ни один движок реестра; убирать
их из `Literal` не стали, чтобы не трогать контракт ради одной строки типа.

## Де-хардкод парсеров

`quality_threshold` (было `0.75` в трёх местах) и `raster_scale` (было `2×` в двух
местах рендера страницы) — параметры, а не константы. Поток: `worker.process_task`
читает `app.ocr.settings.runtime_params(session)` один раз на задачу (без сети — только
`OcrSettings`/`OcrEngineConfig`) и передаёт `OcrRuntimeParams` в
`native.iter_pages(..., params=params)`; оттуда параметры идут в
`paddle_fast.parse_image` именованными аргументами. У всех
параметров есть дефолты, равные прежним хардкодам, поэтому вызовы `iter_pages(path, mode)`
без `params` (тесты, скрипты) не менялись.

`paddle_fast._get_engine()` кеширует движок PaddleOCR по паре `(language, ocr_version)`,
не глобальным синглтоном на первый вызов — иначе смена языка в настройках не
подхватывалась бы до перезапуска воркера.

## Библиотека: переход на реестр

`LibraryProcessingPanel.tsx` не хранит свой список режимов и не стартует с
захардкоженного `useState<ParserMode>("fast")`. Панель читает `GET /api/settings/ocr`,
подставляет `default_mode` как выбор по умолчанию (пользователь может тут же
переключить руками — сейчас переключать фактически не на что, реестр отдаёт одну
рабочую карточку) и рисует ровно те карточки, что вернул реестр — с тем же текстом
статуса, что и в разделе настроек. Если выбранный режим недоступен, под списком
появляется прямая ссылка «Открыть параметры распознавания»
(`/setup?section=ocr&subsection=engines`) вместо тупика. Эндпоинт
`GET /api/material-capabilities` и схема `MaterialCapabilities` удалены целиком —
второго источника правды об OCR-движках в проекте больше нет.

## Проверка

`backend/tests/test_ocr_settings.py` — сервисный слой (`read_settings`,
`update_global_settings`, `update_engine`, `runtime_params`). `test_pdf_layout_parser.py::test_page_quality_threshold_is_configurable`
— порог реально переключает `ocr`/`ocr_low`. Сквозные проверки —
`backend/scripts/check_stage5.py` (реальные миграции и воркер; читает
`/api/settings/ocr` вместо удалённого `/api/material-capabilities`) и
`check_library_workspace.py` (материал-capabilities с настроенным движком). Установка
модели кнопкой проверена вручную через реальный API-контейнер:
`POST .../models/fast-ru/install` → фоновая докачка недостающего файла общего
репозитория → `installed: true` → `DELETE .../models/fast-ru` — до состояния диска
эти два шага дописывать `pytest`-ом не стали: тест реального сетевого похода на
Hugging Face был бы либо сетевым (нестабилен в CI), либо мокал сам huggingface_hub
целиком, теряя ценность проверки.
