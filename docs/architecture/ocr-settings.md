# Настройки распознавания: фактический контракт

Дата фиксации: 26.08.2026. Раздел «Распознавание» доведён до конца целиком:
конфиг и статус (Фаза 1, 25.08.2026), реальная докачка моделей с Hugging Face
и определение железа (Фаза 2), запуск GPU-сервиса «Учебник» кнопкой и переход
`LibraryProcessingPanel` на этот реестр вместо `STATIC_OCR_MODES` (Фаза 3).
Открытых пунктов из исходного плана не осталось — `cloud`/`maximum`/`expert`
остаются заглушками сознательно: это отдельный этап (внешние модели, §22).

## Инварианты

- Реестр движков `backend/app/ocr/engines.py:OCR_ENGINES` — единственный источник
  списка режимов: ключ, заголовок, описание, компромисс, где исполняется
  (`worker` / `gpu_service` / `cloud`), можно ли настраивать. Новый настраиваемый
  движок добавляется одной записью реестра плюс веткой в `settings.read_settings`,
  не переделкой роутера, схем или экрана. Этот же реестр читает
  `LibraryProcessingPanel.tsx` в Библиотеке — второго списка режимов в проекте нет.
- `OcrEngineConfig.mode` — обычная строка, а не FK на перечисление: реестр шире, чем
  `ParserMode` (`fast`/`textbook`), и содержит ещё не реализованные `cloud`/`maximum`/
  `expert`. Для них строк в БД нет — `read_settings` берёт их описание и причину
  недоступности прямо из реестра.
- Разделение по моменту применения:
  - **живо** (следующий разбор материала читает сразу): `OcrSettings.quality_threshold`,
    `OcrSettings.raster_scale`, `OcrEngineConfig(mode="fast").language`/`.model_id`,
    `OcrEngineConfig(mode="textbook").extra["service_url"|"timeout_seconds"]`;
  - **при следующем запуске GPU-сервиса**: `OcrEngineConfig(mode="textbook").model_id` /
    `.device` / `.executor` — контейнер читает их только из переменных окружения при
    старте (`service_control.environment_for`). Если сохранённое значение разошлось
    с уже запущенным контейнером, `OcrEngineRead.restart_required = True`
    (`service_control.environment_applied`) — интерфейс честно просит перезапустить,
    а не молчит и не подменяет их налету.
- `OcrSettings.default_mode` типизирован как `ParserMode` (enum `fast`/`textbook`) на
  уровне колонки — сохранить в БД любое другое значение невозможно даже в обход
  Pydantic. `raster_scale` ограничен `CheckConstraint IN (1.5, 2.0, 3.0)` и тем же
  набором в Pydantic (`Literal[1.5, 2.0, 3.0]`).
- «Быстро» доступен всегда: `paddleocr`/`paddlepaddle` стоят только в образе воркера
  (`requirements-worker.txt`), не в API (`requirements-dev.txt`). Проверять их
  наличие из процесса API нельзя — это будет проверка не того процесса, который
  реально исполняет разбор. Единственный настоящий живой сигнал для «Быстро» —
  непустая ли `data/models` (общий bind-mount с воркером); текст страницы всё равно
  разбирается и без единой скачанной модели — модели нужны только сканам.
- Модели распознавания не входят в поставку и не проверяются на достоверность
  внутри Tentex — доверие исходит из единственного разрешённого источника: репозитории
  организации PaddlePaddle на Hugging Face (`backend/app/ocr/catalog.py:SOURCE_URL`),
  подтверждённой самим Hugging Face. Список файлов и их размеры каталог не хранит —
  спрашивает у Hugging Face API при каждой установке, поэтому прогресс на экране настоящий,
  а не оценка по захардкоженной константе.
- Определение железа не выдумывает: если источник не смог назвать величину (чаще
  всего — объём видеопамяти через Docker, который знает только факт драйвера NVIDIA,
  не цифру), ответ — `None` с причиной, а не оптимистичное значение. У каждого замера
  есть `source`, чтобы пользователь видел, откуда взялась цифра
  (`backend/app/ocr/hardware.py`, докстринг модуля).

## Хранение

Миграция `20260825_0022_ocr_settings.py` (единственная — Фазы 2–3 новых таблиц не
требуют, вся докачка моделей и обнаружение железа выводятся из файловой системы и
внешних API на лету):

- `ocr_settings` — singleton (`id=1`, как `ai_settings`): `default_mode`,
  `quality_threshold`, `raster_scale`, таймстампы;
- `ocr_engine_configs` — по одной строке на настраиваемый движок (`mode` — PK):
  `enabled`, `model_id`, `device`, `language`, `executor`, `extra` JSON, `updated_at`.
  `extra` сегодня хранит только адрес и таймаут GPU-сервиса «Учебника»
  (`service_url`, `timeout_seconds`);
- сиды: `id=1` с дефолтами (`fast`, 0.75, 2.0) и по одной строке на `fast`
  (`language="ru"`, `model_id="PP-OCRv5"`) и `textbook` (`model_id`/`device`/`executor`
  из констант `DEFAULT_TEXTBOOK_*` в `app/ocr/engines.py`, равных дефолтам `ocr_service/app.py`).

Установленность модели — не флаг в БД, а факт на диске: `downloads.installed(spec)`
проверяет, что у каждого репозитория набора есть файл весов (`.pdiparams` /
`.safetensors` / `.pdmodel` / `.bin` тяжелее 1 МБ) в `data/models/official_models/<repo>`
(раскладка `paddlex` — то, что ищет PaddleX). Для будущих наборов в кеше Hugging Face
установленность подтверждает отдельный маркер `.tentex-complete`: один уже скачанный
файл весов не может выдать недокачанную модель за установленную. Прогресс активной загрузки живёт в памяти процесса API
(`downloads._jobs`, по потоку на набор) и теряется при перезапуске API — начатая, но
не оконченная загрузка после рестарта считается незавершённой и продолжается заново
кнопкой «Установить», а не автоматически.

## Обнаружение железа

`backend/app/ocr/hardware.py:probe()` — что реально может исполниться на этой машине,
кешируется на 30 секунд (экран перечитывает настройки после каждого действия, гонять
`nvidia-smi` на каждый `GET` незачем), сбрасывается кнопкой «Проверить ещё раз»
(`GET /api/settings/ocr?refresh=true`) или тестами (`reset_cache()`).

Источники видеокарты по убыванию точности, первый успешный побеждает:

1. `TENTEX_GPU_NAME`/`TENTEX_GPU_VRAM_MB` — явное указание тому, кто запускал установку;
2. `nvidia-smi` — работает, только если Tentex запущен прямо на хосте, не в контейнере;
3. health-check самого GPU-сервиса «Учебник» (`ocr_service/app.py:_gpu()`, через
   `nvidia-smi` изнутри его контейнера, у которого есть доступ к драйверу) — самый точный
   источник внутри Docker, но виден только пока сервис запущен;
4. факт драйвера NVIDIA в `docker info` (`Runtimes.nvidia`) — знает только «видеокарта
   NVIDIA есть», не её объём памяти; это и есть типичный случай честного `vram_mb: null`.

`fits()` сравнивает набор моделей с этим замером и возвращает `True`/`False`/`None`
(`None` — «не смогли проверить», отдельный ответ, не «нет») с объяснением одной строкой.

## Каталог и установка моделей

`backend/app/ocr/catalog.py:OCR_MODELS` — статическое описание каждого набора
(заголовок, когда выбирать, репозитории и их размеры, лицензия, требования к
устройству/видеопамяти/оперативной памяти, предупреждения). Размеры — оценка для
раздела «Ваш компьютер»; реальный прогресс загрузки берётся из Hugging Face API.

`backend/app/ocr/downloads.py`:

- `start_install(model_key)` — фоновый `threading.Thread`, качает каждый репозиторий
  через `huggingface_hub.snapshot_download` с восемью параллельными потоками и Xet.
  Байтовый callback обновляет прогресс на экране внутри большого файла, а не только
  после его конца;
- `cancel_install(model_key)` — ставит `threading.Event`; callback прерывает загрузку
  при следующем полученном фрагменте. Недокачанное содержимое остаётся в кеше и кнопка
  «Продолжить загрузку» возобновляет его;
- `remove(model_key)` — удаляет папки репозиториев, но не трогает те, что нужны
  другому установленному набору;
- `engine_ready(engine)` — установлен ли хоть один набор движка; читает `settings.py`
  для решения `needs_models` у «Учебника» (см. ниже).

## Управление GPU-сервисом через сокет Docker

Раньше экран настроек предлагал текстом выполнить `docker compose --profile textbook up`.
Продукту, который ставится из архива и открывается в браузере, это не ответ — сервис
запускается и останавливается кнопкой.

`backend/app/ocr/docker_engine.py` — минимальный клиент Docker Engine API поверх
`/var/run/docker.sock` (примонтирован в контейнер `api`, см. `docker-compose.yml`),
без SDK: нужно ровно пять вызовов (найти, создать, запустить, остановить, прочитать
хвост журнала), а `docker` SDK тянет `requests` и полтора десятка зависимостей в лёгкий
образ API. Управление, а не создание, идёт командой Docker Engine напрямую, а не
`docker compose`, по одной причине: команда `compose` изнутри контейнера подставила бы
демону **свои** пути (`/app/data`), а тот разрешает их в файловой системе хоста —
получились бы пустые тома. Поэтому пути для тома при первом создании контейнера
`docker_engine.self_container()` берёт из описания **собственного** контейнера API —
только там записаны настоящие пути хоста.

`backend/app/ocr/service_control.py`:

- `describe()` — состояние (`running`/`starting`/`stopped`/`failed`/`absent`/
  `unavailable`) плюс `can_start`/`can_stop`. `absent` (образ ещё не собран) и
  `unavailable` (Tentex не видит сокет Docker) осознанно не предлагают кнопку —
  собрать образ на несколько гигабайт из самого приложения не пытаемся;
- `start(environment)` — создаёт контейнер при первом запуске (образ, порт, тома,
  `DeviceRequests` с драйвером `nvidia`, тот же сетевой алиас `textbook-ocr`, что и в
  `docker-compose.yml`, иначе воркер и API перестанут его находить) либо пересоздаёт,
  если сохранённые `model_id`/`device`/`executor` разошлись с уже созданным контейнером
  (переменные окружения задаются только при создании);
- `stop()` — штатная остановка с таймаутом;
- `environment_applied(environment)` — сверяет желаемые переменные с реально запущенным
  контейнером; на этом основано поле `restart_required` в ответе API.

## API

`backend/app/ocr/router.py`, префикс `/api/settings/ocr`:

- `GET ?refresh=<bool>` — снимок: глобальные настройки, железо, движки реестра
  (каждый — с живым статусом и вложенным списком моделей каталога), `refresh=true`
  сбрасывает 30-секундный кеш железа;
- `PUT` — глобальные настройки, всегда полным объектом;
- `PUT /engines/{mode}` — настройки одного движка, тоже полным объектом; 404
  (`ocr_engine_not_found`) на неизвестный ключ, 409 (`ocr_engine_not_configurable`) на
  `cloud`/`maximum`/`expert`;
- `POST /models/{key}/install` — запускает фоновую загрузку, отвечает сразу
  (сама загрузка идёт в потоке, прогресс — следующим `GET`);
- `POST /models/{key}/cancel`, `DELETE /models/{key}` — отменить активную загрузку,
  удалить установленный набор (409 `ocr_model_busy`, если загрузка ещё идёт);
- `POST /service/start`, `POST /service/stop` — управление контейнером «Учебника».

Единый ответ `OcrSettingsRead` — источник и для раздела настроек, и для панели
обработки материала в Библиотеке: `settings.engine_ready(session, mode)` отвечает на
вопрос «можно ли прямо сейчас разбирать этим движком» одинаково в обоих местах, иначе
кнопка «Подготовить материал» и статус движка в настройках разъехались бы.

Поле `readiness` (`ready` / `downloading` / `needs_models` / `needs_service` /
`starting` / `error` / `unavailable`) заменяет собой то, что раньше было одной серой
строкой вида «Не готово · Локально · GPU · сервис не запущен»: интерфейс подбирает
цвет и заголовок по машинному значению, произвольный текст (`status_detail`) идёт
отдельной строкой под ним.

## Де-хардкод парсеров

`quality_threshold` (было `0.75` в трёх местах) и `raster_scale` (было `2×` в двух
местах рендера страницы) — параметры, а не константы. Поток: `worker.process_task`
читает `app.ocr.settings.runtime_params(session)` один раз на задачу (без сети — только
`OcrSettings`/`OcrEngineConfig`) и передаёт `OcrRuntimeParams` в
`native.iter_pages(..., params=params)`; оттуда параметры идут в
`paddle_fast.parse_image`/`textbook.parse_image` именованными аргументами. У всех
параметров есть дефолты, равные прежним хардкодам, поэтому вызовы `iter_pages(path, mode)`
без `params` (тесты, скрипты) не менялись.

`paddle_fast._get_engine()` кеширует движок PaddleOCR по паре `(language, ocr_version)`,
не глобальным синглтоном на первый вызов — иначе смена языка в настройках не
подхватывалась бы до перезапуска воркера.

## Библиотека: переход на реестр

`LibraryProcessingPanel.tsx` больше не хранит свой список режимов
(`STATIC_OCR_MODES`) и не стартует с захардкоженного `useState<ParserMode>("fast")`.
Панель читает `GET /api/settings/ocr`, подставляет `default_mode` как выбор по
умолчанию (пользователь может тут же переключить руками) и рисует ровно те карточки,
что вернул реестр — с тем же текстом статуса, что и в разделе настроек. Если выбранный
режим недоступен, под списком появляется прямая ссылка «Открыть параметры
распознавания» (`/setup?section=ocr&subsection=engines`) вместо тупика. Старый эндпоинт
`GET /api/material-capabilities` и схема `MaterialCapabilities` удалены целиком —
второго источника правды об OCR-движках в проекте больше нет.

## Проверка

`backend/tests/test_ocr_settings.py` — сервисный слой (`read_settings`,
`update_global_settings`, `update_engine`, `runtime_params`, живой статус с
подставленным `textbook.status`). `test_pdf_layout_parser.py::test_page_quality_threshold_is_configurable`
— порог реально переключает `ocr`/`ocr_low`. Сквозные проверки —
`backend/scripts/check_stage5.py` (реальные миграции и воркер; читает
`/api/settings/ocr` вместо удалённого `/api/material-capabilities`) и
`check_library_workspace.py` (материал-capabilities с настроенным движком). Установка
модели и запуск GPU-сервиса кнопкой проверены вручную через реальный API-контейнер:
`POST .../models/fast-en/install` → фоновая докачка недостающего файла общего
репозитория → `installed: true` → `DELETE .../models/fast-en` — до состояния диска
эти два шага дописывать `pytest`-ом не стали: тест реального сетевого похода на
Hugging Face был бы либо сетевым (нестабилен в CI), либо мокал сам huggingface_hub
целиком, теряя ценность проверки.
