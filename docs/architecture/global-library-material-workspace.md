## Зачем

До этой вертикали общий материал можно было подготовить только изнутри проекта, куда он уже подключён. Это неверно по смыслу: разбор, качество, версии и сам файл принадлежат установке, а не проекту. Теперь у них есть своё место — `/library/:materialId`, — а проектные роли, назначения и привязки остались там, где им и место.

**Граница, которую держит вся вертикаль:** в Библиотеке нет привязок, тем, покрытия, импорта программы и связывания эталонов. Она только переносит уже существующие связи при смене ревизии через общий `transfer_bindings_on_revision`.

## Модель данных

Добавлена одна таблица — `material_revisions` (миграция `20260814_0018`).

| Поле | Смысл |
| --- | --- |
| `material_id`, `revision` | Уникальная пара. Номер монотонно растёт и никогда не переиспользуется |
| `origin` | `imported · parse · manual_edit · ai_cleanup · source_refresh · restore` |
| `parser_mode` | Режим разбора, если версия получена обработкой |
| `parent_revision` | Из какой версии выросла эта |
| `task_id` | Фоновая задача-источник. Без FK: задача живёт короче версии |
| `source_storage_path`, `source_hash` | Неизменяемый снимок источника этой версии. У локального файла наследуется от родителя, у веба и YouTube свой |
| `scope` | `{"kind": "all"}` · `{"kind": "range", "page_from": …, "page_to": …}` · `{"kind": "needs_review", "pages": […]}` · `{"kind": "page", "page": N}` · `{"kind": "restore", "restored_from": N}` |
| `summary` | `page_count`, `native_page_count`, `ocr_page_count`, `review_page_count`, `diagnostics_count`, `changed_pages` |

Миграция создаёт запись `imported` для каждой уже существующей пары `(material_id, revision)`, поэтому история есть и у материалов, разобранных до этой вертикали. У таких записей `summary` пустая — это честно, а не потеряно: сводку никто не считал.

`material_fragments` получили `time_from` и `time_to`: границы сегмента у расшифровки аудио и субтитров. Проверки — оба значения неотрицательны и `time_to >= time_from`.

**Что изменилось в жизненном цикле:** страницы и фрагменты прежней ревизии больше не удаляются после успешного разбора. `_drop_unbound_fragments` убран из воркера. Историческая версия удаляется только вместе с физическим материалом.

| `POST` | `/api/materials/{id}/processing` | Запуск с режимом и областью |

Проектные маршруты сохранены и делегируют ядру после проверки `ProjectMaterial`: `service.get_page`, `page_image_path`, `update_page_text`, `start_processing`, `control_task` — тонкие обёртки.

### Вид источника

`presentation_kind` выводится один раз на сервере, а не проверками MIME по фронтенду:

```
youtube → source_kind == youtube
audio   → source_kind == audio или media_type audio/*
web     → source_kind == url
pdf     → application/pdf
image   → image/*
document→ DOCX/DOC MIME
plain_text → всё остальное поддержанное
```

Возможности (`can_compare`, `can_view_original`, `can_edit_text`, `can_run_ocr`, `can_refresh_source`, `has_outline`, `has_timeline`) выводятся из вида и фактических данных, а не хранятся отдельными флагами: хранимые флаги разъезжаются с реальностью.

`outline_source`: встроенные закладки PDF → `embedded`; иначе заголовочные фрагменты активной ревизии → `recognized`; иначе `none`. Распознанный вариант интерфейс честно подписывает «По заголовкам текста».

## Частичная обработка

Область запуска: `all`, `needs_review`, `range`.

- `needs_review` берёт неподтверждённые страницы активной версии с внутренним качеством `ocr_low`; пустой список — 409 `material_has_no_review_pages`;
- `range` доступен только для PDF, изображения и документа: у снимка веба, субтитров и расшифровки нет безопасной единицы частичного запуска — 422 `material_scope_unsupported`;
- любая область кроме `all` требует уже подготовленного материала.

Checkpoint задачи:

```json
{
  "revision": 4,
  "source_revision": 3,
  "selected_pages": [12, 13, 14],
  "next_index": 1,
  "scope": {"kind": "range", "page_from": 12, "page_to": 14}
}
```

`total` — длина выбранного списка, а не число страниц документа. Прогресс считается по `next_index`, а не по номеру страницы: у диапазона номера не начинаются с единицы.

Порядок воркера:

1. `_prepare_revision` копирует в новую версию все страницы источника, которых нет в выборке;
2. выбранные страницы разбираются заново от `selected_pages[next_index]`;
3. `rebuild_structure` собирает блоки и фрагменты **для всей версии разом** — блоки режутся по заголовкам и пересекают границы страниц, частями их собрать нельзя;
4. `transfer_bindings_on_revision` переносит привязки, `reindex_material` строит индекс;
5. только после этого меняется `Material.active_parse_revision` и записывается `MaterialRevision`.

Ошибка оставляет прежнюю активную версию нетронутой и добавляет задаче понятную ошибку.

## Версии и правки

Ручная правка, уборка текста, обновление внешнего снимка и восстановление всегда создают новую версию; изменение «на месте» запрещено. Мутация с `expected_revision`, отличной от активной, отвечает 409 `stale_material_revision` — так историческая версия остаётся read-only.

`restore_revision` клонирует страницы выбранной версии в `max_revision + 1`, заново собирает структуру, переносит привязки с текущей активной, переиндексирует и только затем активирует. Указатель назад не отматывается, история не теряется.

`refresh_source` работает только для `web` и `youtube`. Новый снимок пишется в `snapshots/{material_id}/{revision}.md` — прежний файл не перезаписывается, поэтому историческая версия читается и после обновления. Если хеш нового снимка уже принадлежит другому материалу, ответ 409 `material_refresh_duplicate` с его id, а текущий материал не меняется.

## Интерфейс

### Уточнение 26.08.2026: сравнение и ручное исправление

Шапка готового материала показывает только имя файла: название проекта и бейдж
«Готов» убраны. Рабочие и ошибочные состояния остаются видны. Подсветка строки
оглавления расширена на один малый отступ влево.

Оригинал вписывается в собственную колонку с учётом пропорций страницы и полос
прокрутки, в том числе при масштабе меньше 50%. Ручной зум сохраняет прокрутку
внутри колонки. Текст масштабируется с переносом строк; «По ширине» возвращает
его к обычному размеру. Разделитель не отбирает ширину второй колонки сверх сетки.

«Полный экран» вызывает Fullscreen API для корня документа и скрывает боковые
панели; повторное нажатие, F и Esc возвращают прежнюю раскладку. При запрете API
во встроенном браузере остаётся режим без панелей внутри окна. Корень выбран,
чтобы портальные диалоги Radix были доступны и в полном экране. То же управление
используется в проектных Материалах; Ctrl+F не включает полный экран.

Карандаш открывает редактор на текущей сцене, без диалога: оригинал слева, поле
текста и «Сохранить»/«Отмена» справа. Боковые панели временно скрыты, листание и
переключение режима недоступны. До 600px изображение и текст расположены друг
под другом. Ctrl+Enter или Ctrl+S сохраняет. В смешанных PDF поле включает OCR
из фрагментов изображений, который отсутствует в Markdown страницы. Ссылки на
локальные вырезы заменяются расшифровкой; исходные вырезы сохраняет существующий
серверный контракт. Повторное открытие ручной версии не добавляет OCR второй раз.

Редактор фиксирует страницу и номер версии при открытии, отправляет
`expected_revision` и оставляет текст при ошибке или конфликте. Во время разбора,
загрузки страницы и сравнения версий исправление недоступно. Несохранённая отмена
и возврат требуют подтверждения; перезагрузка предупреждает об уходе. Черновик
хранится в sessionStorage отдельно для материала, страницы и версии и восстанавливается
при повторном открытии редактора. Успешное сохранение и явный отказ очищают его.

Полноразмерная оболочка `/library/:materialId` включается в `AppLayout` тем же правилом, что и проектные маршруты. Список `/library` остаётся в обычной оболочке.

Три зоны — оглавление, сцена, инспектор — лежат в одной CSS-сетке на полную высоту окна; прокручивается каждая колонка отдельно, страница целиком не прокручивается. Пустых постоянных колонок нет: без оглавления левая зона исчезает.

Нейтральные компоненты просмотра не знают ни про проект, ни про привязки: проектный просмотрщик подмешивает своё через `renderFragmentOverlay` и `fragmentProps` у `StructuredPage`.

Проектная вкладка «Обработка» больше не запускает разбор: там ссылка «Открыть обработку в Библиотеке» с `returnTo` на текущую страницу проекта. Ручная правка из проекта осталась, но честно предупреждает, что изменение общее.

`QualityBadge` — единственная точка перевода: «Текст из файла», «Распознано», «Нужно проверить». Внутренние значения `native`, `ocr`, `ocr_low` остались в хранилище и в wire-формате, но в пользовательский текст не попадают.

`MaterialPage.reviewed_at` хранит пользовательскую сверку отдельно от `quality` и `confidence`. Новый OCR создаёт неподтверждённую страницу, а копирование неизменённой страницы в частичную ревизию сохраняет подтверждение. `LibraryMaterialDetailRead.page_states` отдаёт компактный статус навигации: `ocr` показывается синим, неподтверждённый `ocr_low` — жёлтым, подтверждённый `ocr_low` — как обычная страница. Счётчик и область `needs_review` учитывают только неподтверждённые страницы.

Реализации режимов «Учебник», «Облако», «Максимум» и «Эксперт» — это их этапы, здесь только честные карточки с причинами. ## Быстрый OCR и панель просмотра — 26.08.2026

Для `parser_mode=fast` интерфейс не формирует очередь ручной проверки по
уверенности OCR: скрыты проценты, предупреждение, счётчик и область запуска
`needs_review`. Это правило касается Библиотеки и просмотрщиков материалов;
другие режимы сохраняют проверку. Список Библиотеки теперь возвращает
`parser_mode`, чтобы фильтр и сводка не требовали запроса деталей каждого файла.
`quality`, `confidence`, `ocr_low_page_count` и `reviewed_at` в API и базе не
переоцениваются и не подтверждаются автоматически.

Изображение и его OCR-текст сохраняются; под картинкой текст свёрнут и помечен
как потенциально ошибочный. Изменение интерфейса не отключает OCR, индексацию
или передачу текста фрагментов в экзаменационный контекст. Исходный PDF не
переписывается и не получает скрытый текстовый слой. Текущий экзаменационный
контекст передаёт текст эталона и привязанных фрагментов в пределах бюджета,
но не двоичные изображения или весь PDF.

Карандаш в `ViewerToolbar` вызывает тот же редактор, что и панель обработки.
Во время правки он остаётся на том же месте и получает активное состояние;
нажатие закрывает редактор сразу без изменений или спрашивает, отказаться ли от
черновика. `Ctrl+Enter` и `Cmd+Enter` сохраняют изменённый текст независимо от
того, на какой части редактора находится фокус.
При загрузке страницы, просмотре старой версии, сравнении версий или занятом
сервисе действие недоступно. Иконки оглавления и правой панели включены в
общую группу инструментов; короткая вкладка «Текст» не меняет название панели
«Подготовленный текст». На узком окне группы переносятся без разрыва.

Проверка: `test_detail_reports_quality_counters_for_active_revision` для обоих
режимов проверяет передачу режима в список и детали без потери технических
счётчиков или автоматического подтверждения страниц.
