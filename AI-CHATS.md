# ИИ-чаты Tentex

Статус документа: проектный контракт и план развития на 29.08.2026.

Этот файл сводит в одном месте:

- что уже реализовано в экзаменационном чате и шлюзе внешних моделей;
- какой контекст получает модель и откуда он берётся;
- как должны работать профиль проекта, персона, строгость и навыки;
- как подключать эталонные ответы и учебные материалы;
- как искать внешние источники, сохранять оригинал или сводку и автоматически
  добавлять результат в проект;
- какой общий контур Tools нужен экзаменационному и будущему свободному режимам;
- какие части делать сейчас, а какие зависят от векторного поиска и будущих режимов.

Фактические контракты уже написанного кода остаются в
`docs/architecture/exam-chat.md` и `docs/architecture/ai-model-gateway.md`.
Если реализация расходится с этим документом, расхождение считается незакрытой
задачей, а не скрытым изменением замысла.

## 1. Роль чата в продукте

Чат — не главный экран и не замена Материалу, Эталону, Программе или истории
Попыток. Это один из инструментов Рабочей области, который помогает:

1. разобраться в текущем вопросе;
2. найти и открыть подходящее место в уже добавленных источниках;
3. потренироваться отвечать;
4. получить подсказку, задание или доспрос;
5. сдать ответ и увидеть проверяемый разбор.

Главное преимущество Tentex появляется не от самого диалога, а от связи диалога
с целью обучения: профилем проекта, Программой, эталонными ответами, Материалами,
Попытками и будущим прогрессом. Чат должен использовать эти сущности, но не
копировать их внутрь себя и не становиться отдельной базой знаний.

## 2. Основные решения

1. Внешние модели считаются stateless. При создании чата Tentex сохраняет его
   настройки, но нужный системный и предметный контекст собирается заново для
   каждого вызова. Нельзя рассчитывать, что провайдер «помнит» первый запрос.
2. Системный запрос собирается слоями: правила Tentex → режим → профиль проекта →
   персона и строгость → навык → выбранные данные → хвост разговора → текущий ввод.
3. Свободного пользовательского системного промпта нет. Пользователь выбирает
   понятные пресеты; данные из файлов и полей профиля никогда не становятся
   инструкциями для модели.
4. Навык — пользовательский сценарий с фиксированным входом, требуемым
   контекстом и проверяемым результатом. Он может открыть локальную форму,
   вызвать модельную операцию или выполнить Tool, но не равен тексту `/команда`,
   который просто дописывается в пользовательское сообщение.
5. Проверка ответа живёт внутри сценария чата, но Попытка и Оценка хранятся
   отдельно. Переписка лишь ссылается на них.
6. В текущей вертикали контекст Материалов строится из фрагментов, уже привязанных
   к теме. Поиск по всем добавленным материалам подключается как отдельный этап
   извлечения, а не как отправка целых файлов в модель.
7. Векторный поиск не блокирует экзаменационный чат. Он нужен для качественного
   смыслового поиска среди непривязанных источников, но не для использования
   эталона и уже привязанных фрагментов.
8. Любой ответ по источникам должен сохранять происхождение: материал, страницу,
   фрагмент, ревизию или хеш. Модель не создаёт ссылки на источники из воздуха.
9. Плохой OCR нельзя исправить промптом или векторным поиском. Фрагмент `ocr_low`
   остаётся сомнительным свидетельством и ведёт к оригиналу страницы.
10. Отключённый внешний ИИ не маскируется под чат. Остаются форма сдачи ответа,
    локальный билет и детерминированные ступени проверки.
11. Tools закладываются как общий серверный реестр и детерминированный executor.
    Модельный tool calling позднее становится только способом выбрать Tool; он
    не получает права обходить проверки, подтверждения и журнал Tentex.
12. Внешний поиск не должен тратить модельные токены на то, что умеет поисковый
    провайдер. Модель подключается после выбора результата: для сводки или, при
    доказанной необходимости, компактного переранжирования нескольких сниппетов.

## 3. Термины

| Термин | Значение |
| --- | --- |
| Чат | Сохранённая `ChatSession` в одной области Программы |
| Реплика | Обычное сообщение пользователя или экзаменатора |
| Типизированный блок | Форма ответа, задание, вердикт, доспрос или итог билета, который рисует Tentex по проверенной схеме |
| Режим | Общий контракт поведения: экзаменационный, учебниковый или свободный |
| Персона | Тон и способ объяснения; не меняет факты и рубрику |
| Строгость | Допустимая полнота ответа; влияет на проверку, но не на содержание эталона |
| Навык | Явное действие `/ответ`, `/вопрос`, `/подсказка`, `/точность`, `/задание` или `/билет` |
| Контекстный пакет | Конкретный набор данных, собранный сервером для одного вызова |
| Manifest | Безопасный список включённых и исключённых частей контекста с id, ревизиями, хешами и объёмом |
| Снимок контекста | Данные, на которых была создана Попытка или реплика; нужны для воспроизводимости |
| Память раздела | Короткая сводка старых обычных реплик в одной области Программы |
| Команда | Элемент палитры пользователя; может открыть форму, запустить навык или Tool |
| Tool | Типизированная серверная операция с разрешениями, подтверждением и журналом выполнения |
| Найдено | Представление Материалов, добавленных в конкретный проект через внешний поиск |

## 4. Что уже реализовано

### 4.1. Экзаменационный чат

Работают:

- несколько чатов на одном вопросе;
- сохранённый серверный черновик;
- потоковый ответ через SSE и остановка потока;
- сохранение частичного остановленного ответа;
- последние 12 сообщений в контексте обычного ответа;
- форма `Сдать ответ`;
- неизменяемая Попытка и её номер по теме;
- проверка лесенкой `точное совпадение → ключевые термины → ИИ-судья`;
- Оценка с исходом, группами `Засчитано / Упущено / Неверно` и проверенными
  сервером позициями цитат;
- фактическая модель, токены, стоимость, курс и признак exact-кэша;
- отдельная самооценка;
- история Попыток вне переписки;
- повторная проверка незавершённой Попытки;
- офлайновая сдача ответа без диалога с моделью.

### 4.2. Текущий контекст

Обычная реплика получает:

```text
системный prompt экзаменационного ответа
→ формулировка текущего узла
→ активный эталонный ответ, если он есть
→ до 6 уже привязанных фрагментов по 1500 символов
→ до 12 последних обычных реплик
→ текущий текст пользователя
```

Общий бюджет эталона и фрагментов — 12 000 символов. Фрагменты берутся из
активных привязок темы, а не находятся поиском по всей Библиотеке на каждом
сообщении.

ИИ-судья получает формулировку вопроса, снимок эталона, привязанные фрагменты и
текст одной Попытки. Хвост чата ему не передаётся. Это важный инвариант: разговор
не должен подсказывать судье, какой исход удобнее выставить.

### 4.3. Шлюз внешних моделей

Все обращения проходят через `ModelGateway`. Он уже умеет:

- выбирать модель по роли и настройкам;
- проверять требуемые возможности модели;
- учитывать глобальный и ролевой выключатели;
- оценивать токены и стоимость до вызова;
- требовать подтверждение большого или дорогого запроса;
- применять дневной и операционный лимиты;
- валидировать структурный ответ Pydantic-схемой;
- потоково выдавать текст;
- вести `AiRun` с фактической моделью, токенами и стоимостью;
- использовать exact-кэш там, где он разрешён;
- хранить ключи отдельно от потребителей.

Платный вызов автоматически не повторяется, fallback между провайдерами не
делается, полный prompt и ответ модели не копируются в журнал.

Зарегистрированные роли, относящиеся к чату:

| Роль | Назначение | Сейчас |
| --- | --- | --- |
| `exam_chat_reply` | Потоковый ответ экзаменатора | работает |
| `exam_answer_judge` | Структурная проверка Попытки | работает |
| `exam_chat_memory` | Сжатие старой истории раздела | зарегистрирована, не вызывается |
| `speech_transcription` | Диктовка в композер | зарегистрирована, транспорт не реализован |

### 4.4. Что пока отсутствует

- профиль проекта не попадает в запрос чата;
- персона и строгость нельзя менять в интерфейсе;
- обычный ответ не использует выбранную персону и строгость;
- у чата нет выбора модели;
- контекст нельзя посмотреть или исключить по частям;
- подтверждение большого контекста не продолжает исходную отправку;
- нет палитры навыков, билета, доспроса, возражения и памяти раздела;
- нет диктовки;
- нет автоматического поиска по всем материалам проекта;
- у обычных ответов нет проверяемых ссылок на фрагменты;
- учебниковый и свободный чаты остаются будущими режимами.

## 5. Как должен собираться запрос

### 5.1. Два уровня состояния

`ChatSession` хранит длительные настройки: проект, область, текущий узел,
персону, строгость, override модели, включённые части контекста и черновик.

`ContextAssembler` перед каждым вызовом читает актуальные данные проекта и
создаёт неизменяемый `ContextBundle`. Его manifest и существенные данные
сохраняются у отправленной реплики или Попытки. Поэтому:

- изменение профиля влияет только на будущие вызовы;
- старая Попытка продолжает проверяться по своему снимку;
- интерфейс может точно показать, что ушло в конкретный запрос;
- повторная проверка не зависит от случайно изменившегося файла.

### 5.2. Порядок слоёв

```text
1. Непереопределяемые правила Tentex
2. Prompt режима
3. Карточка профиля проекта
4. Персона и строгость
5. Prompt навыка или обычного сообщения
6. Текущий узел и выбранные доменные данные
7. Извлечённые фрагменты с происхождением
8. Digest Попыток и память раздела
9. Ограниченный хвост текущего чата
10. Текущий ввод пользователя
```

Слои 3 и 6–9 передаются как данные в размеченных блоках. Текст из профиля,
эталона, файлов и переписки не может отменять системные правила или выбирать
инструменты.

### 5.3. Профиль проекта

В базе уже есть почти весь нужный паспорт: предмет, цель, начальный и целевой
уровень, важное и исключённое, формат экзамена, число вопросов, требования
преподавателя, время и процедура экзамена.

Не надо отправлять все поля в каждый запрос. Сервер строит компактную карточку
по назначению вызова:

| Поле профиля | Обычный ответ | Проверка | Билет и вопрос | Планирование |
| --- | --- | --- | --- | --- |
| Предмет | да | да | да | да |
| Цель и целевой уровень | да | да | да | да |
| Текущие знания | для глубины объяснения | нет | для сложности | да |
| Важное / исключённое | да | да | да | да |
| Формат экзамена | да | да | да | да |
| Требования преподавателя | да | да | да | нет |
| Процедура и время экзамена | по запросу | при уместности | да | да |
| Режим и объём занятий | нет | нет | нет | да |
| Дедлайн | нет | нет | нет | да |

Пустые поля не превращаются в общие догадки. Если пользователь спрашивает, как
проходит экзамен, экзаменатор пересказывает только сохранённую процедуру и явно
говорит, чего в профиле нет.

Рекомендуемый внутренний вид:

```json
{
  "subject": "Теория вероятностей",
  "target_outcome": "уверенно отвечать устно",
  "exam_format": "билеты",
  "instructor_requirements": "сначала определение, затем пример",
  "exam_procedure": "два вопроса и один доспрос",
  "important": "строгие формулировки определений",
  "excluded": "доказательства предельных теорем"
}
```

Это пример данных, а не готовый system prompt.

## 6. Персона и строгость

Персона и строгость — разные оси.

| Персона | Меняет | Не меняет |
| --- | --- | --- |
| Спокойный преподаватель | объясняет, поддерживает, задаёт наводящие вопросы | факты, эталон, исход проверки |
| Нейтральный экзаменатор | отвечает кратко и формально | факты, эталон, исход проверки |
| Придирчивый рецензент | указывает оговорки и просит точные формулировки | факты и состав обязательных пунктов |

| Строгость | Правило проверки |
| --- | --- |
| Мягко | засчитывается верная суть при неполной формулировке |
| Обычно | требуются основные пункты, допускаются несущественные пропуски |
| Строго | требуются существенные определения, условия и оговорки эталона |

Требования конкретного преподавателя приходят из профиля проекта и стоят выше
стилевого пресета. Персона не должна изображать реального человека или выдумывать
его мнение.

Изменение действует на будущие ответы. Использованные значения сохраняются в
снимке реплики и Попытки. У обычного диалога и судьи может быть разный текст
prompt, но одна семантика пресетов.

## 7. Prompt-архитектура

### 7.1. Почему нужны отдельные prompts

Обычный ответ, подсказка и проверка точности имеют разные критерии успеха.
Один универсальный prompt быстро обрастёт исключениями и начнёт смешивать
объяснение с оценкой. Поэтому у каждого режима и навыка есть собственный
контракт, а общими остаются только безопасность, профиль и формат источников.

### 7.2. Слои prompt

| Слой | Пример ответственности | Версионирование |
| --- | --- | --- |
| `base` | язык, недоверие к данным, запрет HTML/JSX и выдуманных источников | `chat-base-vN` |
| `mode` | экзаменатор, учебный тьютор или свободный помощник | `exam-mode-vN` |
| `persona` | тон и способ взаимодействия | версия набора пресетов |
| `strictness` | допустимые упущения | версия правил проверки |
| `skill` | подсказка, вопрос, точность, задание, билет | `skill-name-vN` |
| `schema` | допустимый структурный результат | версия Pydantic-схемы |

`AiRun.prompt_version` должен хранить эффективную версию операции, например
`exam-mode-v2/hint-v1`. Иначе после изменения одного навыка журнал и exact-кэш
не отличат старое поведение от нового.

### 7.3. Граница между моделью и приложением

Модель пишет Markdown обычной реплики и содержимое строго заданных полей. Она
не генерирует React, HTML, кнопки, id сущностей или произвольный `payload_kind`.

Tentex:

- выбирает навык;
- собирает контекст;
- вызывает нужную роль и prompt-вариант;
- проверяет структурный ответ;
- создаёт типизированный блок;
- сохраняет Попытку, Оценку и связи;
- решает, влияет ли результат на прогресс.

В ближайшей версии известные навыки остаются явными сценариями приложения, но
серверные действия уже проходят через общий контур Tools. Это не означает
автономного агента:

- `/ответ` открывает локальную форму и вообще не вызывает Tool;
- `/вопрос`, `/подсказка`, `/точность` и `/задание` вызывают фиксированные
  модельные операции с отдельными схемами;
- `Найти в материалах` вызывает read-only Tool локального поиска;
- будущие `Найти источники`, `Сохранить оригинал` и `Сделать сводку` используют
  тот же executor, но требуют внешнего доступа или записи и потому явного
  подтверждения;
- когда появится model-native tool calling, модель сможет предложить вызов из
  опубликованного реестра, но Tentex всё равно валидирует аргументы, права,
  бюджет, подтверждение и результат.

Так сейчас появляется проверяемый общий шов для экзаменационного и свободного
изучения, но не появляется преждевременный агентный цикл с неизвестным числом
шагов и расходов.

## 8. Навыки экзаменационного чата

| Навык | Что делает модель | Что делает Tentex | Прогресс |
| --- | --- | --- | --- |
| `/ответ` | не требуется для открытия формы | создаёт форму; после сдачи — Попытку и Оценку | да |
| `/вопрос` | формулирует один вопрос по узлу и выбранному контексту | валидирует блок и прикладывает форму | после сдачи |
| `/подсказка` | даёт наводку без готового ответа; следующий уровень сильнее | хранит уровень в ветке и будущей Попытке | само действие — нет |
| `/точность` | находит фактические неточности в введённом тексте | показывает источники и метку `Не является оценкой`; Попытку не создаёт | нет |
| `/задание` | создаёт мини-кейс с условием и ожидаемым форматом | валидирует блок и прикладывает обычную форму ответа | после сдачи |
| `/билет` | не выбирает список вопросов | сервер выбирает уникальные узлы и ведёт последовательность | по каждой Попытке |

### 8.1. Обычная реплика

Цель — объяснить или обсудить тему, не выставляя Оценку. Ответ опирается на
включённые источники. Если основания недостаточно, модель говорит об этом и
предлагает открыть Материал или выполнить поиск, а не достраивает факт по памяти.

### 8.2. Сдать ответ

Форма создаётся локально и не требует модели. После отправки:

```text
неизменяемая Попытка
→ точное совпадение
→ проверка ключевых терминов
→ при неоднозначности ИИ-судья
→ Оценка
→ независимая самооценка пользователя
```

Эталон и контекст замораживаются в Попытке. ИИ-судья не получает память чата.
Отсутствие эталона не запрещает сдачу, но результат не называется полноценной
проверкой.

### 8.3. Попросить вопрос

Вход: текущий узел, профиль экзамена, выбранный контекст и желаемая сложность,
если она появится в интерфейсе. Выход: один вопрос и краткий критерий ожидаемого
ответа, скрытый до проверки. Нельзя задавать вопрос за пределами `excluded` или
на факт, для которого нет основания в эталоне/источниках.

### 8.4. Получить подсказку

- уровень 1 — направление или термин;
- уровень 2 — структура ответа или следующий шаг;
- уровень 3 — почти готовый ключевой фрагмент без полного ответа.

Уровень считается в пределах ветки задания/вопроса, сохраняется в Попытке и
впоследствии уменьшает силу свидетельства, когда появится общий движок прогресса.

### 8.5. Проверить точность

Проверяется конкретный текст пользователя, а не его знания. Результат состоит
из тезиса, статуса `подтверждено / спорно / неверно / нет основания`, пояснения
и ссылок на использованные фрагменты. Это не Оценка и не создаёт Попытку.

### 8.6. Получить задание

Первая версия — только текстовый теоретический или прикладной мини-кейс. Модель
возвращает условие, ожидаемый формат и критерии. Исполняемый код, SQL, загрузка
файла и песочница не маскируются под этот блок.

### 8.7. Вытянуть билет

Список выбирает сервер из активных вопросов и задач без повторов. Модель может
вести собеседование и задавать доспрос, но не меняет состав билета. Итог содержит
вопросы, исходы Попыток, главное упущение и фактическую стоимость. Процент
готовности по одному билету не показывается.

### 8.8. Доспрос и возражение

Доспрос создаёт дочернюю Попытку через `parent_attempt_id`, получает отдельную
Оценку и не переписывает исходный вердикт. После ответа строится `Итог ветки`.

`Не согласен` сохраняет причину и комментарий отдельно от Оценки. Автоматическая
платная перепроверка другой моделью в первую версию не входит.

## 9. Материалы, поиск и RAG

### 9.1. Что можно делать уже сейчас

Эталонный ответ и привязанные к теме фрагменты уже являются рабочим предметным
контекстом. Для экзаменационного чата этого достаточно, чтобы:

- объяснять текущий вопрос;
- сравнивать ответ с эталоном;
- давать подсказку;
- проверять точность в пределах известных источников;
- показывать пользователю конкретные страницы рядом с чатом.

То есть ждать эмбеддингов для доводки чата не нужно.

Существующий FTS5/BM25 можно использовать для явного действия `Найти в
материалах`. Оно хорошо ищет термины и точные формулировки, но хуже находит
синонимичные объяснения. Поэтому до этапа 6 оно не должно молча подмешивать
«лучшие совпадения» в каждый запрос и выдавать их за полный смысловой поиск.

### 9.2. Что включать до векторного поиска

По умолчанию:

1. формулировка текущего узла;
2. активный эталон;
3. только уже привязанные к узлу фрагменты;
4. выбранные пользователем результаты явного BM25-поиска;
5. хвост чата и digest Попыток.

Все остальные материалы проекта не включаются автоматически. Это соответствует
текущей вертикали: сначала чат работает на эталонах и проверенных/видимых
привязках, затем получает поиск по всей коллекции.

### 9.3. После этапа 6

Целевой поиск внутри добавленных Материалов:

```text
текст пользователя + заголовок узла
→ фильтр по проекту и активным ревизиям
→ BM25-кандидаты
→ векторные кандидаты
→ слияние рангов RRF
→ усиление уже привязанных фрагментов
→ склейка соседних фрагментов
→ дедупликация
→ бюджет контекста
→ ContextBundle
```

Начальный запрос не обязательно переписывать моделью: достаточно исходного
текста и заголовка темы. Модельное расширение запроса добавляется только после
проверки, что гибридного поиска недостаточно.

Фильтры и сигналы ранжирования:

- только материалы текущего проекта;
- только активная ревизия;
- выбранные пользователем источники, если фильтр задан;
- роль источника и приоритет;
- привязка к текущему узлу как сильный boost, а не единственный допуск;
- `native` и уверенный `ocr` выше `ocr_low`;
- разнообразие материалов, чтобы top-k не состоял из соседних дублей;
- соседние фрагменты для восстановления оборванного определения.

Векторный поиск решает поиск по смыслу, но не проверяет истинность и не лечит
OCR. Для Оценки эталон остаётся главным основанием, а найденные материалы —
дополнительным свидетельством с явным происхождением.

### 9.4. Как показывать источники

Каждому включённому фрагменту сервер назначает стабильную ссылку вида `S1`,
`S2`. Модель может сослаться только на эти идентификаторы. После завершения
ответа сервер:

1. отбрасывает неизвестные id;
2. сохраняет использованные `fragment_id`, `material_id`, страницу и ревизию;
3. прикладывает ссылки к `ChatMessage`;
4. позволяет открыть страницу в соседней зоне;
5. показывает предупреждение качества для `ocr_low`.

Цитата в Оценке дополнительно проверяется точным поиском в тексте Попытки, как
это уже сделано. Ссылки обычного объяснения подтверждают происхождение, но сами
по себе не доказывают корректность вывода модели.

## 10. Контекстные чипы и бюджет

Над композером показываются реальные части будущего запроса:

`Вопрос` · `Профиль` · `Эталон` · `Материал · N` · `Попытки` ·
`История раздела`.

`Мой конспект` появляется только после реализации сущности Конспекта и по
умолчанию выключен.

Каждый чип:

- раскрывает точный состав;
- позволяет исключить часть;
- показывает объём;
- не включается обратно молча;
- объясняет, если без него выбранный навык недоступен.

Рекомендуемый порядок урезания при превышении бюджета:

1. убрать дубли и соседние повторы;
2. сократить старую память раздела;
3. уменьшить число найденных непривязанных фрагментов;
4. уменьшить хвост обычного разговора;
5. сохранить текущий вопрос, профильные ограничения и эталон;
6. попросить подтверждение, если запрос всё ещё превышает пользовательский порог.

Нельзя обрезать фрагмент посередине формулы или молча скрывать обязательный
источник. Manifest помечает `included`, `excluded`, `truncated` и причину.

## 11. Память

Полная история всех чатов во внешний запрос не уходит.

Контекст связности состоит из:

1. ограниченного хвоста текущего чата;
2. детерминированного digest последних Попыток области;
3. модельной сводки старых обычных реплик до 800 оценочных токенов.

Память пересобирается только при переполнении хвоста. Она хранит факты разговора,
не подменяет эталон и не содержит скрытого вердикта о знаниях. Пользователь видит
её полный текст в чипе и может исключить.

Сбой `exam_chat_memory` не блокирует сообщение: остаются хвост и digest Попыток.
ИИ-судья не получает модельную память раздела никогда. История Попыток может
попасть судье только отдельным, явно включённым контрактом и не должна влиять на
фактическую рубрику текущего ответа.

Область памяти — ближайший предок-раздел; у плоской программы — весь экзамен.
История чатов и восстановление последнего чата работают по этой области, а не
только по одному вопросу.

## 12. Диктовка

Диктовка заполняет композер, а не создаёт устную Попытку.

```text
запись в браузере
→ временная передача аудио
→ speech_transcription
→ вставка транскрипта в позицию курсора
→ ручная правка
→ обычная отправка пользователем
→ удаление аудио
```

Транскрипт никогда не отправляется в чат автоматически. Ненастроенная речевая
модель ведёт в Параметры → ИИ; отказ браузера показывается рядом с композером.
Хранение аудио для настоящих устных Попыток — отдельная задача позднего этапа.

## 13. Целевые данные

Уже есть: `ChatSession`, `ChatMessage`, `Attempt`, `Grade`, `AiRun`,
`parent_attempt_id`, `section_scope_node_id`, `context_snapshot` и manifest.

Для доводки экзамена нужны:

| Сущность или поле | Назначение |
| --- | --- |
| `ChatSession.mode` | текущий режим поведения; первая рабочая версия — `exam` |
| `ChatSession.model_override` | явная модель текущего чата |
| `ChatSession.context_flags` | включённые части контекста |
| `ChatMessage.skill` | какая серверная операция создала сообщение |
| `ChatMessage.source_refs` или типизированный payload | проверенные ссылки обычного ответа |
| `ChatToolRun` | состояние, безопасные аргументы и результат выполнения Tool |
| `Attempt.hint_level` | использованные подсказки |
| `Attempt.ticket_run_id` | принадлежность билету |
| `TicketRun` | область, порядок, уникальные узлы, позиция и состояние |
| `GradeDispute` | причина несогласия без изменения Оценки |
| `ChatSectionMemory` | текст, покрытый диапазон, токены, версия и состояние |

Полный текст профиля не дублируется в `ChatSession`. Для каждой отправки
сохраняются профильный fingerprint и использованная компактная карточка. Полный
контекст обязательно замораживается у Попытки; для обычной реплики достаточно
manifest и выбранных source refs, если политика хранения не требует полного
текста.

## 14. Целевые серверные операции

Названия путей уточняются при реализации, но границы должны остаться такими:

| Операция | Результат |
| --- | --- |
| изменить экзаменатора | персона, строгость и модель только для будущих вызовов |
| изменить контекст | сохранённые flags без молчаливого возврата исключённых частей |
| preview контекста | точный manifest, объём, модель и стоимость до отправки |
| отправить сообщение | потоковая реплика и проверенные source refs |
| выполнить навык | типизированный результат конкретной схемы |
| сдать ответ | Попытка → проверка → Оценка |
| создать доспрос | дочерняя Попытка и отдельный вердикт |
| запустить/продолжить билет | серверная последовательность уникальных узлов |
| сохранить возражение | отдельная запись без изменения Grade |
| распознать диктовку | редактируемый текст без автоотправки |
| получить capabilities | доступные режимы, команды и Tools с причиной недоступности |
| выполнить Tool | валидированный запуск с журналом и обязательным подтверждением по политике |

`preview` и фактический вызов должны собирать один и тот же `ContextBundle` или
проверять его fingerprint. Иначе пользователь подтвердит один объём, а уйдёт
другой.

## 15. Ошибки и безопасность

### 15.1. Недоверенные данные

Текст эталона, профиля, фрагментов, OCR и сообщений размечается как data. Команды
внутри него не исполняются. Модель не получает ключи, локальные пути и внутренние
SQL-id, кроме безопасных публичных идентификаторов источников.

Markdown рендерится собственным безопасным подмножеством без присланного HTML и
JSX. Типизированные блоки появляются только после серверной валидации схемы.

### 15.2. Отдельные состояния

Интерфейс не сводит всё к «что-то пошло не так». Различаются:

- внешний ИИ выключен;
- роль выключена;
- модель не настроена или несовместима;
- провайдер недоступен;
- превышен лимит;
- требуется подтверждение большого контекста;
- поток остановлен;
- нет эталона;
- нет привязанных материалов;
- найден только `ocr_low`;
- память не обновилась;
- диктовка не распознана;
- структурный ответ не прошёл схему;
- команда или Tool пока недоступны в этом режиме;
- Tool ждёт подтверждения;
- внешний источник недоступен, изменился или запрещён политикой загрузки;
- источник сохранён, но уверенной автоматической Привязки не получилось.

Черновик, Попытка и уже сохранённый вердикт не теряются из-за сбоя следующего
внешнего вызова. Повторяется только упавшая операция.

## 16. Будущие режимы

### 16.1. Учебниковый чат

Появляется после настоящей учебниковой вертикали. Его режим — тьютор, а не
экзаменатор. Основной контекст: цель обучения, текущая тема, основной и
дополнительные источники, Урок, Конспект и история занятий. Он объясняет,
сравнивает источники и создаёт упражнения, но не выдаёт экзаменационный вердикт
без явной оцениваемой Активности.

### 16.2. Свободное изучение

Проектируется после экзаменационного и учебникового путей. Без программы и
покрытия чат легко превращается в универсальную базу знаний, что выходит за
границы продукта. Поэтому режим должен сначала создать или выбрать учебную цель,
а затем использовать те же механизмы источников и Активностей.

При этом внутри экзаменационного проекта появится более узкий режим с подписью
`Разобраться`. Он сохраняет активный Узел программы, профиль и Материалы, но
говорит как тьютор и не создаёт Оценку без явной команды `Сдать ответ`. Это и есть
«свободное изучение в режиме экзамена»: не новый тип проекта, а другой контракт
одной сессии. Поиск внешних источников доступен и в `Экзамене`, и в
`Разобраться`.

### 16.3. Исследовательские команды

`Найти источники`, `Объяснить по источникам`, `Сравнить источники`, `Сделать
обзор` и `Глубокое исследование` — отдельная будущая группа общей палитры. Поиск
по уже добавленным Материалам не равен поиску во внешнем интернете. Внешний Быстрый
поиск сначала явно импортирует найденный источник в Библиотеку; Глубокое
исследование работает фоном поверх этого контура.

### 16.4. Поиск и автоматическое добавление внешних источников

Функция обязательно входит в будущее развитие, но не в первую кодовую итерацию.
Она доступна из экзаменационного чата и позднее из свободного изучения через один
Tool `search_external_sources`. Это не отдельный «интернет-чат».

Пользователь задаёт:

- что нужно найти;
- тип: `любой`, `статья`, `видео` или `научная публикация`;
- при необходимости язык, свежесть и требование открытого доступа.

Активный вопрос или тема подставляются в запрос как видимый уточняющий контекст.
Tentex не просит модель сочинить поисковую строку на каждом запуске. Первая
версия строит её детерминированно из пользовательского текста и названия узла,
а затем вызывает специализированный поисковый адаптер.

```text
запрос пользователя + текущая тема + фильтры
→ поисковые провайдеры
→ нормализация URL/DOI/video id
→ локальная дедупликация и ранжирование метаданных
→ 5–8 карточек результатов
→ выбор одного результата
→ сохранить оригинал ИЛИ получить сводку
→ существующий конвейер Материала
→ локальный поиск фрагментов
→ машинная Привязка к активной теме
```

#### Как экономить токены

1. Поисковый запрос и фильтры обрабатываются без модели.
2. В prompt не уходят полные поисковые выдачи: только выбранный источник.
3. Сводка строится после загрузки выбранного оригинала, а не по рекламному
   сниппету поисковика.
4. Результат сводки кэшируется по хешу содержимого, версии prompt и модели.
5. Если качества обычного ранжирования не хватает, опциональный дешёвый
   переранжировщик получает не более 20 коротких записей `заголовок + источник +
   сниппет`; по умолчанию он выключен.
6. Повторный запрос переиспользует сохранённые метаданные и не пересуммирует уже
   известную ревизию источника.

#### Что видит пользователь

В выдаче показываются название, тип, автор/канал/издание, дата, короткий сниппет,
доступность полного текста и домен. Для результата доступны два разных действия:

- `Сохранить оригинал` — загрузить статью, PDF или транскрипт;
- `Краткая сводка` — сначала получить и зафиксировать оригинал, затем создать
  производную сводку с явной ссылкой на него.

Сводка не подменяет источник. Даже если пользователь добавляет в рабочий набор
только краткую версию, Tentex хранит происхождение, canonical URL, дату
получения, хеш исходного содержимого и связь с оригинальной ревизией.

После подтверждения результат появляется в Материалах проекта в представлении
`Найдено`. Это свойство связи `ProjectMaterial`, а не глобального `Material`:
один и тот же файл может быть найден в одном проекте и добавлен вручную в другом.
Рекомендуемые будущие поля:

- `ProjectMaterial.added_via = manual | search`;
- `ProjectMaterial.source_search_result_id`;
- `SourceSearch`: проект, чат, узел, запрос, фильтры, статус, время;
- `SourceSearchResult`: нормализованные метаданные, позиция, canonical id и
  ссылка на созданный `Material`, если он был сохранён.

`SourceSearch` хранится отдельно от `ChatToolRun`, потому что пользователь должен
видеть запрос в Материалах и запускать его повторно после окончания чата. Повтор
создаёт новую ревизию выдачи, не удаляет старые Материалы и не меняет их молча.

#### Импорт и автоматическая Привязка

Нужно переиспользовать уже существующий безопасный импорт URL и транскриптов
YouTube, разбор Материала и файловое хранилище. Для научных PDF, DOI и других
видеоплатформ добавляются адаптеры, а не второй конвейер документов.

После успешного разбора Tentex:

1. прикрепляет Материал к проекту как `ADDITIONAL` с назначением
   `STUDY_SOURCE` и `added_via=search`;
2. ищет фрагменты по исходному запросу и активной теме;
3. создаёт 1–3 Привязки со статусом `machine` и механизмом `search`, только если
   результат прошёл порог уверенности;
4. показывает созданные Привязки и позволяет подтвердить, снять или заменить их.

Если уверенности нет, Материал всё равно остаётся в `Найдено` с честным статусом
`Привязка не создана`. Нельзя привязывать весь документ к теме только потому,
что он пришёл из её поискового запроса.

#### Ограничения и подтверждения

- Поиск read-only и может запускаться сразу.
- Загрузка внешнего содержимого, создание сводки с платной моделью и добавление
  в проект требуют явного действия пользователя.
- Модель не может сама скачать или прикрепить найденный результат.
- Действуют существующая защита от SSRF, лимиты размера, типы файлов и журнал
  происхождения.
- Удаление результата поиска не удаляет уже импортированный Материал.

## 17. Общий контур Tools

### 17.1. Выбранная архитектура

Рекомендуется средний вариант между двумя крайностями:

| Вариант | Плюс | Почему не выбирается сейчас |
| --- | --- | --- |
| Сразу дать модели native tools и автономный цикл | максимальная гибкость | меняет transport/gateway, требует потоковых tool calls, лимитов шагов и совместимости провайдеров до появления реального сценария |
| Оставить только отдельные endpoints | минимальная работа | экзаменационный и свободный режимы начнут дублировать разрешения, подтверждения и журнал |
| **Общий `ToolRegistry` + детерминированный `ToolExecutor`** | один контракт для UI и будущей модели | выбранный вариант; model-native planner подключается позднее поверх него |

Tools живут в общем backend-модуле, а не внутри `exam`, потому что поиск,
импорт и сводка нужны нескольким режимам. Реестр не зависит от конкретного
провайдера модели.

### 17.2. Контракт Tool

Каждый Tool объявляет:

- стабильный `key`, название, описание и иконку-категорию;
- режимы и условия доступности;
- Pydantic-схемы входа и результата;
- эффект: `read`, `write` или `external`;
- политику подтверждения;
- тип блока результата для UI;
- обработчик, таймаут и безопасный код ошибки.

`ToolExecutor` выполняет одинаковую последовательность:

```text
найти spec
→ проверить режим и доступность
→ валидировать вход
→ проверить проект/чат/узел
→ запросить подтверждение по политике
→ создать ChatToolRun
→ выполнить handler
→ валидировать результат
→ сохранить итог
→ создать типизированный блок чата при необходимости
```

В журнале не хранятся ключи провайдера и полные тела внешних документов.
Большой результат становится Материалом или отдельной доменной сущностью, а
`ChatToolRun` хранит ссылку и компактный итог.

### 17.3. Команда, навык и Tool — не одно и то же

- Команда — то, что выбирает пользователь в палитре.
- Навык — модельное поведение с prompt и схемой результата.
- Tool — серверное действие над данными или внешним миром.

Например, `/ответ` — команда, которая открывает форму без модели и Tool;
`/точность` — команда, запускающая навык; `Найти в материалах` — команда,
запускающая Tool; `Найти источники` позднее запускает цепочку нескольких Tools.
Так интерфейс остаётся понятным, а backend не называет tool calling любую кнопку.

### 17.4. Что реально входит в первую итерацию

- реестр и executor;
- журнал `ChatToolRun`;
- capability-ответ для UI с причиной недоступности;
- настоящий read-only Tool `search_project_materials` поверх текущего FTS5/BM25;
- заблокированные спецификации будущих `search_external_sources`,
  `import_found_source` и `summarize_found_source` с меткой `Позже`;
- адаптерная граница, через которую native tool calling сможет использовать те
  же specs, но без реализации агентного цикла.

Это доказывает архитектуру реальным локальным поиском и не выдаёт заглушку за
работающий внешний интернет.

## 18. Очередь реализации

### Срез A. Контекст и управляемый экзаменатор

- добавить профиль проекта в `ContextAssembler`;
- разделить base/mode/persona/strictness prompts и версионировать их;
- добавить выбор персоны, строгости и модели;
- добавить context flags, чипы и точный preview;
- продолжать отправку после подтверждения большого контекста;
- сохранить снимки использованных настроек.

Результат: на реальном проекте экзаменатор знает сохранённую процедуру и
требования преподавателя, а пользователь видит, на чём основан каждый вызов.

### Срез B. Основные навыки

- `/ответ`, `/вопрос`, `/подсказка`, `/точность`, `/задание`;
- отдельные prompt-варианты и схемы;
- уровень подсказки в Попытке;
- проверяемые source refs у обычных и skill-ответов;
- пустое состояние с тремя главными действиями.

Результат: чат становится тренажёром, а не только окном свободной переписки.

### Срез C. Экзаменационный протокол

- билет;
- доспрос и `Итог ветки`;
- возражение;
- память раздела;
- история чатов по области;
- диктовка в композер.

Результат: можно пройти связное экзаменационное собеседование и сохранить все
результаты без смешивания их с перепиской.

### Срез D. Поиск по всей коллекции

После этапа 6:

- локальные эмбеддинги и `sqlite-vec`;
- гибрид BM25 + vector через RRF;
- склейка соседей и дедупликация;
- автоматическое извлечение по явному пользовательскому запросу;
- открытие использованного фрагмента рядом с чатом;
- тесты качества на реальных предметах и русском языке.

Результат: вопрос «где это объясняется в моих материалах?» находит смысловые
совпадения даже без готовой привязки.

### Срез E. Внешние источники

После стабилизации локального поиска и импорта:

- адаптеры поиска статей, видео и научных публикаций;
- сохранённые `SourceSearch` и повтор запроса из Материалов;
- карточки результатов и выбор `оригинал / сводка`;
- представление `Найдено`;
- импорт через существующий конвейер и машинные Привязки;
- кэш сводок, лимиты, подтверждения и проверка происхождения;
- затем — сравнение источников и фоновое Глубокое исследование.

Результат: пользователь находит новый источник из текущей темы, осознанно
добавляет его в проект и сразу получает проверяемую связь с Программой.

## 19. Критерии готовности

Чат считается доведённым для текущей экзаменационной вертикали, когда:

1. профиль проекта заметно и проверяемо влияет на будущие реплики;
2. персона меняет тон, строгость — допустимые упущения, но ни одна не меняет факты;
3. пользователь видит и управляет точным составом контекста;
4. эталон и привязанные Материалы реально используются со ссылками на страницы;
5. все шесть экзаменационных навыков проходят от выбора до сохранённого результата;
6. билет, доспрос и возражение не переписывают исходные Попытки и Оценки;
7. старые результаты воспроизводимы после изменения профиля, эталона или настроек;
8. большой запрос подтверждается без потери введённого текста;
9. остановка и внешняя ошибка не заставляют ленту мигать и не теряют данные;
10. при выключенном ИИ честно остаётся только резервный локальный контур;
11. на нескольких реальных предметах модель не выдумывает источник и корректно
    признаёт недостаток или низкое качество данных;
12. поиск по непривязанным материалам не объявляется полноценным до проверки
    гибридного контура этапа 6.

## 20. Решения, принятые по умолчанию

- Экзаменационные и исследовательские команды визуально разделены в одной
  палитре; недоступные команды честно помечаются `Позже`.
- Список чатов и память группируются по ближайшему разделу, а не только по узлу.
- Формулировка текущего вопроса остаётся в форме ответа и дереве; шапка может
  освободить место под область памяти и контрол экзаменатора.
- `Мой конспект` не показывается до появления реальной сущности Конспекта.
- До векторного поиска чат автоматически использует только эталон и привязанные
  фрагменты; BM25 вызывается явно.
- После векторного поиска извлечение остаётся управляемым и видимым: целые файлы
  никогда не отправляются в prompt без отбора и бюджета.
- Общий `ToolRegistry` и детерминированный executor появляются до свободного
  агента; native tool calling позднее подключается как планировщик поверх них.
- В первой итерации настоящий Tool только один — локальный поиск в Материалах.
  Внешний поиск, импорт результата и сводка видны как будущие возможности и не
  имитируются фальшивыми ответами.
- Профиль проекта читается актуальным для будущих вызовов, а каждый результат
  сохраняет собственный снимок и fingerprint.

## 21. План первой кодовой итерации

### 21.1. Цель и демонстрируемый результат

Первая итерация не пытается закончить все навыки. Она должна превратить текущую
заготовку в устойчивую оболочку чата и доказать три главных механизма:

1. настройки чата действительно влияют на следующий вызов;
2. пользователь видит состав контекста и умеет вызвать действие из палитры;
3. один настоящий Tool выполняется через общий реестр и рисуется в ленте.

Демонстрационный сценарий после итерации:

```text
открыть вопрос
→ выбрать персону, строгость и совместимую модель
→ увидеть чипы Вопрос / Профиль / Эталон / Материал
→ задать обычный вопрос и получить плавный потоковый ответ
→ открыть палитру команд клавишей /
→ выбрать «Найти в материалах»
→ увидеть найденные фрагменты и открыть Материал
→ открыть «Сдать ответ»
→ получить существующий типизированный вердикт в новой ленте
```

### 21.2. Граница итерации

#### Работает по-настоящему

- текущий экзаменационный режим;
- обычный чат и остановка генерации;
- форма ответа, Попытка и существующая проверка;
- персона, строгость и модель на уровне сессии;
- профиль проекта в контексте;
- context flags и раскрываемые чипы;
- палитра по кнопке `+` и клавише `/`;
- локальный BM25-поиск по Материалам как `search_project_materials`;
- типизированные блоки формы, вердикта и результата Tool;
- корректное восстановление истории без мигания потокового ответа.

#### Видно, но честно недоступно

- режим `Разобраться`;
- `/вопрос`, `/подсказка`, `/точность`, `/задание`, `/билет`;
- диктовка;
- внешний поиск статьи, видео или публикации;
- сохранение найденного оригинала и сводка.

У такого пункта есть описание, метка `Позже` и причина недоступности. Нажатие не
создаёт фальшивое сообщение и не списывает токены. Обычный пользовательский
вопрос при этом остаётся рабочим и не называется навыком `/вопрос`.

#### Не входит

- model-native tool calling и агентный цикл;
- внешние поисковые провайдеры и новые сетевые зависимости;
- эмбеддинги и RRF;
- память раздела, билет, доспрос и возражение;
- мобильная перестройка всей Рабочей области;
- изменение алгоритма оценки ответа.

### 21.3. Интерфейс

Интерфейс берёт удачные паттерны современных кодовых и исследовательских чатов,
но не копирует их пиксельно. От Codex нужен компактный управляющий слой у
композера и видимое выполнение действий; от Claude — спокойная читаемая лента и
отдельные содержательные карточки. Всё остаётся внутри существующей вкладки
Рабочей области Tentex.

#### Шапка

Слева — название области и короткий текущий вопрос. Справа — единый контрол
`Экзаменатор`, история и `Новый чат`. Контрол открывает popover:

- персона: спокойный преподаватель, нейтральный экзаменатор, строгий проверяющий;
- строгость: мягко, обычно, строго;
- модель: только модели, поддерживающие одновременно поток и structured output;
- пояснение, что изменения действуют на следующие ответы.

Изменение сохраняется сразу. При ошибке прежнее значение остаётся выбранным,
рядом показывается локальная ошибка с повтором.

#### Лента

- сообщение пользователя — компактный нейтральный блок;
- обычный ответ ассистента — плоский читаемый Markdown без тяжёлого пузыря;
- форма, вердикт и Tool — отдельные типизированные карточки;
- текущая операция показывает статус `Ищу в материалах…`, `Проверяю…` или
  `Готовлю ответ…`, а не универсальный spinner;
- источник открывается рядом через существующую механику Рабочей области;
- кнопка перехода вниз появляется только когда пользователь ушёл от конца.

Вердикт сохраняет три содержательные полосы `обязательное / усиливает / лишнее`,
но получает компактную шапку исхода, раскрываемый проверенный ответ и отдельную
строку ограничений источников. Процент знания не добавляется.

#### Контекст

Над композером находится тихая строка чипов. Клик открывает popover с включёнными
элементами, объёмом и переключателем. Обязательный для операции элемент нельзя
выключить без объяснения. Строка `В запрос уходит: ...` удаляется: она занимает
место, но не позволяет управлять составом.

#### Композер

Одна поверхность без вложенных рамок:

```text
┌ Спросите или опишите ответ ─────────────────────────────┐
│                                                        │
│ [+]  [Экзамен ▾]  [Модель ▾]       [микрофон] [→/стоп] │
└────────────────────────────────────────────────────────┘
```

- `+` и `/` открывают одну палитру;
- палитра группирует `Экзамен`, `Материалы`, `Исследование`;
- доступны стрелки, Enter, Escape и поиск по названию/описанию;
- режим показывается компактным селектором, `Разобраться` пока disabled;
- модель дублируется в нижней панели для быстрого доступа, но открывает тот же
  контрол состояния, что и в `Экзаменаторе`;
- микрофон disabled с tooltip, пока диктовка не подключена;
- Send превращается в Stop без изменения ширины кнопки.

На узкой ширине нижняя строка переносится предсказуемо, карточки становятся в
одну колонку, popover не выходит за экран. Цвет применяется только семантически,
анимации — короткие CSS-переходы конкретных свойств с учётом
`prefers-reduced-motion`; `transition: all` и каскадное появление сообщений не
используются.

#### Пустое состояние

Три настоящих действия:

- `Сдать ответ`;
- `Задать вопрос` — ставит фокус в композер;
- `Найти в материалах` — открывает мини-форму запроса.

Будущие функции находятся в палитре с меткой `Позже`, а не занимают главную
пустую поверхность.

### 21.4. Целевые контракты первой итерации

#### Настройки сессии

В `ChatSession` добавляются:

```text
mode: exam | study                  default exam
model_override: {provider_id, model_id} | null
context_flags: {
  profile: true,
  reference: true,
  fragments: true,
  attempts: false,
  section_memory: false
}
```

`model_override` хранится JSON-снимком, а не внешним ключом: запись должна
оставаться читаемой, если подключение провайдера позже удалено. API валидирует
пару `provider_id + model_id` по безопасному каталогу. `study` уже есть в enum,
но сервис до следующей итерации возвращает `chat_mode_unavailable`.

Одна операция
`PATCH /projects/{project_id}/chat/sessions/{session_id}/settings` изменяет
`mode`, `persona`, `strictness`, `model_override` и `context_flags`. Частичное
обновление не сбрасывает неуказанные поля.

#### Capabilities и Tools

`GET /projects/{project_id}/chat/capabilities?node_id=...` возвращает режимы,
команды и Tools. У каждого элемента есть `available` и
`unavailable_reason`; frontend не держит скрытый второй список доступности.

Первый Tool:

```text
key: search_project_materials
effect: read
confirmation: never
input: {query, node_id, limit <= 10}
result: {items[{fragment_id, material_id, title, page, excerpt, score}]}
output_kind: material_search_results
```

Запуск:

`POST /projects/{project_id}/chat/sessions/{session_id}/tools/{tool_key}/runs`.

Ответ создаёт `ChatToolRun`; завершённый результат прикрепляется к
`ChatMessage.payload` и рисуется в истории. Повтор открытия чата не запускает
поиск снова. Для первой итерации endpoint может отвечать синхронно: состояние
`queued/running` уже есть в модели, но фоновой очереди пока нет.

#### Поток сообщений

Событие SSE `started` уже содержит `message_id`; frontend использует его как id
оптимистичной реплики. `delta` складываются в буфер и публикуются не чаще одного
кадра. `completed` должен вернуть финальную `ChatMessageRead`, чтобы заменить
оптимистичную запись без полного перечитывания сессии. При `failed` и `stopped`
частичный текст остаётся в ленте с соответствующим состоянием.

### 21.7. Условия завершения первой итерации

Итерация завершена, если одновременно выполнено следующее:

1. профиль, персона, строгость и model override видны в сохранённом manifest;
2. preview и фактический вызов имеют один fingerprint;
3. локальный поиск проходит через ToolExecutor и не вызывает модель;
4. будущие Tools нельзя запустить обходом UI;
5. потоковая реплика не исчезает между последним delta и серверным сообщением;
6. все старые формы ответа и вердикты продолжают открываться;
7. интерфейс полностью управляется клавиатурой и не ломается на узкой ширине;
8. disabled-возможности названы честно и не создают данные;
9. backend-тесты, ruff, typecheck, build и lint проходят;
10. фактический контракт обновлён после, а не до реализации.
