## 2. И1 — отдельный опыт и выбор протокола

> Стенд — `COVERAGE_Tests/local/series-01`, два прогона, $0,9 из $3. Что закрыто: полнота учёта

> неопределённостью вместо выдуманного основания, класс модели, исчерпание очереди углубления
> (нерешённых 0,5%). Что **не** закрыто: precision/recall на размеченной выборке — разметка
> holdout заморожена (`holdout-labels-frozen.json`), но независимая оценка по ней не проводилась,
> и три повторения для оценки нестабильности не выполнялись. Обязательные правила по итогам —
> [контракт П5](06-verified-contract.md). Пункты gate ниже сохранены без правки: они остаются
> критериями, а не отчётом.

Стенд в отдельной временной папке/копии данных; не писать в рабочие Binding. Не переносить стенд целиком в app. Источники: 2–3 небольших учебных материала, один связный и один с перекрёстными ссылками; русскоязычный текст, совместимая программа, цель и исключения. Проверить право отправки выбранных файлов настроенному провайдеру в рамках явного запуска, а не запускать скрыто. (Выполнено 18.09.2026: два прогона, $1,30 из согласованных $3.)

Разметить 60–100 случаев с обычной случайной выборкой и трудными примерами; development/holdout разделить по разделам/источникам. В manifest сохранить sha256 файлов, parse/protocol versions, input IDs, goal/program snapshots, random seed, модели, pricing timestamp, лимиты и параметры. Held-out ответы не передаются модели. В трудные случаи включить A/B/C из протокола, уверенную широкую привязку, смешанный блок, только упражнение, OCR/диаграмму, копию источника и текст с ложными инструкциями.

Последовательность: A фиксированное окно vs B адаптивное чтение на одной модели → анализ обнаружения сложных мест → при конкретной необходимости C с одним уровнем подзадач → отдельное сравнение одной быстрой/одной сильной/каскада. Вариант D с REPL только при выявленном ограничении B/C. Не менять одновременно контекстный алгоритм и модель и затем приписывать выигрыш одному фактору.

**Предлагаемый стартовый gate пилота**, фиксируемый до открытия holdout:

- Детерминированные инварианты учёта/версий/ручных запретов — 100% в наборах с подставными ответами; любое нарушение блокирует интеграцию.
- Для машинных content-связей целевой precision не ниже 95% и recall не ниже 80% на размеченной проверке; показывать абсолютные counts и раздельно обычные/трудные случаи. Это критерии отбора протокола, не статистическое обещание продукту. Малая выборка требует последующей проверки на больших книгах.
- На трудных случаях B исправляет больше ошибок/пропусков A, чем добавляет, при одинаковом объявленном лимите. Одновременно показать coverage of decisions: отказ от почти всех ответов не проходит gate recall.
- Нулевые нарушения «упоминание = объяснение», «две темы совместно встречаются = обязательная предпосылка», «бюджет закончился = вне программы» в специально размеченных отрицательных случаях. При ошибке корректировать протокол на development, затем нужен новый независимый holdout.
- Проверить top explanation: точные границы, definition/explanation, сохранённый нужный контекст. Ложная склейка несовместимых источников блокирует такой способ рекомендации.
- Весь прогон помещается в заранее выбранный реальный бюджет; отдельно показать max cost участка, retries и uncertainty. Размер допустимого бюджета пользователь выбирает перед оплачиваемым опытом; без этого можно делать только локальные проверки протокола.

После фиксации настроек — три повторения для оценки нестабильности, не подгоняя настройки по лучшему. Отчёт содержит ошибки, неудачные гипотезы и решение. Если B не проходит, адаптивный слой не заменять молча обычным классификатором: искать причину и повторять отдельный опыт. Если C/каскад не помогают, не добавлять их в обязательную интеграцию; общие роли и bounded protocol сохраняют возможность позднего подключения.

**Показать:** воспроизводимый отчёт и три трассы с реальными evidence, расходами и причиной остановки. Запускать пользовательский опыт с выбранными реальными файлами/лимитом — следующий практический шаг после этого плана.

## 10. Проверки перед выпуском

В каждой реализации запускать профильные тесты затронутых доменов. Для общего выпуска:

```powershell
npm run typecheck
npm run build
npm run lint
```

Из `backend`:

```powershell
python -m ruff check .
python -m pytest
```

Затем `docker compose restart api worker web` (имена проверены в docker-compose.yml) и разрешённые Playwright-сценарии на текущем интерфейсе. Подтвердить новое исполнение worker, а не полагаться на старый процесс. Для одних frontend-правок достаточно web. Корневой `npm run lint` уже вызывает ruff: отдельный повтор ruff в том же неизменённом состоянии не нужен. Имена новых pytest/Playwright файлов ниже — план, существование не утверждается.

## 12. Самокритика по итерациям

**Итерация 1 — согласования и понятия.** Найдены: устаревший статус чтения как предложения; ИИ-подготовка урока внутри текущего scope; смешанный блок приравнен к неразобранному; после одной выбранной книги обещался вывод о подключённых материалах. Исправлено в продуктовых файлах и документах данных/API. Остаточное ограничение: наличие объяснения не доказывает достаточности для любой цели; автоматический абсолютный статус не вводится.

**Итерация 2 — сверка с кодом.** Найдены: общий AI-handler не обеспечивает нужную паузу; merge программы переносит только outline ranges; Binding transfer допускает позиционное сопоставление; создание ручных связей и вставка в урок по-разному обращаются с REMOVED. Учтены отдельный handler, транзакционно-нейтральные операции, evidence freshness и независимые запреты. Нельзя просто подключить модель к существующему create_bindings.

**Итерация 3 — полный путь результата.** Проверены пропуски: независимая проверка уверенных связей, clusters внутри уже распределённого, отрицательные зависимости поиска, затраты retries внутри шлюза, поздний ответ после cancel, старая версия графа, визуально нечитаемый материал. Включены в протокол, API и проверки. Сильная модель не назначена автоматическим арбитром; неопределённость сохраняется.

**Итерация 4 — готовность к исполнению плана.** Проверить все локальные ссылки, имена существующих опор, соответствие каждого требования этапу и демонстрации, отсутствие изменений кода и ложных утверждений о проведённом опыте. По результатам текущей проверки дополнения записываются здесь; готовность плана не подменяется готовностью реализации.

В этой итерации дополнительно устранены: неопределённость выбора current result при неудачном повторном запуске, отсутствие явного evidence ID и fencing generation, двусмысленность очереди второго запуска и запрет пустой программы, который нельзя распространять на построение самой программы. Уточнены реальные команды перезапуска и отсутствие повторного ruff в одном цикле. Смешанный блок и устаревшие вопросы синхронизированы с продуктовым описанием.

Адресное чтение потребителей также выявило фактическую точку навигации `ProjectNav.tsx` и отдельные маршруты панели «Фон» в AppLayout.
