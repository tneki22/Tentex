# Данные, актуальность и атомарные изменения

Рабочий контракт будущей реализации. Связанные документы: [индекс](README.md), [протокол](02-research-execution.md), [API](03-api-and-surfaces.md), [проверенный контракт](06-verified-contract.md). Где этот документ расходится с контрактом, действует контракт: он опирается на измерение.

## 1. Три разные единицы

**Блок** — единица обязательного учёта. **Фрагмент и точный диапазон** — адресуемое основание и единица существующей привязки. **Исследовательский участок** — временная задача по одному или нескольким блокам, включая контекст вне них. Их нельзя хранить как одну сущность.

**Target** — единица решения модели, валидации и receipt: обычный блок целиком либо один детерминированный интервал большого блока ([протокол §2](02-research-execution.md#2-полный-обзор)). На стенде они совпадали, потому что разбиение не понадобилось, и контракт П5 называет их одним словом; в продукте совпадение не гарантировано. У блока из четырёх интервалов четыре независимых исхода: провал интервала 2 не отменяет решения по 1, 3 и 4 и не откатывает строку блока. Исход самого блока агрегируется из его targets — `inspected` только когда все интервалы дали структурно допустимый ответ, иначе блок остаётся в работе с уже сохранёнными частичными решениями. Пакет собирается независимо от границ блоков, поэтому в одном ответе модели встречаются targets разных блоков и разной природы.

Пример: блок B состоит из F1 (объяснение изоляции), F2 (пример блокировок), F3 (реклама курса). Система учитывает B один раз; F1 и F2 получают содержательные связи, F3 — служебный исход. Чтение предыдущего блока A как контекста не завершает его первичную обработку.

Содержательные назначения: definition, explanation, example, exercise. Отдельно mention и context. Назначений у одного участка может быть несколько; происхождение machine/manual/confirmed и механизм pass_two/lesson/outline не заменяют назначение. У старых связей назначение unknown, пока не исследовано или не указано человеком.

Связь остаётся на существующем MaterialFragment. Основание внутри большого фрагмента может содержать проверенные текстовые границы/цитату и список контекстных фрагментов; это не новое разбиение опубликованного материала. Если фрагмент смешанный, его нельзя целиком назвать объяснением. Чтение показывает выделение и окружающий текст, а вставка в урок использует уже поддерживаемые границы; точность до произвольного символа не обещается, если редактор её не поддерживает.

## 2. Минимальные дополнения к схеме

Названия предварительные, ответственность и ограничения обязательны. Хранение — текущая SQLite/Alembic. Пять новых таблиц и расширение существующей Binding по [разбору 18.09](05-architecture-review.md); отдельная таблица 1:1 для её метаданных не нужна. Новая очередь, отдельная графовая БД и копия полного текста не нужны.

| Запись | Поля и ограничения |
|---|---|
| `coverage_runs` | id, project_id, job_id UNIQUE, mode (initial/incremental/deep_program), request_key UNIQUE в проекте, schema/protocol versions, снимок цели и программы, scope материалов с ревизиями, context_scope, fingerprints, model-role snapshot, limits, control_version, stop_reason, created/finished. Состояние исполнения берётся из BackgroundJob, не дублируется вторым enum |
| `coverage_block_results` | run_id, material_id, material_revision, block_id, order и состав фрагментов; UNIQUE(run_id, block_id). Сначала manifest-строка pending, затем validated result с fragment dispositions, consumed spans, publication state, error/reason, result_version. Из строки без результата видно, что блок ещё не обработан |
| `coverage_tasks` | run_id, kind (overview/refine/synthesis), target IDs, task_key UNIQUE в запуске, state, parent_id optional, question, checkpoint, bounded result, dependency refs/search scope, call receipts, stop_reason. Это задания внутри одного job, не вторая внешняя очередь |
| `coverage_findings` | project_id, run_id, kind (new_topic/rename/split/merge/prerequisite/overlap/conflict), proposal_version, state, evidence refs, отличие/ограничения цели, suggested operations, dependency fingerprints, feedback, applied_action_id. Отдельный receipt выбранных операций позволяет частично применять составное предложение |
| Существующая `Binding` | Nullable-поля roles, semantic_kind (unknown/content/mention/context), evidence_ref на версию task/result и локальный ключ, semantic_revision для версии назначения. Проверенные ревизии/зависимости остаются в указанном результате; freshness вычисляется по ним. Это текущая проекция, не копия доказательств |
| `coverage_decisions` | project_id, kind (hide_reading/prefer_reading/reject_link/out_of_goal/service_override/prerequisite), target scope, source revision + anchor fingerprint, goal fingerprint при необходимости, payload, version, action_id. Хранит личный выбор и запреты независимо от переноса/удаления Binding |

JSON допустим для ограниченного ответа участка, снимков и перечня зависимостей. Не прятать всю коллекцию и все связи в одном JSON job.checkpoint. Часто фильтруемые поля project/run/material/topic/state индексируются; подробности подгружаются по страницам. Foreign key на изменяемый фрагмент в историческом свидетельстве nullable/SET NULL с сохранённым locator, ревизией и хешем; каскад удаления Binding не должен незаметно стирать историю пользовательского запрета. При физическом удалении проекта его исследовательские данные удаляются вместе с ним.

Диагностика извлечения принадлежит MaterialRevision.summary и существующим diagnostics страницы/материала, а не проектному CoverageRun. Сохранять возможности адаптера, известные пропуски и происхождение OCR/ASR. В сериализации элементов и адресах фрагментов сохранять bbox_reliable и тип локатора; синтетические координаты логической страницы не выдавать за физические. Новая проектная таблица для этих общих данных не требуется. Manifest фиксирует версию диагностики вместе с ревизией.

Добавить `Project.coverage_revision` для конкурентных изменений карты. GoalPassport получает только подробность дерева; семантический fingerprint вычисляется из уже существующих полей цели и значимых полей программы. `BackgroundJobKind` расширяется одним видом исследования; `deep_program` использует тот же обработчик с другим контрактом результата. Общий kind не означает общее место назначения: переход из панели «Фон» строится по `coverage_runs.mode` — initial/incremental ведут в Покрытие, `deep_program` в Программу. Идентификатор результата/задачи передаётся через существующий AiRun.context_manifest, а job_id связывает вызов с запуском; отдельное выдуманное поле metadata не требуется.

У run дополнительно `execution_generation`: увеличивать при каждом получении задания worker, публикация проверяет и generation, и актуальный lease_owner.

Это **внутренний fencing-токен**, и клиенту он не принадлежит: он растёт на каждом взятии задания, в том числе при штатной передаче кванта обратно в `queued`, поэтому пауза, отправленная с только что прочитанного значения, ловила бы 409 на ровном месте. Для пользовательских команд у run есть отдельный `control_version` — он меняется только от смены намерения (pause/resume/cancel), и именно его проверяет `/control`. Один счётчик на две задачи не годится: у fencing и оптимистичной блокировки разный источник изменений. Пока задание берётся один раз и передачи кванта нет, оба счётчика ведут себя одинаково, поэтому ранняя реализация вправе проверять `execution_generation`; отдельный `control_version` обязателен ровно с того момента, как появляется возврат задания в `queued` между квантами. Создание запуска резервирует writer до проверки существующего queued/running/paused исследования проекта; конкурирующий старт возвращает его ID, а не создаёт второй manifest. Это два разных случая, и путать их нельзя: **повтор того же `request_key` с тем же телом** — идемпотентность, 200 и тот же запуск; **другой запрос при занятом проекте** — 409 `coverage_run_active` с ID действующего запуска в теле ошибки, чтобы интерфейс предложил продолжить или отменить его. Это короткая проверка под SQLite-writer, не блокировка проекта на время модели.

Каждое evidence внутри task/result имеет устойчивый local key; внешний evidence_id составляется из result UUID и этого key. Его endpoint валидирует обе части и project ownership. Не выводить ID из текста цитаты. При reuse manifest-строка содержит ссылку на конкретную совместимую версию прежнего result, а не копию ответа и не ещё один счётчик.

Текущий результат блока выбирается по активной ревизии материала и применённому compatible result version; более поздний failed/pending run не затирает прошлое валидное решение. При необходимости перепроверки старое явно stale и исключено из актуальных показателей. Bindings — источник текущих связей, block results — источник полноты/исходов; ручная коррекция пересчитывает проекцию исхода без изменения исторического ответа модели. Единственная добавленная связь не делает неизвестный остаток блока решённым.

Queries покрытия используют только initial/incremental результаты pass2. Manifest deep_program показывает полноту построения программы, но не участвует в показателях исследования относительно утверждённой программы. Общий сборщик snapshot учитывает phase=draft/active для pass1; active textbook обязателен для pass2.

## 3. Полный учёт и смешанные блоки

До первого вызова сервер материализует manifest всех выбранных готовых ревизий. Модель его не редактирует. Все фрагменты каждого блока должны иметь явный исход: содержательное соответствие, только упоминание/контекст, содержательное вне программы, служебное, смешанное с указанными частями или unresolved. Для mixed перечисляются основания обеих частей; неизвестный остаток остаётся unresolved. В пустом блоке без фрагментов учитывается причина и качество разбора, а не выдуманное успешное чтение.

Manifest гарантирует учёт подготовленного представления. Потерянная парсером таблица не появляется в нём автоматически: качество извлечения и известные непроверенные области показываются отдельно. Подпись «просмотрены все блоки подготовленного текста» не означает «всё содержимое исходного файла понято». Пакеты модели собираются независимо от границ блоков по правилам [структурного разбиения](05-architecture-review.md#6-умное-разбиение-без-отдельного-агента-сегментатора).

Две независимые оси:

- Работа: pending, processing, inspected, error. Inspected означает, что все части прочитаны и получен структурно допустимый ответ, а не что весь смысл установлен.
- Исход: linked, outside_program, service, mixed_resolved, unresolved. Устаревание отдельно, не новый смысловой исход. Пользовательский выбор needed/irrelevant не выводится только из outside_program.

Большой блок состоит из детерминированных частей: covered ranges должны закрывать входной диапазон без пропусков; перекрытие контекстных окон не удваивает учёт. Результат становится inspected только после всех частей. Проверка разбиения доказывает обработку входа, но не понимание моделью.

### Показатели

1. **Полнота просмотра запуска** = inspected / manifest blocks. Ошибки, pending, устаревшие после изменения исходника показываются отдельно. Исторический запуск сохраняет свой знаменатель; текущая карта сравнивает его с активными ревизиями.
2. **Темы с содержательным материалом** = видимые изучаемые узлы с актуальной content-связью / все видимые изучаемые узлы. Sections не считаются, topic/subpoint считаются каждый сам по себе. Предки не получают содержание потомка автоматически. Unknown legacy отдельно: «Есть прежние связи; назначение не проверено».
3. **Материал**: прежде всего распределение всех блоков. Из полностью разобранных содержательных блоков отдельно fully linked, mixed resolved, outside program. Дополнительная доля `(fully linked + mixed resolved) / (fully linked + mixed resolved + outside program)` подписана **«Блоки с материалом по программе среди разобранных»**, рядом mixed count. Она не называется долей всего текста, не означает полное покрытие смешанных блоков; неопределённые и устаревшие не прячутся. При нуле знаменателя «Нет данных». Упоминания без содержательной связи не попадают в числитель.
4. **Основа чтения**: определение и объяснение с совместимыми основаниями. Пример/упражнение само по себе даёт содержательную связь, но не эту основу. Никакого процента освоения.

Пример: 100 блоков = 20 полностью связаны + 10 смешанных разобраны + 15 вне программы + 10 служебных + 30 pending + 5 ошибок + 10 inspected/unresolved. Просмотрено 65/100; содержательная связь есть у 30 из 45 разобранных содержательных блоков, 10 из них смешанные. Это не «67% всего материала изучено». Итоговые показатели вычисляет сервер из записей, не модель. Матрица/граф используют тот же запрос и union ID при свёртке дерева.

## 4. Публикация и ручные ограничения

Сначала ответ валидируется: схема, полный состав targets, принадлежность проекту, ревизии, ссылки, роли, причина неопределённости. Текст документа не может изменить протокол или разрешённую область.

**Единица валидации, публикации и receipt — решение по одному target** (блок целиком или интервал большого блока, см. §1), **а не ответ модели целиком** (измерено 18.09.2026, [контракт §2](06-verified-contract.md#2-контракт-1-изоляция-пакета-обязательна)). Не прошедшее проверку решение становится `unresolved` в одиночку и не отменяет соседние решения того же ответа; отбраковка всего пакета вдвое снижает долю разобранного материала при большей стоимости. То же на уровень ниже: негодная опора отклоняется одна, привязка без опор снимается, и только решение без привязок становится `unresolved`. Так же и на уровень выше: `unresolved` одного интервала не отменяет опубликованные связи соседних интервалов того же блока, а только оставляет блок непросмотренным до их завершения.

**Опора проверяется по смыслу, а не побайтово** ([контракт §3](06-verified-contract.md#3-контракт-2-опора-проверяется-по-смыслу-а-не-побайтово)). Лестница: точное вхождение → нормализованное (разделители формул, команды LaTeX, NFKC, гомоглифы, точечные выноски) → приближённое по доле слов → исправление адреса на фактически прочитанную единицу. Уровень починки сохраняется в результате; `ref_corrected` попадает в выборочный аудит. **Текст опубликованной опоры всегда берётся из снимка материала, а не из ответа модели** — иначе пользователь увидит в своём материале текст, которого там нет.

**Углубление уточняет первичный проход и не отменяет его** ([контракт §4](06-verified-contract.md#4-контракт-3-углубление-уточняет-первичный-проход-и-не-отменяет-его)). Решение задачи уточнения заменяет решение обзора по тому же блоку, только если само прошло проверку; иначе остаётся решение обзора с пометкой происхождения. Незавершённая задача уточнения оставляет результат обзора целиком. Это правило внутри одного запуска, в дополнение к правилу «более поздний failed/pending run не затирает прошлое валидное решение» между запусками.

Затем отдельная короткая project_write_transaction:

1. Повторно проверить проект, допустимое состояние job и intent остановки, lease/run generation, актуальность цели/материалов, snapshot пользовательских решений.
2. Если result receipt уже применён — вернуть прежний результат без повторных связей и счётчиков.
3. Для новой пары создать Binding(MACHINE, PASS_TWO) с назначением и evidence_ref. Существующую MANUAL/CONFIRMED не менять. REMOVED и reject_link не восстанавливать. Для старой MACHINE другого механизма не терять происхождение: добавить проверенную семантику без смены механизма; конфликт семантики — finding.
4. Обновить только принадлежащие исследованию машинные результаты в пересчитанной области; не очищать все связи проекта. Снять переставшую подтверждаться машинную связь можно только после нового полного решения по этому target, а не из-за пропуска в ответе. Причину сохранить. При техническом сбое прежняя связь становится устаревшей, не ложной.
5. Сохранить result receipt, зависимости, новые findings, увеличить coverage_revision, зафиксировать транзакцию.

**Публикация создаёт Binding и для несодержательных назначений.** `mention` и `context` нужны навигации, поэтому они попадают в ту же таблицу, что и содержательные связи, и с первой же машинной публикации любой потребитель, считающий привязки без разбора назначения, начинает завышать обеспеченность темы. Конкретно: `bindings/service.py:get_summary` фильтрует статусы, но не `semantic_kind`, а на его `fragment_count > 0` стоит индикация «есть материал» в `ProjectWorkspace.tsx`, `Program.tsx` и `Materials.tsx`. Тема с одним упоминанием загорелась бы обеспеченной — это прямое нарушение согласованного различия связей (UX §8, R-11), и происходит оно молча, без единой ошибки. Поэтому вместе с машинной публикацией `get_summary` обязан отдавать содержательное и несодержательное раздельно, учебниковые поверхности считают обеспеченность только по content, а экзаменационные потребители получают прежнее суммарное число. Разделение входит в ту же правку, что и издатель, а не откладывается до новых экранов покрытия.

Сеть и модель никогда не находятся внутри write-транзакции. Ручное действие между чтением и публикацией выигрывает; старый ответ становится неприменённым результатом с конфликтом. Полный запуск не блокирует редактор программы, уроков и просмотр карты. Фоновая публикация не добавляет сотни записей в пользовательский undo.

## 5. Изменения программы и undo

Создание темы из кандидата: preview содержит узел, parent, selected evidence и точные связи. Apply с expected_program_revision, expected_coverage_revision и proposal_version создаёт узел, выбранные CONFIRMED-связи и запись ProjectActionLog **одной транзакцией**. Повтор request_key возвращает сохранённый receipt. Не вызывать несколько публичных mutation-функций, каждая из которых коммитит и пишет отдельный undo: вынести общие транзакционно-нейтральные операции из program_chat/program.

Undo восстанавливает before-images, ручные статусы, структуру и состояние proposal; не удаляет первичный материал или весь результат исследования. Существующий журнал поддерживает последнюю допустимую пользовательскую операцию, а не произвольный time travel. Перед отменой проверить after-fingerprints затронутых сущностей: последующие фоновые изменения не должны перезаписываться старым снимком. Если есть конфликт — 409 с конкретным объектом и возможность нового preview; не выполнять частичную тихую отмену.

**Merge:** preview выбирает survivor и перечисляет переносы связей, диапазонов и LessonTopic. Объединить без дубликатов пары Binding; manual/confirmed приоритетнее machine. Если одна сторона снята пользователем, а другая активна — конфликт нужно разрешить в preview. Исчезающие темы мягко скрываются. Дочерние темы переносятся с сохранением порядка и проверкой циклов. Уроки сохраняют содержание, порядок и прогресс; ссылки на тему переводятся только как явно перечисленная часть операции, дубли LessonTopic схлопываются. Сводки/конспекты/история не сливаются и не удаляются: старые узлы остаются доступны через историю. Если затронуты будущие занятия, их связи также перечисляются, семантическая завершённость не переносится автоматически.

**Split:** исходная тема остаётся до выбора пользователя; новые темы и предложенное распределение фрагментов показываются отдельно. Нет автоматического размножения всех связей и уроков на обе темы. Если пользователь скрывает исходную тему, назначения LessonTopic выбираются явно; один урок может сохранить несколько тем. Неопределённые назначения блокируют применение именно этого split, не весь проект.

**Rename/move:** сохраняются ID. Перестановка меняет отображение; изменение смысла названия/цели требует перепроверки. **Prerequisite:** отдельное типизированное отношение между темами с основанием и пользовательским подтверждением, не parent_id. Проверка self-edge/duplicate/cycle для принятых обязательных предпосылок; overlap остаётся гипотезой и не ограничивает порядок учёбы. Удаление/undo предложения не уничтожает реальные связи материала.

**Совместное изучение:** дополнительно допустим finding `joint_study` и подтверждённое симметричное отношение в coverage_decisions. Пример: при цели понять всю теорию объяснения двух тем опираются друг на друга; показывать их рядом и давать переход к нужной теме. Это не merge и не цикл обязательных предпосылок. Требуются основания зависимости учебных результатов и соответствие глубине; простая совместная встречаемость недостаточна. Отношение не меняет порядок существующих уроков автоматически.

## 6. Инкрементальность и изменение материала

| Изменение | Действие |
|---|---|
| Новый источник | Полный manifest только его; пересмотреть соответствующие clusters и отрицательные выводы по расширившейся области |
| Новая тема | Применить уже проверенные selected links; бесплатно отобрать кандидатов по сохранённым описаниям/FTS, включая распределённые; запустить их проверку явно |
| Цель/исключения/ожидаемый результат | Сразу устаревают оценки пригодности и предложения структуры; фактические связи не удаляются. Предложить расширенную проверку, без скрытого платного запуска |
| Rename с изменением смысла / split / merge | Затронутые узлы, их связи, read/search dependencies и соседние кандидаты; отрицательные выводы тоже требуют пересмотра |
| Перестановка или display-only правка | Перестроить виды без вызовов модели; семантический fingerprint не меняется |
| Ручная связь / скрытие результата | Немедленно обновить карту/чтение и версию ограничений. Не нужен модельный вызов |
| Новая parse revision | Все затронутые решения пометить устаревшими. Точный однозначный fingerprint может подтвердить неизменный участок; позиционный перенос не делает research evidence актуальным |
| Отключение источника | Удалить из текущих агрегатов, инвалидировать зависевшие от него выводы, остановить новые чтения. Исторический run обозначить потерявшим источник |

Чтения хранят (material, revision, fragment/block, hash). Поиски дополнительно хранят запрос, filters, manifest/revision области и факт усечения. Вывод «не найдено» зависит от области, не только от возвращённых ID. При неизвестном влиянии выбирается более широкая перепроверка; нельзя обещать идеально минимальный пересчёт.

Текущий FTS содержит только активную parse revision. Перед чтением/поиском проверять соответствие snapshot; проверку активной ревизии и сам SQL-поиск выполнять в одном коротком read snapshot. При несовместимости завершить job как cancelled со stop_reason=snapshot_changed; в UI «Остановлено: материалы изменились». Затем пользователь явно перепланирует на новые версии с reuse совместимого. Это не paused: несовместимый снимок нельзя возобновить, а оставленная пауза блокировала бы создание нового run. Публикация повторяет проверку: ревизия могла измениться после поиска. Не продолжать старый run по новым hits и не строить исторический FTS без отдельной доказанной потребности.

Пользовательские снятия сохраняются независимо от активной Binding. Для переноса запрета нужны точный однозначный anchor и тема; если сопоставление неоднозначно, запросить разрешение конфликта и до него не создавать потенциально ту же связь автоматически. Перенос ручной привязки сохраняет выбор, но показывает сомнение в локаторе; исправление текста не превращает его в машинный.

Старый run после смены программы может закончить текущий вызов для диагностики, но новые несовместимые результаты не публикует. Продолжение использует новый run с reuse совместимых receipts и списком перепроверки; исторические snapshots не переписываются. Само «продолжить» без изменения снимка возобновляет тот же run.

## 7. Миграция и совместимость

Аддитивная Alembic-миграция: пять новых таблиц/индексы, nullable-семантика Binding, coverage_revision, подробность дерева, enum kind и поля адреса/качества при необходимости. Backfill старых Binding = unknown; не присваивать definition/explanation по механизму OUTLINE или MANUAL. Экзаменационные потребители сохраняют старый контракт. Новые учебниковые агрегаты используют назначения Binding и явно показывают legacy отдельно.

Перед изменением переноса/удаления прочитать все callers `transfer_bindings_on_revision`, `transfer_refs_on_revision`, `delete_project_material_bindings`, публикацию parse revision и undo. Защитить существующие сценарии test_binding_transfer/test_lesson_editing/test_material_revisions. Отдельно проверить очистку незавершённого разбора, удаление материала и каскады; потеря исторического locator показывается как недоступность, не подменяется страницей новой версии.

Развёртывание: резервная копия SQLite штатным согласованным способом → migration → проверка foreign_key_check и старых уроков/ручных связей → запуск нового worker/web. Откат приложения требует совместимой схемы; downgrade с удалением результатов допускается только после экспорта/резервной копии и отдельного решения. В текущей задаче эти команды не выполняются.
